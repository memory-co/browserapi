# trace 控制台:按操作打点的全量 DOM 快照,只读;输入全走 CDP

```bash
python3 examples/trace_console/serve.py --port 9090
# 打开 http://<这台机器>:9090/
```

和 [rrweb_console](../rrweb_console/) 是**同一个外壳、同一条输入路径**,只换了画面从哪来 ——
两个端口可以并排开着直接比(8090 是 rrweb,9090 是这个)。

## 换掉的是画面模型,不是别的

| | rrweb(8090) | 这里(9090) |
| --- | --- | --- |
| 画面 | **增量链**:一张全量快照 + 之后每一次 DOM 变更 | **离散全量快照**:每次操作前后各打一张 |
| 一条坏了 | **之后全错**,而且不自恢复、不报错 | **只错这一张**,下一张照样对 |
| 往页面里注入 | rrweb 记录器,**五百多 KB** | 只有一个**十几行的光标探针** |
| 中间过程 | 连续,动画看得见 | **没有**,只有「操作前 / 操作后」两态 |
| 谁在推 | 页面里的 MutationObserver 推 | **我们从外面 `Runtime.evaluate` 拉** |

第三行是这条路容易被低估的地方:**它不需要往被自动化的页面里塞一个大库。**
[c §13.4④](../../docs/v2/works/c-pixels.md#134-换个用途同一项技术就成立了)
把「改页面」记成了 rrweb 的一项代价 —— 这条路基本不付这笔钱。

第四行是它的代价。但对「记录 tab 操作行为」这个目标来说,离散帧其实正好匹配:
你关心的本来就是每次操作前后的状态差。

## 只读是结构性的

渲染出来的那棵 DOM 整个 `pointer-events: none`,上面盖着一层透明接收层。
代码里**没有任何一条路把事件送进渲染出来的 DOM**。

```
你的鼠标/键盘 → 接收层 → WS → Input.dispatchMouseEvent / insertText → 真正那个 tab
                                → 拉一张新快照 → 整张换掉
```

**整张换掉,不打补丁** —— 这就是「误差不累积」在实现上的样子。

## 什么时候打点

按操作打,不定时轮询(静止的页面一张都不多打):

| 触发 | |
| --- | --- |
| 按下鼠标 | 前后各一张,成为一条 `click` 动作 |
| 敲完一串字(停 0.9s 收口) | 一条 `type` |
| 导航完成 / 资源到齐 / 滚动 / 按键 | 补一张(**只更新画面,不记成动作**) |
| 「重打」按钮 | 手动补一张 |

## `/trace.zip` 是一份真的 Playwright trace

顶栏那个按钮下下来,`npx playwright show-trace webmuxd-trace.zip` 直接能开。
**实测**:动作列表 3 条、标题带「谁做的」、快照面板渲染出 40 个节点、
输入框里的 `hello 世界` 读得出来。

资源(图片、字体、样式)**打进 zip 里**,不指回本服务 ——
trace viewer 是 https 的,指一个 http 地址会被当混合内容拦掉。
包内走 `trace.network` 的 HAR 条目 + `resources/<sha1>`,由它的 service worker 同源提供。

## 实测(自检页,2026-08-20)

| 验什么 | 结果 |
| --- | --- |
| 点按钮 | 真页面收到,**新快照里看得到** |
| 中文输入 | `hello 世界` 进了输入框,快照里也在 |
| 光标 `pointer` / `text` | 跟着变 |
| 光标 `url(...)` 自定义 | **降级 `default`**(白名单) |
| 只读 | 渲染 iframe 的 `pointer-events` 实测是 `none` |
| 体积 | 4 张快照 19 KB(自检页);真实页面一张约 23 KB |
| 导出 | `/trace.zip` 用官方 viewer 打开,快照面板正常 |

## 还没做的:结构共享

Playwright 自己的 snapshotter 在快照之间做**结构共享** —— 未变子树只存一个
`[[n, m]]` 引用,所以第二张往后都很小。**这里没做**:每一张都是全量,
真实页面上一张约 23 KB,每个动作两张。

要做的话得在页面里维护**跨快照稳定的节点身份**(Playwright 那个注入式
snapshotter 正是为此存在的),不是四十行序列化器能顺带做的。
现在靠两条兜:动作history 封顶 40 条、zip 用 deflate 压。

> 顺带说清一件容易搞混的事:**结构共享恰恰意味着这一张依赖前一张**
> (引用指向更早那份快照里的子树)。独立性是解析之后才有的,不是线上格式就有的。
> 不做引用的话,**线上格式本身就是彼此独立的** —— 在「误差不累积」这条性质上
> 只强不弱,代价是体积全额付。

## 其它粗糙处

- 只跟一个 tab;页面新开的 tab 不进画面
- 视口钉死 1280×800,没做跟随窗口
- 没有中间过程:两次打点之间的动画、视频、canvas 动作一概看不到
  —— 要连续画面得回到截屏那条腿
- 资源缓存在内存,只有 8 MB 单个上限,没有淘汰
- chrome 是这个服务的子进程,`Ctrl-C` 和 `kill` 都会关干净
