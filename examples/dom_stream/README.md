# DOM 流能不能顶掉 xpra 那一格

```bash
python3 examples/dom_stream/serve.py --port 7955
# 打开 http://<这台机器>:7955/
```

一个端口,**同一个 tab 的两条画面通道并排放着**:

| | 左边 | 右边 |
| --- | --- | --- |
| 传什么 | **DOM 序列化**(NodeSnapshot 嵌套数组) | **整屏 JPEG**(`Page.startScreencast`) |
| 谁渲染 | 观看端的 iframe | 远端 Chromium |
| 对应 | rrweb / Playwright snapshotter 那一类 | 第一条腿 |

**两边都能点、都能打字,输入走同一条路** —— 不管点的是哪边,都翻译成
`Input.dispatchMouseEvent` 送进同一个 tab。这正是要验的:
画面来源可以有多条,输入只有一条([b §1](../../docs/v2/works/b-input.md#1-收口在哪))。

## 页面上那三格分别在回答什么

**① 靶页(`/demo`,默认就是它)** —— canvas、CSS 动画、表单、一直在变的文字各一份。
左边缺什么,一眼能看见。

**② 对齐检查(下面那张表)** —— 这是**判断能不能用的那一格**。
它拿真实页面里每个 `#id` 的位置,和替身里同一个 `#id` 的位置逐个比。
差多少,点下去就偏多少。

**③ 两条通道各自的字节数** —— 标题栏右侧,分开算。

## 实测(靶页,1024×768,2026-08-20)

| | DOM 流 | CDP 截屏 |
| --- | --- | --- |
| 带宽 | **17.9 KB/s** | 10995 KB/s(未限流的 60fps canvas) |
| canvas 的画面 | **没有** —— 元素在,绘制不在 | 有 |
| CSS 动画 | 有(动画是样式,不是像素) | 有 |
| 文字更新 | 跟得上,和右边同一时刻 | — |
| **对齐** | **最大偏移 124 px** | 天然对齐 |

那 124 px 是这样来的:**canvas 在替身里画不出来 → 它那个盒子塌了 → 下面所有东西整体上移**。
于是替身里 `#phone` 在 y=289,真实页面在 y=413。

> 在左边照着按钮的位置点下去,送出去的是 289;真实页面那里什么都没有。
> **看着点在按钮上,实际点在旁边,并且不报错** ——
> 这就是 [c §5.3](../../docs/v2/works/c-view.md#53-它的边界能补的和补不了的)
> 说的那一条,现在是一个能读出来的数,不是一句话。

带宽那一栏也要照实读:**省下来的正是没画出来的那部分。** 纯文字页面上差距会小很多,
带 canvas / video 的页面上差距大,是因为那些内容根本没传。

## 结论

**顶不掉。** 不是慢一点或者糊一点 —— 是**坐标会错，而且错了不报错**。
画面来源可以退化,输入不能;而这条来源把画面的误差直接变成了输入的误差。

它该去的位置在 [c §16](../../docs/v2/works/c-view.md#16-playwright-trace不是来源是产物):
**当产物用,那三条代价一条都不成立** —— 回放上没有人操作。

## 已知的粗糙处(这是原型)

- 快照 **100ms 轮询一次**,不是按变化推。页面里的 MutationObserver 只能说"脏了",
  序列化本身还得拉一次
- **每次都发全量**,没做 `[[n,m]]` 增量引用 —— 真做要传的字节还会更少
- `resourceOverrides` 没接:外站的 CSS / 图片在替身里会去打原站
- iframe 用 `sandbox="allow-same-origin"` 才量得到对齐;脚本已经在序列化时剥掉了,
  但真做要重新想这里的边界
- 起来的 chrome 是这个服务的子进程,**`Ctrl-C` 和 `kill` 都会把它关掉**
  —— 第一版没接 SIGTERM,反复重启漏了九十多个进程,现在补上了
- 右边那条没限流(`everyNthFrame: 1`),webmuxd 自己的管线是有回执和降质的
  ([c1](../../docs/v2/works/c1-quality.md)),所以那个 KB/s 只能当上限看
