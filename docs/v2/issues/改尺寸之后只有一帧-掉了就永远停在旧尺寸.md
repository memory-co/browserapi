# 改尺寸之后只有一帧,掉了就永远停在旧尺寸

**状态**:**已定位机理,未修**(2026-08-23)。
**影响**:JPG 那条腿,人改窗口大小之后**画面可能一直停在旧尺寸**,
而观看端那个 `<img>` 的 CSS 尺寸已经跟着变了 —— 于是一张旧图被拉伸,
**没有任何报错**。`v2_browser_pixel_align` 跑全量时偶发红,红的就是这个。

## 量到的

改尺寸之后重发 `Page.startScreencast`,Chromium **只出一帧**:

```
第一次开                   要 1260x774 → 收到 1 帧
直接重发(不 stop)          要  980x574 → 收到 1 帧
先 stop 再开               要  700x500 → 收到 1 帧
```

(顺带排除了一个猜测:**不 stop 直接重发是有效的**,参数会生效、也会出帧。)

**只有一帧,意味着没有第二次机会。** 被测的是 `example.com` —— 一张静态页,
之后再没有 damage,也就再没有帧。那一帧只要在任何一环掉了,
画面就**永远**停在旧尺寸。

单独跑必绿(每次改尺寸观看端收到 3–4 条下行);只有跑全量、机器忙的时候
才红。所以掉的那一下和负载有关,但**"只有一帧"这个设计本身才是根因** ——
负载只是把它按出来。

## 怀疑掉在哪(还没坐实)

- `screen.py: _on_frame` 有三道闸:`sid != self._sid`、`not self.jpg.on`、
  `not self.viewers`。改尺寸那一刻正好在重启截图流,三道都可能短暂不成立。
- `cast_id` 是"每次 start 递增"的,客户端靠它丢旧帧 ——
  重启前后那一帧的归属如果判错,就会被当成残帧丢掉。

## 修的话该往哪个方向

**不该是"多等一会儿"**,而是**让那一帧变得不可丢**:

- 改完尺寸之后,服务端确认观看端拿到了新尺寸的帧,没拿到就再推一次
  (`Page.captureScreenshot` 兜一张也行);
- 或者让 `cast` 那条消息带上尺寸,观看端发现帧尺寸和 `cast` 对不上就主动要一张。

## 为什么先不修

改的是背压那一圈([c1](../works/c1-quality.md)),那儿的每一条都有理由,
不该顺手动。而且现在**有一条测试盯着它** —— 它偶发红,红了就是这件事。
