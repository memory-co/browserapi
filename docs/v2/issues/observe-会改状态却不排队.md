# `observe` 会改状态,却不走那把动作锁

**状态**:未修。
**影响**:对另一个 tab 做一次 `observe`,会把正在跑的 `act` 的前台切走;
人正在看的画面也跟着跳。

## 量出来的

```
两个 tab,当前是 t_2
observe 了 t_1 → 现在当前是 t_1
notes: ['为了拍这张图,这个 tab 被切到了前台']
```

**它自己在 notes 里说了。** 说了是对的([i §2③](../works/i-agent-surface.md#2-动词表)
那条"每个动词都要能回答做完之后页面变成什么样"),
问题不在"没说",在**它和 `act` 之间没有次序**。

## 为什么会这样

`observe` 要像素就得在前台 —— Chromium 不渲染后台 tab,拍出来是白的或旧的。
所以它调 `bring_to_front()`,而那一下是 `tabs.activate()`,**改的是 session 状态**。

而 [`sessions.py`](../../../webmuxd/sessions.py) 那条规矩:

> **一个 session 同时只跑一个动作**,并发调返回 `409 busy`,不排队、不交错。

`act()` 拿 `_action_lock`,**`observe()` 不拿**。于是:

```
act 在 t_2 上点一个按钮(锁着)
    ├─ 与此同时 observe t_1 → activate(t_1)
    └─ act 后面那几步在"当前 tab 已经不是 t_2"的世界里继续跑
```

## 这算不算 bug,取决于 observe 是不是"动作"

两种说法都成立,而**这正是问题** —— 现在的代码等于两种都选了一半:

- **observe 是只读的** → 那它就不该 `activate`。可它必须,否则拍不到东西
- **observe 是动作** → 那它就该排队,`409 busy` 一视同仁。可它现在不排

**结论只能有一个。** 倾向后者:它确实改了状态,那就按动作算 ——
读一眼要等一个正在跑的 act 结束,这是对的,因为那一眼本来也拍不到
一个操作到一半的页面。

顺带要想清楚的:`/api/screenshot` 和 `/api/text` 也走 `bring_to_front`,
同一条口子。

## 一条更小的观察

顺着量出来的:`observe()` 那五个 CDP 往返(元素表 / page / 盲区 / 正文 / 截图)
之间同样没有锁 —— 所以"一次调用 = 一个时刻"从来没有被强制过,
只是把窗口从三个 HTTP 往返压到五个 CDP 往返(实测 95ms)。
**是程度差别,不是性质差别** —— 文档里别写成后者。
