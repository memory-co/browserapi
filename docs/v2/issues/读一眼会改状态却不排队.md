# 读一眼会改状态,却不走那把动作锁

**状态**:未修。
**影响**:对另一个 tab 读一眼(`/api/screenshot`、`/api/text`),
会把正在跑的 `act` 的前台切走;人正在看的画面也跟着跳。

## 量出来的

```
两个 tab,当前是 t_2
读了 t_1 一眼 → 现在当前是 t_1
```

**它一声不吭。** 原来那个 `/api/observe` 至少还在 notes 里说一句
"为了拍这张图,这个 tab 被切到了前台";口子砍成两个之后
([capture.py](../../../webmuxd/capture.py)),`/api/screenshot` 回的是裸字节,
连那句话都没地方放。问题因此更明显,不是更轻。

## 为什么会这样

读一眼要像素就得在前台 —— Chromium 不渲染后台 tab,拍出来是白的或旧的。
所以 `Session._reading_session()` 调 `bring_to_front()`,
而那一下是 `tabs.activate()`,**改的是 session 状态**。

而 [`sessions.py`](../../../webmuxd/sessions.py) 那条规矩:

> **一个 session 同时只跑一个动作**,并发调返回 `409 busy`,不排队、不交错。

`act()` 拿 `_action_lock`,**读那条不拿**。于是:

```
act 在 t_2 上点一个按钮(锁着)
 ├─ 与此同时 GET /api/screenshot?tab=t_1 → activate(t_1)
 └─ act 后面那几步在"当前 tab 已经不是 t_2"的世界里继续跑
```

## 这算不算 bug,取决于「读一眼」是不是动作

两种说法都成立,而**这正是问题** —— 现在的代码等于两种都选了一半:

- **读是只读的** → 那它就不该 `activate`。可它必须,否则拍不到东西
- **读是动作** → 那它就该排队,`409 busy` 一视同仁。可它现在不排

**结论只能有一个。** 倾向后者:它确实改了状态,那就按动作算 ——
读一眼要等一个正在跑的 act 结束,这是对的,因为那一眼本来也拍不到
一个操作到一半的页面。

两个口子走的是同一条路(`Session._reading_session()`),**改一处就够**。

## 一条顺带没有了的

原来这儿还记着一条:`observe()` 那五个 CDP 往返之间同样没有锁,
所以"一次调用 = 一个时刻"从来没被强制过,只是把窗口压小了。

**`observe` 砍掉之后这条不存在了** —— 现在两个口子各自只有一个 CDP 往返,
本来就没有"一包东西要保持一致"这回事。

这是砍掉它顺带买到的:**少一个概念,少一类要解释的不一致。**
