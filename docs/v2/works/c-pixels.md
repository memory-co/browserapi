# c · 像素从哪来

**一句话**:CDP 截出来的 JPEG 和 xpra 发过来的区域图,**本来就是同一种东西** ——
压缩过的图片,带着位置和时间推过来。由此,「像素从哪来」构成一个清晰的接缝:接缝之上(输入、光标、tab、原生 UI、
日志、权限)只有一套实现,接缝之下可以有多条。
**第三条来源(rrweb)是对这个接缝的一次真正检验** —— 它连像素都不传,
改由观看端重排 DOM 得到画面;接缝之上确实一行不用改,
而接缝本身要付的代价比前两条大得多(§13)。

## 1. 第一条腿:让 Chromium 自己截

画面由我们生成之后,第一个问题是像素的来源。CDP 中现成的答案是
`Page.startScreencast`:请求 Chromium **在页面变化时推送一张图**。

选择它的理由:

- **零依赖。** 浏览器自带能力,headless 即可运行,不需要 X,也不需要第三方进程
- **只包含页面内容。** 截取的是渲染结果而非桌面 —— 没有窗口边框和 tab 条,
  因而不存在「裁掉浏览器 UI」一类问题
- **静止不产帧。** 页面无变化时不发送任何帧

这条路可用,效果也好于预期。**但它的形状决定了它的上限。**

`screencastFrame` 提供的是**整屏图像**。Chromium 不提供「哪一块发生了变化」,
只提供当前的完整结果。由此:

| | 结果 |
| --- | --- |
| 滚动一行 | **整屏重发** |
| 编码 | 只能**预先选定一种**,全程不变 —— 文字与图片使用同一质量 |
| 静止之后 | 就停在最后那张有损的图上,**不会变清晰** |
| 局部动画 | 一个角落在动,发的还是整屏 |

这不是参数问题,而是**该接口只提供整屏**。要突破这一上限,必须引入
damage 追踪:识别变化区域、只发送该区域,并按其内容选择编码。

## 2. 缺的那半,自己造还是拿现成的

把上面那张表倒过来,就是一张待办清单:

```
知道哪一块变了            ← damage 追踪
把变化切成合适的块        ← 区域合并、边界处理
按各块内容选择编码        ← 文字用无损,图片用有损,视频用帧间
滚动时只发位移            ← 位移编码
静止后补一张无损的        ← 质量分级刷新
链路慢了自动降质          ← 码率自适应
```

**这是一个发展了二十余年的领域** —— X11 远程显示、VNC、RDP、SPICE 各有成熟实现。
自行重做一遍,等于把本项目变成一个远程显示项目,而它的定位是「浏览器的 tmux」。

因此问题转化为:**能否引入一个已完成上述清单的实现,仅将其用作像素来源?**

一个硬性条件:**它只能负责像素。** 这类协议通常自带完整的输入、剪贴板、
音频与文件传输;一旦启用,[b](b-input.md) 中的安全收口即不复存在(见 §7.1)。
因此候选实现必须可以拆分:**取其下行,不取其上行。**

## 3. xpra:符合这个条件的那个

xpra 的定位是「X11 的 tmux」:使远端 X 程序的生命周期长于连接,允许断开后重新接入。
它为此实现的能力,恰好覆盖 §2 的清单:

```
观测一个 X 显示 ──▶ 识别变化区域 ──▶ 切分 ──▶ 逐块选择编码 ──▶ 按其协议发送
```

它自带的编码器包括 `webp` / `jpeg` / `png` / `rgb`,以及一个 **`scroll`**
(只发位移向量,不发像素),视频那档还有 `h264` / `vp8` / `vp9`。
质量自适应和"静止后补一张无损的"也是现成的。

它有一个前提:**其观测对象是一个真实的 X 显示**,因此浏览器必须是有头的;
而服务器上没有物理显示器 —— 相关的一整套(Xvfb 是什么、为何不用 Xorg)见 §6。

而其上行可以不使用:协议要求的上行仅有六个握手与回执包,**输入是可选的**(§7.1)。
这一性质决定了它可以作为一条像素来源接入,而不是一个并行的整体方案。

## 4. 关键:两条路产出的是同一种东西

CDP 那条:

```
Page.screencastFrame
   data      base64 的一整屏 JPEG
   metadata  尺寸、滚动位置、时间戳
   sessionId 哪个 tab
```

xpra 那条:

```
draw
   wid            哪个窗口
   x, y, w, h     屏幕上的哪一块
   coding         这块用什么压的:webp / jpeg / png / rgb32 / scroll
   data           压完的字节
   packet_sequence 用来回执
```

**抛开命名,两者结构一致:一块像素、它的位置、所用编码,以及一个回执号。**

| | CDP screencast | xpra |
| --- | --- | --- |
| 一次给多大 | **整屏** | **一块 damage 区域** |
| 编码谁挑 | 我们挑一次,全程不变 | **每块各挑** |
| 有哪些编码 | jpeg / png / webp | webp / jpeg / png / rgb / **scroll** / h264… |
| 回执 | `screencastFrameAck` | `damage-sequence` |
| 静止时 | 不产帧 | 不产帧 |

差异集中在**粒度**与**编码由谁选择**,而不在数据的性质上。

> 这是两者能够共用同一抽象、而 VNC 不能的原因 ——
> VNC 替换的不只是像素,还包括输入、权限与 runtime 契约。
> **仅替换像素、其余不动**,才构成可并列的两条来源。

### 4.1 它强在哪,以及它的劣势区

xpra 的长处**恰好对应 screencast 在结构上的缺失**:

| | screencast | xpra |
| --- | --- | --- |
| 更新粒度 | 整屏一帧 | **按 damage 区域** |
| 选编码 | 固定一种 | **每块区域各选**:文字走无损 webp/rgb |
| 滚动 | 整屏重发 | **`scroll` 包只发位移向量** |
| 静止之后 | 就那样了 | **`auto-refresh`:先发有损的,静止后补一张无损的** |

最后一条是其文字更清晰的根本原因:**运动时降质、静止后转为无损**。
screencast 无论是否运动都维持同一质量。

实测(同机同页,2026-08-18):

| 场景 | 结果 |
| --- | --- |
| 滚一页 Wikipedia,22 秒 | 3.71 Mbps。其中 **`scroll` 包用零字节完成了 57% 的重绘面积** |
| 全屏动画 1024×768,24 秒 | 2.86–9.34 Mbps ≈ 20 fps |

第二行是**它的劣势区间**,须一并说明:整屏持续变化时,分区域重传退化为整屏重传,
并额外承担分区开销。因此 screencast 并非被取代的旧实现,
而是**该场景下更合适的那一条**。

## 5. 接缝切在哪

> **两条来源之间唯一的差别,是像素从哪来。**
> 输入、光标、tab、原生 UI、日志、token、只读 —— **一模一样**。

(§13 的第三条来源连"像素"这个词都不成立,而上面这句话依然成立 —— 那是它最值得记的一点。)

在观看端,这一条被推广成了**通道模型**:每条通道对应一个上游系统,
声明自己能提供哪些能力,由一张固定的优先级表仲裁 ——
帧优先取 xpra,光标优先取 CDP([e §6](e-client.md#6-通道模型))。
本篇之后的内容是"帧"这一种能力上的展开。

这一条在代码中可检查:切换来源仅修改了
[`view/cast.py`](../../../webmuxd/view/cast.py) 里三个 `if`
(不发 `Page.startScreencast`、不改视口、忽略客户端 resize),
**没有第二处分叉**。

| | 谁负责 |
| --- | --- |
| 像素 | ← **只有这一行会变** |
| 输入翻译成 `Input.*` | 我们([b](b-input.md)) |
| 光标同步 | 我们 |
| tab 表 / `active` | 我们(`Target.activateTarget`) |
| 浏览器自己的那些 UI | 我们(CDP 拦截 + 自己画卡片) |
| 日志、事件、token、只读 | 我们 |

### 5.1 xpra 还提供了什么,以及为什么不取

xpra 是一个完整的远程显示协议,除像素外还提供输入、剪贴板、音频、文件传输,
以及**光标**。其中光标最值得讨论,因为我们确实需要它,并且为此付出了成本
([b §5](b-input.md#5-光标同步):向页面注入探针 + 命中测试 + 白名单)。

**它确实可用。** 实测:悬停在链接与空白之间切换时,xpra 按变化推送 cursor 包:

```
cursor  png 24×24  热点(4,4)  serial=3  720 B    ← 箭头
cursor  png 24×24  热点(8,5)  serial=4  722 B    ← 手型
```

即使输入来自 CDP 的合成事件(X 指针并未移动),Chrome 仍会更新窗口的 X 光标,
因此该通道随悬停正常变化。

两者的对比:

| | xpra 的 cursor 包 | CDP 探针 |
| --- | --- | --- |
| 数据形态 | 光标**图像**(PNG + 热点 + serial) | CSS **关键字** |
| 需要注入页面 | 否 | 是 |
| `cursor: auto` 的命中测试 | 不需要,X 已完成解析 | 需要 |
| 自定义光标 `url(...)` | 原样支持 | 白名单降级为 `default` |
| 光标名称 | 实测为空,只有图像 | 本身即关键字 |
| 每次变化的数据量 | ~720 B | 约十余字节 |
| 两条来源都可用 | **否,仅 xpra** | 是 |

**结论:不取。** 理由按重要性排列:

**① 它只存在于一条来源上。** 采用它意味着同一个用户可见行为存在两套实现,
而这正是 §5 那条接缝要避免的情况;并且 CDP 探针无论如何都必须保留 ——
screencast 那条来源没有别的选择。**这是新增复杂度,不是替换。**

**② 它会使两条来源的信任模型不一致。** 白名单存在的原因是:光标取值会写入
观看端的 `style.cursor`,而远端页面不可信。改用图像后,远端可以完全控制
观看端光标的像素 —— 这一变化只发生在一条来源上,而两条来源行为不一致
比任一种行为本身更难判断。

**③ 名称字段为空,无法低成本转换。** 若 xpra 能给出 X 光标名
(`left_ptr` / `hand2` / `xterm`),即可映射为 CSS 关键字并保持白名单模型;
实测该字段为空,只能得到图像。

**记录一个前提变化会推翻该结论的情形**:如果页面探针因某种原因必须移除
(例如对注入敏感的场景),xpra 的 cursor 通道是该来源上唯一的替代,
代价是接受光标图像。届时需要一并处理 screencast 那条来源的等价行为。

## 6. 这一套东西是什么

```
  ┌─ 浏览器 ────────────┐  画页面。它不知道自己在被录,
  │  chrome --kiosk      │  只知道"我有一个 X 显示可以画"
  └───────┬──────────────┘
          │ X 协议
  ┌───────▼──────────────┐  **虚拟显示**:一个没有显示器的 X server,
  │  Xvfb :80            │  把像素画进内存。没有键鼠,没有 GPU
  └───────┬──────────────┘
          │ X 的 Damage / Composite 扩展(哪块变了?)
  ┌───────▼──────────────┐  **xpra**:盯着那个 X 显示,把变化的区域
  │  xpra start-desktop  │  切分、逐块编码,按其协议发送
  └───────┬──────────────┘
          │ ws,只绑回环
  ┌───────▼──────────────┐  **我们**:一个口、token、上行白名单
  │  sessiond            │
  └──────────────────────┘
```

三个常被混起来的名字:

| | 是什么 | 不是什么 |
| --- | --- | --- |
| **X / Xorg** | 一套显示协议,以及它的参考实现 | 不是"图形界面"本身 |
| **Xvfb** | **一个 X server**,把像素画进内存而不是显卡 | 不是 xpra 的一部分 |
| **xpra** | 盯着一个 X 显示做 damage 追踪 + 编码 + 传输 | **它不自己造显示** —— 得有人给它一个 |

**X 这一层的必要性**:xpra 采集的是**一个真实窗口**,而真实窗口需要 X server;
服务器上没有物理显示器,该 X server 只能是虚拟的。
screencast 不需要 X —— headless 浏览器不向任何显示输出。

### 6.1 虚拟显示钉死 Xvfb

xpra 的配置(`xvfb =` 那行)列了四种,**选哪个是发行版打包方定的**:

| | 要什么 | |
| --- | --- | --- |
| **`Xvfb`** ← 用这个 | `xvfb` 包,几 MB | 没有 GLX/DRI,分辨率靠 RandR 改 |
| `Xorg` + dummy 驱动 | **整个 Xorg** + 一份 xorg.conf | 云主机上通常没装 |
| `Xephyr` | 一个**已经在跑**的 X 显示 | 服务器上用不了 |
| `weston` + `Xwayland` | weston | 依赖更重 |

**显式传入 `--xvfb=Xvfb …`,不读取该配置。** Debian 系默认 `Xvfb`,
RHEL 系默认 Xorg+dummy,而云主机通常不安装 Xorg —— 同一条命令在两台机器上结果不同。

更关键的是它**绕过了探测**:`which("Xvfb")` 探测成功,而 xpra 实际使用 Xdummy。

> **探测对象必须与实际使用的对象一致。** 中间隔着第三方配置时,探测不构成保证。

分辨率:Xvfb 以较大尺寸(`8192x4096`)启动,再由 xpra 通过 RandR 调整到目标尺寸,
变更尺寸无需重启 X。

### 6.2 有头 + Xvfb 和 headless 差在哪

| | headless(screencast) | 有头 + Xvfb(xpra) |
| --- | --- | --- |
| **WebGL** | 有(自动退到 SwiftShader) | **默认没有** —— 要显式 `--use-gl=angle --use-angle=swiftshader`;`--disable-gpu` **救不回来**,有头下它关得更彻底 |
| GPU | 没有 | 没有 —— 两条都是软件渲染 |
| 原生对话框 | 不渲染 | **渲染,但点不动**(§9) |
| 浏览器自己的 bar | 没有 | 有 —— 所以要 `--kiosk`(§8) |
| 进程数 | 一个 | 三个:Xvfb + xpra + chrome |

### 6.3 要探哪些东西

| 探什么 | 少了会怎样 | |
| --- | --- | --- |
| `xpra` 可执行文件 | 什么都起不来 | ✓ |
| `Xvfb` 可执行文件 | vfb 起不来,xpra 自己退出 | ✓ |
| **跑 xpra 的那个 python 里有没有 PIL** | `start-desktop` 起不到一半就死。注意是**它的解释器**(读 shebang),不是我们的 —— webmuxd 常在 venv 里 | ✓ |
| 空闲的 X 显示号 | 撞号,起不来 | ✓ |
| **服务端有哪些图像编码器** | 我们只报 jpeg/png/webp/rgb/scroll。这个 xpra 编译时要是没带 webp 和 jpeg,就只剩 rgb —— **画面能出但带宽爆炸,而且不报错** | ✗ 还没探 |
| **xpra 的协议版本** | 我们写死 rencodeplus,更老的版本握手就失败,报错不指向版本 | ✗ 还没探 |

第五条属于「可运行但表现很差」一类,**比启动失败更难定位** —— 启动失败至少有报错。

## 7. 线切在哪

```
浏览器  ├── WS /channel/xpra       xpra 协议,只下行画面
        └── WS /channel/cdp      输入、光标、tab、ack —— 和另一条腿完全一样
```

### 7.1 输入不走 xpra

xpra 自带完整的输入协议(`pointer-position` / `button-action` / `key-action`),
直接使用最为省事。**但这会拆掉 [b](b-input.md) 中的安全收口** ——
边界将由「仅能表达 `Input` 域的四种意图」退化为「在代理层过滤 packet」,
而**过滤属于黑名单模型,遗漏一类即出现一个缺口**。

因此**客户端不向该连接发送任何输入**。协议本身要求上行六个包
(`hello` / `map-window` / `focus` / `damage-sequence` / `ping_echo` / `disconnect`),
缺少任一个将导致收不到帧或被断开。这一约束反而带来一个更强的性质:

> **上行是一个闭集,因此可以使用白名单。** 代理仅放行这六个,其余全部丢弃。
> 白名单与黑名单的区别在于:**新增的 packet 类型默认被拒绝**。

收口由此成为**两层**:客户端不实现发送逻辑,代理也不放行。

**代价**:xpra 自身的输入路径(加速、组合键、IME)一概不继承,
仍使用我们自己的翻译层。换取的是安全模型完全不变。

### 7.2 那条连接经过我们

**经反向代理,不直接暴露 xpra 的端口。** 对外只呈现一个地址;
且 token 需在此校验一次 —— xpra 自身的鉴权是进程级的,
不识别我们的只读/可写 token。

## 8. 画面里没有 bar

xpra 截的是真实的浏览器窗口,所以画面里本来会有 tab 条和地址栏。
量一下 `outerHeight - innerHeight`:

| 启动方式 | bar 高度 |
| --- | --- |
| 普通启动(带 `--no-sandbox` 警告条) | 143 |
| `--test-type --disable-infobars` | 88 |
| 再加 **`--kiosk`** | **0** |

**采用 `--kiosk`,不做裁剪。** 结果与裁剪一致(画面中不含浏览器 bar,tab 由我们绘制),
但省去一整套易错机制:无需发送高度变更通知、无需在客户端计算裁剪、
**无需为鼠标 `y` 补回偏移**(这一处最易出错且不易发现);
同时那 88 行像素不再被编码传输后丢弃(768 中的 88,约 **11.5% 带宽**)。

> `crop_top` 一旦存在,就必须处理其变化(视频全屏时归零、书签栏展开时增大);
> kiosk 下它恒为 0,**不存在变化这一情形**。

一处细节:kiosk 配合 `--window-size=1024,768`,在 1024×768 的显示上实际得到
**1023×767**,右侧与底部各有一列黑边。处理方式是**多请求两个像素**,
超出显示的部分被裁掉,画面铺满;代价是页面视口变为 1026×770,
右下各 2 像素落在可见区域之外 —— 优于一条持续可见的黑边。

## 9. 接缝之上的东西一律不动

更换像素来源不影响接缝之上的任何一层。最容易被误以为可以省掉的是
**浏览器自己的那些 UI**(对话框、下载、文件选择、权限、认证)——
有头之后画面里能看见它们了,直觉上似乎可以让人自己点。

**不能。** 实测:有头 Chrome 会把 JS 对话框绘制出来,但**那个按钮无法被点击** ——
它属于浏览器进程绘制的 UI,而 `Input.*` 作用于渲染进程;
加之 §7.1 规定输入不走 xpra,**我们允许的任何输入路径都无法关闭它**。

因此这一整套拦截保持不变,并且理由变得更强 ——
从「不拦就看不见」变成「不拦就点不动」。展开见 [g §5](g-native-ui.md#5-有头之后能看见但点不动)。

## 10. 默认走哪条

```bash
webmuxd install                                          # 有 root 就把 xpra 那套装上
webmuxd new --id work --port 7900                        # 默认 xpra
webmuxd new --id work --port 7900 --transport screencast # 零系统依赖那条
```

**默认选择效果更好的一条,而非更易安装的一条。** 安装成本由 `webmuxd install` 承担 ——
它本就是运行前必须执行的步骤(需要下载浏览器),一并处理 xpra / Xvfb / PIL。

**启动失败即报错,不静默回退。** 静默回退会使使用者误以为当前画质来自 xpra。
退路是显式指定 `--transport screencast`。

**`remote` 上不存在该选择**:该路径下只有一个 CDP 端点,无法访问对端的 X 显示,
screencast 是**唯一可能**的像素来源 —— 它在那条路上就是默认,而这不是降级。

## 11. 客户端

xpra 的协议要自己解,所以客户端第一次有了独立的模块:
[`static/xpra.js`](../../../webmuxd/view/static/xpra.js) +
[`rencode.js`](../../../webmuxd/view/static/rencode.js),去掉注释三百来行。

只需三百行的原因是 **`xpra-html5` 中不存在解码器** ——
图像交由 `createImageBitmap`,视频交由 WebCodecs,其自身只实现协议。
其余五千行为窗口管理、剪贴板、音频、虚拟键盘与 jQuery,**均不在需求范围内**。

一条重要的设计杠杆:**服务端只发送客户端在握手中声明过的编码**,
视频编码还需额外声明色彩空间。**未声明的编码永远不会被发送。**
因此客户端的复杂度由我们决定 —— 当前不声明视频编码,
也就不需要 WebCodecs,无需处理关键帧与解码器重置。

## 12. 这个抽象买到了什么

第二条来源的价值不限于 xpra 本身。

**它验证了「像素来源」这一接缝。** 只有一条实现时,「此处可替换」始终是一个断言;
出现第二条之后,该断言成为可检查的事实 —— 切换来源仅修改三处 `if`,
输入、权限、tab、原生 UI 均未改动。

**并且这条来源来自第三方。** xpra 是一个成熟的开源图像协议:
damage 追踪、区域切分、编码器选择、质量自适应,以及 `scroll` 这类位移编码,
均非本项目实现,也不应由本项目实现。

据此,后续可接入的方向是清晰的:

| 以后想要 | 从哪来 | 现在缺什么 |
| --- | --- | --- |
| **h264 / vp9** | xpra 那边编码器已经在了 | 客户端报一下色彩空间 + 一个 WebCodecs 分支,协议层不动 |
| 更好的静止画质 | xpra 的 `auto-refresh` 已经在跑 | 参数还没调 |
| **rrweb** | **第三条腿**,展开在 §13 | 它把"像素从哪来"回答成"不从远端来"。§5 那张表(输入、光标、tab、原生 UI、日志)确实一行不用改 —— **但背压与回执随通道走,那部分要重做**(§13.4③) |
| 别的传输(WebRTC 之类) | 再往后 | 同样只需回答"像素从哪来" |

**判据由此简化:一条新的像素来源只需回答一个问题 —— 像素从哪来。**
若它同时要求接管输入、权限或 tab,则它不是一条来源,而是另一套产品。

## 13. 第三条来源:rrweb —— 它不传像素

§12 那条判据("一条新的来源只需回答一个问题")到此为止还只经受过一次检验,
而那次的两条来源本来就同类。rrweb 是第一个真正来考这道题的,
它的答案与前两条都不同:**像素不从远端来,由观看端自己渲染出来。**

### 13.1 它是什么

rrweb 是一个页面内的记录器:注入之后监听 DOM,先发一张全量快照,
其后只发增量变更 —— 每条是 `{type, data, timestamp}` 的 JSON。
另一端的 replayer 用这些事件把 DOM 重建出来,按时间戳推进。
它的本职是 session replay(Browserless、Sentry 等均以它做录屏)。
**当作画面流使用,就是不落盘、实时推给观看端。**

三条来源并列:

| | `/channel/cdp` | `/channel/xpra` | `/channel/rrweb` |
| --- | --- | --- | --- |
| 线上传的是 | 整屏图片 | 区域图片 | **DOM 变更(JSON)** |
| 谁渲染 | 远端 Chromium | 远端 Chromium | **观看端的浏览器** |
| 帧 | 有 | 有 | **没有** —— 它是事件流,不是帧序列 |
| 保真 | 像素级 | 像素级 | **近似**(§13.4①) |
| 量级 | 3.71 Mbps(§4.1 实测) | 同左 | **文本 diff,低一到两个数量级** |
| 客户端 | 换 `<img>.src` | 三百行协议(§11) | **一个 replayer,数万行** |

前两条的差别在**粒度**(§4);第三条的差别在**传的是什么**。

### 13.2 它推翻了一句话

整套文档的出发点是:**终端传语义,浏览器传像素** ——
ttyd 送字符与控制序列,由 xterm.js 渲染;这一侧送图,渲染在远端已经完成
([a §6](a-architecture.md#6-客户端位置换了))。

rrweb 使浏览器这一侧也变成传语义:DOM 变更即这一侧的"字符流",replayer 即这一侧的 xterm.js。

这不是措辞问题,它改变了客户端的性质:

> 前两条来源上,**客户端不含渲染器** —— 解码由浏览器提供
> ([e §6.7](e-client.md#67-通道内部画面这条的共性))。
> rrweb 这条上客户端**重新成为一个渲染器**,且该渲染器既非我们实现、也非浏览器内置,
> 而是一个第三方库。**这条来源的客户端体量超过另外两条之和。**

因此它不是"再加一条腿"那样便宜,其价值必须足以抵这笔账。

### 13.3 它买到什么

**① 带宽。** 前两条的下限由图像编码决定;rrweb 传的是文本差异。
纯文字变化的页面上量级差一到两位。链路差的场景(移动网络、跨洲)是它明确优于另外两条的区间 ——
**也是三条里唯一在"画面"这件事本身上的优势;②③ 都不是画面。**

**② 回放。** 这是 rrweb 的本职能力。同一条流写在 `log.jsonl` 旁边,
即补上 [i §5](i-agent-surface.md#5-现在的三个缺口) 缺的那一项 ——
"点一条动作跳到那一刻"。像素那两条要做回放只能存视频,
而**存下来的视频不可搜索、不可 diff、不能取出某个元素**。

**③ 它是结构化的。** 一条 rrweb 流可以回答"这一刻那个按钮上的文字是什么",
一张 JPEG 回答不了。这与
[i §3.1](i-agent-surface.md#31-记控件的身份不记控件的内容) 同向 ——
那里记的是动作,这里记的是页面本身。

### 13.4 它要付什么

**① 保真度并非像素级,且缺口正落在自动化常见的页面上。**

| 情形 | rrweb 上的结果 |
| --- | --- |
| `<canvas>` 的 2D / WebGL 绘制 | **不出现** —— 元素在,绘制指令不在(有 canvas 插件,代价另算) |
| `<video>` / `<audio>` 的画面 | **不出现** —— 元素在,帧不在 |
| 跨域 iframe | 仅有外框,内部 DOM 不在(除非该 iframe 内也注入 rrweb) |
| 字体缺失 | 文字**重排**,而非显示为方块 |

前两条来源不存在此类问题:它们截取的是渲染结果,页面上是什么便是什么。

**② 坐标不再天然对齐 —— 这是最要紧的一条。**

输入始终走 `/channel/cdp`,送出的是页面坐标
([b §1](b-input.md#1-收口在哪))。前两条来源上这件事无需处理:
观看端看到的正是远端渲染出的那张图,点在哪里即是哪里。

rrweb 这条上,观看端看到的是**它自己重排出来的 DOM**。
一处字体不同、一条 `@media` 命中不同,布局即偏移 —— 而**输入不会随之偏移**,
它送出的仍是坐标。结果是:**看上去点在按钮上,实际点在按钮旁边,并且不报错。**

因此这条来源附带一条硬性要求:

> **观看端的 replayer 必须与远端渲染出同一套布局** —— 同一视口尺寸、同一套字体、
> 同一 `devicePixelRatio`。这些在前两条来源上无关紧要,在这条上是正确性前提。

字体一项 [d §2](d-install.md#2-每样东西从哪来) 已在处理,但它装的是**远端**的字体;
这条来源要求**观看端**同样具备 —— 而观看端是使用者的浏览器,不在我们的控制范围内。
该项目前没有答案(§14)。

**③ "丢旧帧保新帧"在这条上不成立。**

前两条来源上,背压策略是缓冲满了保留最新、丢弃最早
([e §5](e-client.md#5-背压客户端的义务是必须回执))——每一帧自足,丢掉旧的只损失一个中间状态。

rrweb 的事件是一条增量链。**丢掉其中一条,重放出的 DOM 自此与真实页面不一致,
且不会自行恢复** —— 界面看上去正常、内容却是错的,比画面卡住更难发现。
这条通道只有两种选择:不丢(以延迟换顺序),或丢弃之后**重发一张全量快照**。
两者均非现成,需要单独设计。

**④ 它改变页面环境,且幅度大于现状。**

[b §5](b-input.md#5-光标同步) 的光标探针已经在改变页面环境,这一点一直是承认的。
rrweb 是同类代价的放大:一个持续运行的 MutationObserver、一个大得多的脚本,
并且**其开销落在被自动化的那个页面上** —— 前两条的开销均在页面之外。
对注入敏感的场景,这是一条比探针显著得多的痕迹。

### 13.5 它在通道模型里的位置

按 [e §6.6](e-client.md#66-这个模型是用来想清楚的不是插件框架) 的三个问题:

**① 它是哪个上游的连接?** —— 页面内的那个记录器。数据经既有的 CDP binding 送出,
但**它可以独立于 CDP 失效**:页面导航、CSP 拦住注入、脚本抛错 —— 三种情形下
CDP 本身完好、输入照常送达,仅画面消失。故障边界不同,因此它自成一条通道。

> 这一条把 [e §6.1](e-client.md#61-通道--一个上游系统的连接) 的"上游"
> 由**一个独立进程**放宽为**一个能独立失效的数据生产者**。
> rrweb 是第一条上游位于页面内、而非另一个进程的通道。

**② 它能提供哪些能力?** —— 只有帧。光标、输入、尺寸、tab、原生 UI 一概不提供。
其中输入是那条不可协商的约束:**新增通道一律不得承载输入。**

**③ 在每种能力上排第几?** —— 帧这一能力上排末位:`xpra > cdp > rrweb`。

但这一行的实际作用有限。**仲裁的前提是几个提供者可以互换**,而 §13.4 说明它不能 ——
换过去画面会失真、坐标会错位。因此结论只有一条:

> **`/channel/rrweb` 只在被显式选中时启用,不参与自动仲裁。**

```bash
webmuxd new --id work --transport rrweb
```

它不会因另外两条不可用而被自动选上。这与 §10 的"启动失败即报错,不静默回退"
是同一条规矩:**使用者必须知道自己看的是像素,还是重排出来的 DOM。**

### 13.6 现状

**尚未实现。本节是设计,不是描述。** 落地需要四项:注入侧的记录器与出流通道、
sessiond 上的一条 `/channel/rrweb`、观看端引入 replayer,
以及 §13.4② 与 §13.4③ 两条的答案(布局对齐、背压策略)——
**这两条未解决之前,前三项没有意义。**
在此之前 `--transport` 仍只有 `xpra` 与 `screencast` 两个取值。
