# c · 像素从哪来:两条腿

**一句话**:CDP 截出来的 JPEG 和 xpra 发过来的区域图,**本来就是同一种东西** ——
压缩过的图片,带着位置和时间推过来。看清这一点之后,"像素从哪来"就是一个
干净的接缝:接缝之上(输入、光标、tab、原生 UI、日志、权限)只有一套,
接缝之下可以有两条腿,而且以后还能有第三条。

## 1. 第一条腿:让 Chromium 自己截

画面归我们产之后,第一个问题是"从哪拿像素"。CDP 里现成的答案是
`Page.startScreencast`:告诉 Chromium **"页面变了就给我一张图"**,
它就一张张推过来。

选它的理由当时很硬:

- **零依赖。** 浏览器自带的能力,headless 就能跑,不需要 X、不需要第三方进程
- **只有页面内容。** 它截的是渲染结果,不是桌面 —— 没有窗口边框、没有 tab 条,
  也就没有"裁掉浏览器 UI"这类问题
- **静止不产帧。** 页面不变就一张都不发

这套东西跑起来了,而且比预期的好。**但它的形状决定了它的上限。**

`screencastFrame` 给的是**一整屏的图**。Chromium 不告诉你"哪一块变了",
只告诉你"现在长这样"。于是:

| | 结果 |
| --- | --- |
| 滚动一行 | **整屏重发** |
| 编码 | 只能**事先挑一种**,全程不变 —— 文字和照片同一个质量 |
| 静止之后 | 就停在最后那张有损的图上,**不会变清晰** |
| 局部动画 | 一个角落在动,发的还是整屏 |

这不是参数没调好,是**这个接口只提供整屏**。要突破它,得有人去做
damage 追踪:知道哪一块变了,只发那一块,还要按那块的内容挑编码。

## 2. 缺的那半,自己造还是拿现成的

把上面那张表倒过来,就是一张待办清单:

```
知道哪一块变了            ← damage 追踪
把变化切成合适的块        ← 区域合并、边界处理
按每块的内容挑编码        ← 文字用无损,照片用有损,视频用帧间
滚动时只发位移            ← 位移编码
静止后补一张无损的        ← 质量分级刷新
链路慢了自动降质          ← 码率自适应
```

**这是一个做了二十多年的领域** —— X11 远程显示、VNC、RDP、SPICE,
每一条上面都有成熟实现。自己重做一遍,等于把这个项目变成一个远程显示项目,
而它本来该是"浏览器的 tmux"。

所以问题变成:**能不能找一个已经做完这张清单的东西,只把它当像素来源用?**

一个硬条件:**它只能管像素。** 这类协议通常自带完整的输入、剪贴板、
音频、文件传输 —— 那些一旦用上,[b](b-input.md) 那个安全收口就没了
(见 §7.1)。所以候选必须能被切开:**要它的下行,不要它的上行。**

## 3. xpra:符合这个条件的那个

xpra 的定位是"X11 的 tmux" —— 让远端的 X 程序活得比连接久,人可以断开再接回来。
它为此做的事,正好是 §2 那张清单:

```
盯着一个 X 显示 ──▶ 哪一块变了 ──▶ 切块 ──▶ 每块挑编码 ──▶ 按自己的协议发出去
```

它自带的编码器包括 `webp` / `jpeg` / `png` / `rgb`,以及一个 **`scroll`**
(只发位移向量,不发像素),视频那档还有 `h264` / `vp8` / `vp9`。
质量自适应和"静止后补一张无损的"也是现成的。

它有一个前提:**它盯的是一个真的 X 显示**,所以浏览器必须是有头的,
而服务器上没有显示器 —— 那一整套(Xvfb 是什么、为什么不是 Xorg)在 §6。

而它的上行是可以不用的:协议要求的上行只有六个握手/回执包,
**输入是可选的**(§7.1)。这一条决定了它能被当成"一条腿",而不是"另一个方案"。

## 4. 关键:两条路产出的是同一种东西

CDP 那条:

```
Page.screencastFrame
   data      base64 的一整屏 JPEG
   metadata  尺寸、滚动位置、时间戳
   sessionId 哪个 tab
```

xpra 那条:

```
draw
   wid            哪个窗口
   x, y, w, h     屏幕上的哪一块
   coding         这块用什么压的:webp / jpeg / png / rgb32 / scroll
   data           压完的字节
   packet_sequence 用来回执
```

**去掉名字看形状,两边是一样的:一块像素 + 它在哪 + 用什么压的 + 一个回执号。**

| | CDP screencast | xpra |
| --- | --- | --- |
| 一次给多大 | **整屏** | **一块 damage 区域** |
| 编码谁挑 | 我们挑一次,全程不变 | **每块各挑** |
| 有哪些编码 | jpeg / png / webp | webp / jpeg / png / rgb / **scroll** / h264… |
| 回执 | `screencastFrameAck` | `damage-sequence` |
| 静止时 | 不产帧 | 不产帧 |

差别全在**粒度**和**谁挑编码**上,不在"这是什么东西"上。

> 这就是为什么这两条能共用一个抽象,而当年的 VNC 不能 ——
> VNC 换掉的不只是像素,连输入、权限、runtime 契约一起换了。
> **只换像素,别的不动**,才谈得上"两条腿"。

### 4.1 它强在哪,以及它的劣势区

因为 xpra 强的地方**恰好是 screencast 结构上缺的**:

| | screencast | xpra |
| --- | --- | --- |
| 更新粒度 | 整屏一帧 | **按 damage 区域** |
| 选编码 | 固定一种 | **每块区域各选**:文字走无损 webp/rgb |
| 滚动 | 整屏重发 | **`scroll` 包只发位移向量** |
| 静止之后 | 就那样了 | **`auto-refresh`:先发有损的,静止后补一张无损的** |

最后一条是它文字更清楚的真正原因:**动的时候糊、停下来就变清晰**。
screencast 那条动不动都是同一个质量。

实测(同机同页,2026-08-18):

| 场景 | 结果 |
| --- | --- |
| 滚一页 Wikipedia,22 秒 | 3.71 Mbps。其中 **`scroll` 包用零字节完成了 57% 的重绘面积** |
| 全屏动画 1024×768,24 秒 | 2.86–9.34 Mbps ≈ 20 fps |

第二行是**它的劣势区**,要一起写出来:整屏都在动的时候,分区域重传退化成
整屏重传,还多背了分区的开销。所以 screencast 不是"旧的那条",
是**那种场景下更合适的那条**。

## 5. 接缝切在哪

> **两条腿之间唯一的差别,是像素从哪来。**
> 输入、光标、tab、原生 UI、日志、token、只读 —— **一模一样**。

这句话不是愿望,它在代码里是可检查的:换一条腿只改了
[`view/cast.py`](../../../webmuxd/view/cast.py) 里三个 `if`
(不发 `Page.startScreencast`、不改视口、忽略客户端 resize),
**没有第二处分叉**。

| | 谁负责 |
| --- | --- |
| 像素 | ← **只有这一行会变** |
| 输入翻译成 `Input.*` | 我们([b](b-input.md)) |
| 光标同步 | 我们 |
| tab 表 / `active` | 我们(`Target.activateTarget`) |
| 六类原生 UI | 我们(CDP 拦截 + 自己画卡片) |
| 日志、事件、token、只读 | 我们 |

## 6. 这一套东西是什么

```
  ┌─ 浏览器 ────────────┐  画页面。它不知道自己在被录,
  │  chrome --kiosk      │  只知道"我有一个 X 显示可以画"
  └───────┬──────────────┘
          │ X 协议
  ┌───────▼──────────────┐  **虚拟显示**:一个没有显示器的 X server,
  │  Xvfb :80            │  把像素画进内存。没有键鼠,没有 GPU
  └───────┬──────────────┘
          │ X 的 Damage / Composite 扩展(哪块变了?)
  ┌───────▼──────────────┐  **xpra**:盯着那个 X 显示,把变化的区域
  │  xpra start-desktop  │  切块、挑编码器压缩、按自己的协议发出去
  └───────┬──────────────┘
          │ ws,只绑回环
  ┌───────▼──────────────┐  **我们**:一个口、token、上行白名单
  │  sessiond            │
  └──────────────────────┘
```

三个常被混起来的名字:

| | 是什么 | 不是什么 |
| --- | --- | --- |
| **X / Xorg** | 一套显示协议,以及它的参考实现 | 不是"图形界面"本身 |
| **Xvfb** | **一个 X server**,把像素画进内存而不是显卡 | 不是 xpra 的一部分 |
| **xpra** | 盯着一个 X 显示做 damage 追踪 + 编码 + 传输 | **它不自己造显示** —— 得有人给它一个 |

**为什么需要 X 这一层?** 因为 xpra 截的是**一个真的窗口**。要有真窗口就要有
X server;服务器上没有显示器,所以那个 X server 得是虚拟的。
screencast 那条不需要 X —— headless 的浏览器不画到任何显示上。

### 6.1 虚拟显示钉死 Xvfb

xpra 的配置(`xvfb =` 那行)列了四种,**选哪个是发行版打包方定的**:

| | 要什么 | |
| --- | --- | --- |
| **`Xvfb`** ← 用这个 | `xvfb` 包,几 MB | 没有 GLX/DRI,分辨率靠 RandR 改 |
| `Xorg` + dummy 驱动 | **整个 Xorg** + 一份 xorg.conf | 云主机上通常没装 |
| `Xephyr` | 一个**已经在跑**的 X 显示 | 服务器上用不了 |
| `weston` + `Xwayland` | weston | 依赖更重 |

**我们显式传 `--xvfb=Xvfb …`,不读那份配置。** Debian 系默认 `Xvfb`,
RHEL 系默认 Xorg+dummy,而云主机上没有 Xorg —— 同一条命令两台机器一台能跑一台不能。

更要紧的是它**绕过探测**:`which("Xvfb")` 明明探到了,xpra 转头去用 Xdummy。

> **探的东西和用的东西必须是同一个。** 中间隔着一层别人的配置,
> 探测就只是一句安慰话。

分辨率:Xvfb 起一个很大的屏(`8192x4096`),再让 xpra 用 RandR 缩到目标尺寸,
改尺寸不用重起 X。

### 6.2 有头 + Xvfb 和 headless 差在哪

| | headless(screencast) | 有头 + Xvfb(xpra) |
| --- | --- | --- |
| **WebGL** | 有(自动退到 SwiftShader) | **默认没有** —— 要显式 `--use-gl=angle --use-angle=swiftshader`;`--disable-gpu` **救不回来**,有头下它关得更彻底 |
| GPU | 没有 | 没有 —— 两条都是软件渲染 |
| 原生对话框 | 不渲染 | **渲染,但点不动**(§9) |
| 浏览器自己的 bar | 没有 | 有 —— 所以要 `--kiosk`(§8) |
| 进程数 | 一个 | 三个:Xvfb + xpra + chrome |

### 6.3 要探哪些东西

| 探什么 | 少了会怎样 | |
| --- | --- | --- |
| `xpra` 可执行文件 | 什么都起不来 | ✓ |
| `Xvfb` 可执行文件 | vfb 起不来,xpra 自己退出 | ✓ |
| **跑 xpra 的那个 python 里有没有 PIL** | `start-desktop` 起不到一半就死。注意是**它的解释器**(读 shebang),不是我们的 —— webmuxd 常在 venv 里 | ✓ |
| 空闲的 X 显示号 | 撞号,起不来 | ✓ |
| **服务端有哪些图像编码器** | 我们只报 jpeg/png/webp/rgb/scroll。这个 xpra 编译时要是没带 webp 和 jpeg,就只剩 rgb —— **画面能出但带宽爆炸,而且不报错** | ✗ 还没探 |
| **xpra 的协议版本** | 我们写死 rencodeplus,更老的版本握手就失败,报错不指向版本 | ✗ 还没探 |

第五条是"能跑但很差"的那一类,**比"起不来"难查得多** —— 起不来至少会报错。

## 7. 线切在哪

```
浏览器  ├── WS /xpra       xpra 协议,只下行画面
        └── WS /api/view   输入、光标、tab、ack —— 和另一条腿完全一样
```

### 7.1 输入不走 xpra

xpra 自带完整的输入协议(`pointer-position` / `button-action` / `key-action`),
用它最省事。**但那会把 [b](b-input.md) 那个安全收口拆掉** ——
边界会从"只能表达 `Input` 域那四个意图"变成"在代理层过滤 packet",
而**过滤是黑名单思维,漏一类就破一个口**。

所以**客户端不往那条连接发任何输入**。协议本身要求上行六个包
(`hello` / `map-window` / `focus` / `damage-sequence` / `ping_echo` / `disconnect`),
少一个就收不到帧或者被断开 —— 但这反而更好:

> **上行是一个闭集,所以能走白名单。** 代理只放行这六个,其余一律丢弃。
> 白名单不是黑名单,**新出现的 packet 类型默认被拒**。

于是收口是**两层**的:客户端不写发送代码,代理也不放行。

**代价要说清楚**:xpra 自己那套输入路径(加速、组合键、IME)一样都不继承,
继续用我们自己的翻译。换来的是安全模型一个字不动。

### 7.2 那条连接经过我们

**反代,不直接暴露 xpra 的端口。** 人拿到的是一个地址;
而且 token 得在我们这儿校验一次 —— xpra 自己的鉴权是进程级的,
不认我们的只读/可写 token。

## 8. 画面里没有 bar

xpra 截的是真实的浏览器窗口,所以画面里本来会有 tab 条和地址栏。
量一下 `outerHeight - innerHeight`:

| 启动方式 | bar 高度 |
| --- | --- |
| 普通启动(带 `--no-sandbox` 警告条) | 143 |
| `--test-type --disable-infobars` | 88 |
| 再加 **`--kiosk`** | **0** |

**用 `--kiosk`,不裁。** 效果和裁一样(画面里没有浏览器的 bar,tab 由我们画),
但省掉一整套会出错的机制:不用发"高度变了"的通知、不用在客户端算裁剪、
**不用把鼠标 `y` 加回去**(那是最容易错、错了还很隐蔽的一处),
而且那 88 行像素不再被编码传输然后扔掉(768 里的 88 = **11.5% 带宽**)。

> `crop_top` 一旦存在,就得处理它变化的情况(视频全屏归 0、书签栏变大);
> kiosk 下它恒等于 0,**没有"变化"这回事**。

一处细账:kiosk + `--window-size=1024,768` 在 1024×768 的显示上实际拿到
**1023×767**,右下各露一列纯黑。做法是**多要两格**,超出显示的部分被裁掉,
画面铺满;代价是页面视口成了 1026×770,右下各 2 像素在可见区域外。
比一条一直看得见的黑边好。

## 9. 原生 UI 照旧归我们

换一条腿不改变这一条:六类原生 UI 的 CDP 拦截**原样留着,而且照旧由我们画卡片**。

| | 为什么还要拦 |
| --- | --- |
| **JS 对话框** | 它挡着页面。人能在画面里点是一回事,**程序撞上它还是会永久卡住** |
| **文件选择** | 那个 X 里根本没有文件管理器,原生框弹出来也没法用 |
| **下载** | 有气泡,但文件落在那台机器上 —— 还是要 API 取 |
| **权限 / 认证** | 和画面无关,本来就在 CDP 那一层 |

而且有一条比想象中更硬:**有头的 Chrome 会把 JS 对话框画出来,但那个按钮点不动。**

```
Page.enable → 页面 alert() → javascriptDialogOpening 抛了
                           → 同时 Chrome 把对话框画了出来,页面变灰
Input.dispatchMouseEvent(点 OK) → 没有 javascriptDialogClosed
```

因为那个按钮是**浏览器进程画的 UI**,而 `Input.*` 打的是渲染进程;
加上 §7.1 定了输入不走 xpra —— **我们允许的任何输入路径都关不掉它**,
只有 `Page.handleJavaScriptDialog` 能。两条推论:

1. 我们那张卡片是**必需品**,它的按钮是画面上唯一有效的按钮
2. 它必须是**盖住整个视口的不透明 scrim**,否则画面上会同时出现两个对话框,
   而其中一个是死的

## 10. 默认走哪条

```bash
webmuxd install                                          # 有 root 就把 xpra 那套装上
webmuxd new --id work --port 7900                        # 默认 xpra
webmuxd new --id work --port 7900 --transport screencast # 零系统依赖那条
```

**默认给好的那条,不是好装的那条。** "好装"那一半由 `webmuxd install` 兜 ——
它本来就是跑之前必须走一遍的(浏览器得下下来),顺手把 xpra / Xvfb / PIL 也装了。

**起不来就报错,不静默退回。** 静默退回等于让你以为自己在看 xpra 的画质。
退路是显式说一声 `--transport screencast`。

**`remote` 上不存在这个选择**:那儿我们只有一个 CDP 端点、碰不到对面的 X 显示,
screencast 是**唯一可能**的像素来源 —— 它在那条路上就是默认,而这不是降级。

## 11. 客户端

xpra 的协议要自己解,所以客户端第一次有了独立的模块:
[`static/xpra.js`](../../../webmuxd/view/static/xpra.js) +
[`rencode.js`](../../../webmuxd/view/static/rencode.js),去掉注释三百来行。

之所以只要三百行,是因为 **`xpra-html5` 里没有解码器** ——
图像交给 `createImageBitmap`,视频交给 WebCodecs,它自己只做协议。
那五千行是窗口管理、剪贴板、音频、虚拟键盘、jQuery,**我们一样都不要**。

一条设计杠杆值得记住:**服务端只会发客户端在握手里报过的编码**,
视频编码还要额外报色彩空间。**不报,就永远不会收到。**
所以"客户端要背多重"由我们说了算 —— 现在不报视频编码,
也就不需要 WebCodecs、不用管关键帧和解码器重置。

## 12. 这个抽象买到了什么

第二条腿的价值不只是 xpra 本身。

**它把"像素来源"这个接缝验证了一遍。** 在只有一条实现的时候,
"这里可以换"永远只是一句话;有了第二条之后,那句话变成了可检查的事实 ——
换一条腿只动三个 `if`,输入、权限、tab、原生 UI 一行没改。

**而且这条腿是别人的。** xpra 是一个成熟的开源图像协议,
damage 追踪、区域切块、编码器选择、质量自适应、`scroll` 那种位移编码 ——
这些都不是我们造的,也不该由我们造。

于是往前看,能插进来的东西是清楚的:

| 以后想要 | 从哪来 | 现在缺什么 |
| --- | --- | --- |
| **h264 / vp9** | xpra 那边编码器已经在了 | 客户端报一下色彩空间 + 一个 WebCodecs 分支,协议层不动 |
| 更好的静止画质 | xpra 的 `auto-refresh` 已经在跑 | 参数还没调 |
| 别的传输(WebRTC 之类) | 第三条腿 | 只要它能回答"像素从哪来",接缝之上一行不用改 |

**判据也因此变得简单:一条新的腿只需要回答一个问题 —— 像素从哪来。**
它要是还想顺便管输入、管权限、管 tab,那它就不是一条腿,是另一个产品。
