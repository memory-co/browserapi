# c1 · 画质:三个旋钮与自适应([c](c-view.md) 的参考篇)

**这一篇只讲 `/channel/cdp` 那条来源。** `/channel/xpra` 有它自己的一套
(按区域挑编码、静止后补无损、码率自适应),那些不是我们的参数 ——
见 [c §4.1](c-view.md#41-它强在哪以及它的劣势区)。

**一句话**:画面糊有**三个互不相干的来源**,调错旋钮不会有任何效果;
另有一套按链路状况自动降质的机制,它的输入是回执往返时间。

## 1. 三个旋钮

### 1.1 编码格式

`jpeg` / `png` / `webp` 三种(`avif`、`bmp` 会被拒绝)。

反直觉的一条:**扁平 UI 页面在最高质量下 PNG 比 JPEG 更小**(96 KB vs 136 KB)——
大片同色区域是无损压缩的主场。但图片密集的页面结论相反,PNG 会明显膨胀。

**默认 `jpeg`,不按内容自动切换。** 猜格式会让带宽变得不可预测,
而这属于优化,不属于先跑通。

### 1.2 quality

默认 80,上限 100,代价约 **1.56 倍**带宽。它同时是自适应升质的上限。

### 1.3 渲染倍率(真正的大头)

在高 DPI 观看端上,前两个旋钮怎么调都没用 —— **糊是放大造成的,不是压缩造成的**:

| 观看端 | 帧原始 | CSS 显示 | 物理像素 | 实际放大 |
| --- | --- | --- | --- | --- |
| 普通屏 dpr=1 | 1280×800 | 1280×800 | 1280×800 | 1.00x |
| Windows 150% 缩放 | 1280×800 | 1280×800 | 1920×1200 | **1.50x** |
| Retina dpr=2 | 1280×800 | 1280×800 | 2560×1600 | **2.00x** |

**但它不是「越大越清晰」的旋钮,只用来匹配观看端的 dpr。** 实测同一块文字区域的
梯度能量(越高越锐):

| | 梯度能量 | 每帧 |
| --- | --- | --- |
| 原生 1280 出图 | **17.11** | 55 KB |
| 出 2560 再缩到 1280 显示 | **13.94** | 144 KB |

在 dpr=1 的屏幕上,倍率 2 不只是没变好,而是**锐度低约 18%**,还多花 2.6 倍带宽。
原因是原生渲染时文字采用了针对该像素网格优化的抗锯齿,
放大渲染再降采样等于把这套抗锯齿重新平均了一遍。

因此观看端状态栏要显示**有效缩放**:`1.00x` 正确,`> 1` 该提高倍率,
`< 1` 是在浪费带宽。

> **算这个值不能用 CDP 的 metadata。** `screencastFrame` 报的
> `deviceWidth` / `deviceHeight` 是 **CSS 尺寸** —— 倍率为 2 时它报 1024×768,
> 而实际图像是 2048×1536,据此算出的「有效缩放」会差一倍,
> 而这一栏恰恰是用来判断该不该调倍率的。
> **帧的真实尺寸只有解码之后才知道**,所以客户端取解码后的宽度。

### 1.4 倍率必须三处同时对上

```
Emulation.setDeviceMetricsOverride  deviceScaleFactor=2
   页面 devicePixelRatio = 2            ✓
   Page.captureScreenshot = 2560×1600   ✓
   Page.screencastFrame   = 1280×800    ✗  ← 完全没生效

启动参数 --force-device-scale-factor=2
   Page.screencastFrame   = 2560×1426   ✓  ← 只有这条路有效
```

配套两件事漏一个即前功尽弃:

- `startScreencast` 的 `maxWidth` / `maxHeight` 要跟着乘倍率 ——
  否则浏览器会把放大的画面缩回 CSS 尺寸再编码,等于没做
- 观看端要把画面元素的尺寸**显式设为 CSS 像素** ——
  否则 2560px 宽的图按 2560 CSS px 渲染,画面直接大一倍

**由此得到一条对整体设计的约束**:`--force-device-scale-factor` 是**浏览器启动参数**,
不是 per-tab,更不是 per-观看者。所以:

- 倍率是 **session 级**的,起 session 时确定,变更需重启浏览器
- 多个观看者 dpr 不同时,**只能照顾其中一个**;默认 1,由起 session 的人决定

**鼠标坐标不受影响** —— CDP 的 `Input.*` 接收的是 CSS 像素。
因此代码中「CSS 像素的视口尺寸」与「物理像素的帧尺寸」必须是**两套分开的量**,
混用会使倍率大于 1 时点击位置整体偏移。

## 2. 分辨率是 per-tab 的

与倍率相反,视口尺寸走 `Emulation.setDeviceMetricsOverride`,**每个 target 各自一份**,
修改它只需一条 CDP 命令,不重启任何东西。默认 1024×768。

> **待验**:多个 target 各自设置不同尺寸时是否互不干扰、帧尺寸是否跟随。
> 若不独立,改尺寸就必须退回 session 级。**目前没有测试覆盖这一项。**

`/channel/xpra` 那条不适用:那里的画面尺寸由虚拟显示决定,
设置视口反而会让页面渲染成另一个尺寸而窗口不变。

## 3. 按链路状况自适应

发帧时记录时间戳,收到回执算往返时间,滑动窗口取均值:

| | 值 |
| --- | --- |
| 往返 > **725 ms** | 降质 |
| 往返 < **600 ms** | 升质 |
| 两个方向各节流 | **8 秒** |
| 降质顺序 | 先降 quality(每次 **−20**,下限 **25**),到底后改为抽帧(上限每 **8** 帧取一) |
| 升质上限 | 启动时给定的 `quality`,不会自行超过 |

**先降画质再抽帧,顺序不能反。** 糊一点的连续画面比清晰的卡顿画面可用得多 ——
拖拽和滚动时,连续性就是可操作性。

**下限是 25。** 更低是马赛克,而从 20 直接到 5 是一个断崖。
降质的意义是「糊一点但仍可操作」,不是「糊到看不清」。到底之后改为抽帧,
那才是链路确实撑不住时该退的方向。

**降质要留下痕迹。** 状态栏只有当前值,而「什么时候降的、降之前往返多少」
是事后才会问的问题,因此同时写入日志:

```jsonc
{"kind":"session","event":"quality_changed","quality":60,"every_nth":1,
 "rtt_ms":812,"direction":"down"}
```

### 3.1 这个往返时间不是 ping

计时点在发送之前,因此它**包含帧的传输时间** —— 60 KB 在窄带上就是几百毫秒。
这是有意的:需要的是拥塞信号,而不是网络延迟。

但它有一个反馈回路必须知道:

> **画质调越高 → 帧越大 → 测得的往返越长 → 触发降质。**
> 所以在窄带上把 quality 调到 95,它可能自己把自己降回去。

### 3.2 两处容易踩空

- **PNG 是无损的,`quality` 对它完全无效。** 该模式下自适应只剩抽帧一个手段,
  代码中需分开处理。
- **本机往返只有几毫秒**,画质会一直顶在上限。

> **验证不需要人为加延迟**:把两个阈值压到本机往返之下即可,
> **死区必须保留**(升质阈值 < 降质阈值),这样能在本机跑出真实的降级路径。
>
> 曾经把降质阈值设为 0 试验,**死区被破坏** —— 两个条件同时成立,
> 于是升降来回震荡。这反过来说明了死区的作用:没有它,
> 一条在阈值附近抖动的链路会让画质持续变化,**比一直糊更难受**。
