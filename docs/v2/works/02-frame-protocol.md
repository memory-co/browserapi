# 02 · 帧怎么发

**一句话**:一条 WebSocket,下行是「28 字节二进制头 + JPEG 裸字节」,
上行是 ack 和归一化输入事件。ack 既是背压也是 RTT 探针,RTT 决定画质。

## 0. 这一篇的地位:照抄,不重新设计

**图片流这一层原样按 demo 来**(`~/browserbox/demo/`,约 700 行,17 项 e2e 已经跑通)。
头部布局、ack 额度、缓冲策略、RTT 阈值、降质顺序 —— **参数照抄,不调优**。

所以本篇写的不是"我们打算怎么设计",而是**"抄的时候哪几处不能想当然改"**:
下面每一节都是一个已经有人踩过的坑,以及为什么那个答案是对的。
凡是抄 BrowserBox 的阈值都标了出处,凡是 demo 和它有分歧的都写明为什么。

**优化留到以后**,清单和触发条件在 [§6](#6-以后可以再优化的) —— 先跑起来,
有了真实负载的数字再动。现在就调参等于凭想象优化。

## 1. 为什么是二进制头,不是 JSON

CDP 给的 `Page.screencastFrame` 是 base64。如果原样塞进 JSON 转发:

- 体积 **+33%**,而滚动时本来就已经 10 Mbps 了
- 每帧多一次编解码,两端都是
- 客户端拿到还要再 `atob` 一次才能进 `<img>`

所以服务端 base64 解一次,拼一个定长头直接发裸字节。客户端一个 `DataView`
读完头,剩下的整段 `Blob` 丢给 `<img>` 的 `createObjectURL`。

布局和 BrowserBox 一致(demo 的 `buildHeader`):

| 偏移 | 内容 |
| --- | --- |
| 0–3 | castSessionId —— 每次 `startScreencast` 递增,用来丢弃切 tab 前的残帧 |
| 4–7 | frameId —— 单调递增,客户端可据此丢乱序帧 |
| 8–23 | targetId —— 32 个 hex 字符切成 4 个 uint32 LE |
| 24–27 | 保留 |

**targetId 进头部是有用的,不是装饰**:客户端画的 tab 条知道自己现在该显示哪个 tab,
帧头对不上就直接丢 —— 切 tab 的瞬间管道里还有旧 tab 的帧([05 §3](05-active-tab.md#3-切-tab-是把-screencast-搬过去))。

## 2. ack 背压:两个独立的环

这是最容易写错的一处。**有两个 ack,它们必须解耦:**

```
Chromium ──frame──> webmuxd ──frame──> 客户端
         <──Page.screencastFrameAck──┘        ← 环 A:收到就立刻回,不回 Chromium 会停流
                     <──── ack(JSON) ────┘    ← 环 B:客户端回的,只用来对客户端做背压
```

**环 A 必须无条件立刻回。** 它是 CDP 的流控,不回 Chromium 就不再产帧。
把它和客户端的 ack 串起来(等客户端回了再回 Chromium)会让一个慢客户端**把整条流拖死**,
而且拖死的是所有观看者。

**环 B 是对客户端的背压**,demo 的参数:额度 `ACK_COUNT = 2` 帧,没额度时新帧进一个
长度 3 的小缓冲。

> **缓冲满了留最新丢最旧。** 直播画面里过期帧毫无价值,留旧的只会让延迟越积越大。
>
> 这里和 BrowserBox 有个**有意的分歧**:它的 `ack.buffer` 用 `unshift` 插入、`pop` 取出,
> 实际取的是缓冲里最旧的那帧。demo 直接取最新的、其余丢弃。webmuxd 跟 demo。

demo 的自测里有一项专门验证:一个故意不回 ack 的客户端**只能收到 2 帧就被卡住**,
而同时连着的正常客户端不受影响。这一项必须在 webmuxd 这边照样测 ——
它是"一个卡住的观看者不能影响别人"的唯一证据。

### 多观看者

v2 允许多人同时看同一个 session(v1 里那是 VNC 的多 client)。每条连接**各自一份额度和缓冲**,
帧是同一份 `Buffer` 的引用,不复制:

```
                    ┌─> 观看者甲(额度 2,缓冲 [f9])
一帧 ──fan out──────┼─> 观看者乙(卡住了,缓冲 [f9],f7/f8 已丢)
                    └─> 观看者丙(额度 2,缓冲 [])
```

慢的那个只是自己掉帧,不拖累别人,也不拖累环 A。

## 3. RTT 自适应画质

发帧时记时间戳,收到环 B 的 ack 算 RTT,滑动窗口取均值。阈值直接取自 BrowserBox 的
`src/zombie-lord/screenShots.js`:

| | 值 |
| --- | --- |
| RTT > **725 ms** | 降质 |
| RTT < **600 ms** | 升质 |
| 两个方向各 throttle | **8 秒** |
| 降质顺序 | 先砍 quality(每次 **−20**,下限 **25**),砍到底再抽帧(`everyNthFrame` 上限 **8**) |
| 升质上限 | 启动时给的 `quality`,不会自己超过 |

**先砍画质再抽帧**,顺序不能反:糊一点的连续画面比清晰的卡顿画面可用得多 ——
人在页面上拖拽、滚动时,连续性就是可操作性。

> **下限是 25,不是 BrowserBox 那个 5。** 抄它的阈值时把下限也抄了,后来发现不对:
> **q5 是马赛克,根本没法用**,而且 `20 → 5` 是个断崖。降质的意义是"糊一点但还能
> 操作",不是"糊到看不清"。25 也不是拍的 —— BrowserBox 自己在 Tor 模式下就把下限
> 压到 25([01 §4](01-frame-source.md)),那是它认为的"还能用"的底。
> 到底了就改抽帧,那才是链路真撑不住时该退的方向。`--min-quality` 可以改。

**降质要留下痕迹。** 状态栏只有当前值,而"什么时候降的、降之前 RTT 多少"是事后
才会问的问题 —— 所以它同时进 scrollback,用已有的 `session` 类目
(那儿本来就装 `session_started` / `chrome_restarted` 这种系统自己做的事):

```jsonc
{"kind":"session","event":"quality_changed","quality":60,"every_nth":1,
 "rtt_ms":812,"direction":"down"}
```

**这个数量的 RTT 不是 ping。** 计时点在 `send` 之前,所以它包含**帧的传输时间** ——
60 KB 在窄带上就是几百毫秒。这是有意的:要的是拥塞信号,不是网络延迟。
但它有个反馈回路要知道:**画质调越高 → 帧越大 → 测出来的 RTT 越大 → 触发降质**,
所以 `--quality 95` 在窄带上可能自己把自己降回去。

两个坑:

- **png 是无损的,`quality` 对它完全无效**。png 模式下自适应只剩抽帧一个手段,代码里要分开处理。
- 本机跑 RTT 只有几毫秒,画质会一直顶在上限。

> **不用加延迟也能验 —— 把阈值搬下来就行。**
>
> 原来这儿写着"想验证必须人为加延迟,否则它在测试里等于没跑过"。
> 换个做法:`SLOW_MS` / `FAST_MS` 压到本机 RTT 之下,**死区照留**(`FAST < SLOW`),
> 就能在本机跑出真实的降级路径。`pixels_on_a_wire` 里那条实测到
> `80 → 60 → 40 → 20`,单调下降。
>
> 第一次试的时候我把 `SLOW_MS` 设成 0,**死区被毁了** —— 两个条件同时成立,
> 于是 down / up 来回震荡。那反过来证明了死区是干什么的:
> 没有它,一个在阈值附近抖动的链路会让画质一直变,**比一直糊更难受**。

## 4. 清晰度:三个独立的旋钮

画面糊有三个互不相干的来源,**调错旋钮不会有任何效果**。这一节全部是 demo 实测。

### ① 编码格式

`Page.startScreencast` 的 `format` 实测支持 `jpeg` / `png` / `webp`(CDP 文档只列了前两种),
`avif` 和 `bmp` 会被拒绝(`Invalid image format`)。

反直觉的一条:**扁平 UI 页面在 q100 下 PNG 比 JPEG 还小**(96 KB vs 136 KB)——
大片同色区域是无损压缩的主场,而 JPEG 到 q100 已经极度浪费。但图片密集的页面结论相反,
PNG 会明显膨胀。

**照抄 demo:默认 `jpeg`,不自动切换。** 按页面内容猜格式会让带宽变得不可预测,
而且那属于优化([§6](#6-以后可以再优化的)),不属于先跑起来。

### ② quality

默认 80,可以到 100,代价约 **1.56x** 带宽。它同时是自适应升质的上限。

### ③ 渲染倍率(真正的大头)

高 DPI 观看端上,前两个旋钮怎么调都没用,因为糊是**放大**造成的,不是压缩造成的:

| 观看端 | 帧原始 | CSS 显示 | 物理像素 | 实际放大 |
| --- | --- | --- | --- | --- |
| 普通屏 dpr=1 | 1280×800 | 1280×800 | 1280×800 | 1.00x |
| Windows 150% 缩放 | 1280×800 | 1280×800 | 1920×1200 | **1.50x** |
| Retina dpr=2 | 1280×800 | 1280×800 | 2560×1600 | **2.00x** |

**但 dsf 不是"越大越清晰"的旋钮,它只用来匹配观看端的 dpr。** demo 量过同一块文字区域的
梯度能量(越高越锐):

| | 梯度能量 | 每帧 |
| --- | --- | --- |
| dsf=1 原生 1280 出图 | **17.11** | 55 KB |
| dsf=2 出 2560 再缩到 1280 显示 | **13.94** | 144 KB |

比值 0.815 —— 在 dpr=1 的屏幕上,dsf=2 不只是没变好,是**测量上锐度低了约 18%**,
还多花 2.6 倍带宽。原因是原生 1280 渲染时文字用的是针对该像素网格优化过的抗锯齿,
2560 渲染再降采样等于把这套抗锯齿重新平均了一遍。

所以客户端状态栏里要显示**有效缩放**:`1.00x` 正确,`> 1` 该升 dsf,`< 1` 是在浪费带宽。

> **算这个数时不能信 CDP 的 metadata。** `screencastFrame` 的
> `deviceWidth` / `deviceHeight` 报的是 **CSS 尺寸** —— dsf=2 时它说 1024×768,
> 而图其实是 2048×1536,拿它算出来的"有效缩放"会差一倍,
> 而那一栏正是用来判断该不该调 dsf 的。
> **帧的真实尺寸只有解码之后才知道**,所以客户端用 `img.naturalWidth`。
> 这条是加 `--dsf` 时撞出来的。

### dsf 的大坑,以及它对 v2 的约束

demo 实测:

```
Emulation.setDeviceMetricsOverride  deviceScaleFactor=2
   页面 devicePixelRatio = 2            ✓
   Page.captureScreenshot = 2560x1600   ✓
   Page.screencastFrame   = 1280x800    ✗  ← 完全没生效

启动参数 --force-device-scale-factor=2
   Page.screencastFrame   = 2560x1426   ✓  ← 只有这条路管用
```

配套两件事漏一个就前功尽弃:`startScreencast` 的 `maxWidth`/`maxHeight` 要跟着乘 dsf
(否则 Chromium 把 2x 画面缩回 CSS 尺寸再编码,等于白做);客户端要把 `<img>`
的尺寸**显式定成 CSS 像素**(否则 2560px 宽的图按 2560 CSS px 渲染,画面直接大一倍)。

**这条对 v2 的约束要写在明处**:`--force-device-scale-factor` 是**浏览器启动参数**,
不是 per-tab、更不是 per-观看者。所以:

- dsf 是 **session 级**的,起 session 时定,改它要重启浏览器
- 多个观看者 dpr 不同时,**只能照顾一个**。默认 1,由起 session 的人决定

**鼠标坐标不受影响**:CDP 的 `Input.*` 收的是 CSS 像素。所以代码里
「CSS 像素的视口尺寸」和「物理像素的帧尺寸」必须是**两套分开的量**,
混用会让 dsf>1 时点击位置整体偏移。

## 5. 分辨率是 per-tab 的

和 dsf 相反,视口尺寸走 `Emulation.setDeviceMetricsOverride`,**每个 target 各自一份**,
改它是一条 CDP 命令,不用重启任何东西 —— v1 那条"容器按默认分辨率起 → 量 `crop_top` →
`xrandr` 调 X 分辨率"的两段式([v1/works/04 §2](../../v1/works/04-chrome-ui-externalization.md#2-怎么把-chromium-的-ui-弄没))
整个消失。

默认 1024×768,和 v1 保持一致(CHANGELOG 0.3.0)。

> **待验**:多个 target 各自 override 不同尺寸时是否互不干扰、帧尺寸是否跟着 override 走。
> 本轮探针写到这一项时收工了,落地前必须补测 —— 如果不独立,`resize` 就得是 session 级的。

## 6. 以后可以再优化的

**现在一条都不做。** 列出来是为了两件事:一是标明它们是**已知的选项,不是遗漏**;
二是每条写清**什么时候回来动它** —— 没有触发条件的优化就是凭想象优化。

| 优化 | 大概能换到什么 | 什么时候回来动它 |
| --- | --- | --- |
| **帧去重** —— 和上一帧完全相同就不发 | 静止场景已经接近 0(实测静置 3 秒 1 帧),**收益可能很小** | 量到重复帧占比超过一成 |
| **WebP 替 JPEG** | 同画质下更小,`format` 已经支持,一行参数 | 真实负载的码率数字出来之后,同页面 A/B 一次 |
| **按内容选格式**(扁平 UI 走 png) | demo 实测扁平页 q100 时 PNG 比 JPEG 小 30%(§4①) | 有了真实页面的分布,而且能判得准的时候 |
| **区域更新** —— 只发变化的矩形 | 打字/悬停这类小面积重绘省很多 | 有人抱怨"只是打个字也在跑流量"。注意这正是 VNC 的路子,而它在全屏运动时是负收益([01 §4.1](01-frame-source.md#41-但更费带宽--更不流畅)) |
| **多观看者共享编码** | 现在是同一份 `Buffer` 扇出,已经不重复编码 | 除非引入 per-观看者的分辨率/画质,否则**不需要** |
| **H.264 / VP8 走 WebRTC** | 带宽降一个量级 | 带宽成为实际投诉。但实测流畅度已经赢了 VNC,**它换的是带宽不是体验**([works/README](README.md#明确不做))。BrowserBox 的双通道赛跑是怎么回事、为什么我们不抄,见 [09 §4](09-wire-format.md#4-browserbox-的上行) |

排在最前面的两条(帧去重、WebP)成本最低、风险最小,真要动就从它们开始 ——
而且都要**先量再动**,不要凭"应该会更好"。
