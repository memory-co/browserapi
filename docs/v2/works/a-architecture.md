# a · 架构基础定位

**一句话**:webmuxd 是浏览器的 tmux + ttyd。tmux 那一半照搬,ttyd 那一半重写 ——
因为**终端传的是语义,浏览器传的是像素**。这一篇从前到后走一遍整条链路,
每一跳是什么、为什么是这样;具体取舍在后面各篇。

## 1. 定位

| tmux 的概念 | webmuxd | |
| --- | --- | --- |
| session 活得比连接久 | 一个浏览器 + 一个 sessiond | 照搬 |
| window / pane | tab | 照搬 |
| `new -A -s` 幂等 | `session(id=…)` 幂等 | 照搬 |
| attach / detach | 打开或关掉那个网页 | 照搬 |
| scrollback | 一个 `log.jsonl` | 照搬 |
| **ttyd:把终端搬进浏览器** | **把浏览器搬进浏览器** | **重写** |

前五行是这个项目最省心的部分:**"门面短命,屋子长命"这个模型在浏览器上原样成立**。
所有的设计问题都在最后一行 —— 而下面这条链路就是最后一行的展开。

## 2. 整条链路

```
   ┌─ 那台机器 ────────────────────────────┐        ┌─ 人这边 ──┐

     Chromium ◀──── CDP ────▶ sessiond ◀──── WebSocket ────▶ 客户端 ──▶ 屏幕
        ▲            RPC         │              一条            <img>
        │                        │
     真正的浏览器           唯一有状态的那个                     程序 ──▶ HTTP /api
     活得比连接久           帧从这儿出、输入从这儿进
```

对着 ttyd 看,一跳对一跳:

| | 终端 | 浏览器 |
| --- | --- | --- |
| 被驱动的东西 | `bash` | Chromium |
| 服务怎么接它 | **pty,一条字节流** | **CDP,一个 RPC 接口** |
| 服务 ↔ 客户端 | 一条 WS | 一条 WS |
| 客户端是什么 | xterm.js(几万行) | 一个 `<img>` + 一层薄协议 |

下面按这个顺序走一遍。

## 3. Chromium ↔ sessiond:CDP 是 RPC,不是流

**这是整条链路里最容易被想错的一跳。**

ttyd 那边,`bash` 一启动,pty 就是一条现成的字节流:输出自己流过来,
输入写进去就行。**接上就有。**

CDP 不是。它是一个 JSON-RPC 接口(也跑在 WebSocket 上,但那是巧合):

```
sessiond ──▶ {"method":"Page.startScreencast","params":{…}}
Chromium ──▶ {"method":"Page.screencastFrame","params":{"data":"<base64>",…}}
sessiond ──▶ {"method":"Page.screencastFrameAck","params":{…}}
```

**画面和输入都是我们主动要来的,不是流过来的。** 三条推论:

- **要开口要,才有画面。** 不发 `startScreencast` 就一帧都没有;
  这也意味着**没人在看的时候可以不要**。
- **要回执,流才继续。** 不回 ack,Chromium 就停止产帧 —— 流控在协议里。
- **输入是一条条命令。** 一次点击是 `Input.dispatchMouseEvent`,
  不是"把字节写进去"。**所以输入必然经过我们的手** —— 这一条后面会反复用到。

## 4. sessiond:唯一有状态的那个

链路两端都可以随时消失:网页关掉,浏览器照常跑;浏览器崩了,可以再起。
**中间这个进程是唯一必须记着事情的地方**:

- 谁在看(以及是只读还是可写)
- 现在截的是哪个 tab
- 该发多大、多清晰的帧
- 那本 scrollback

它同时是两边的**翻译层**:把 CDP 的帧翻成我们的线上格式,
把客户端的输入翻成 CDP 命令。往后所有的设计问题基本都落在这个进程里。

## 5. sessiond ↔ 客户端:一条 WebSocket,两种帧

**和 ttyd 一样是一条连接**,这一点常被误解成"浏览器方案更复杂所以要多开几条"。

ttyd 在载荷的**第一个字节**里自造了一个 opcode 来区分控制和数据:

```
'0' + 终端输出        '1' + 标题        上行:'0' 键盘、'1' 改尺寸
```

我们用的是 **WebSocket 本来就有的那一位** —— 协议自己就分 text(0x1)和
binary(0x2):

```
binary   28 字节定长头 + 图片裸字节        ← 载荷
text     {"type":"cast",…} / {"type":"cursor",…}   ← 控制
上行 text {"type":"mouse",…} / {"type":"ack","frameId":N}
```

差别不大,但方向是对的:**分层由传输层保证,不由约定保证。**

> 另有两条 WS 不在这条主链路上:`/api/events` 是给程序听的事件流,
> 以及换像素来源时才存在的那条(后面专门一篇)。它们都不改变这个骨架。

## 6. 客户端:位置换了

链路最右端是最反直觉的一处。

| | ttyd | webmuxd |
| --- | --- | --- |
| 客户端在做什么 | **全是渲染** —— 解 VT 状态机、维护屏幕缓冲、画字形 | **全是协议** —— 拆头、丢残帧、回 ack、心跳、输入归一化、IME |
| 有多大 | 几万行 | 几百行 |
| 渲染谁做 | 客户端自己 | **浏览器自带**(`<img>` 解 JPEG) |
| 有没有现成的 | **`npm i xterm`** | **没有** |

终端那边的难点是渲染,而渲染有一个几十年的标准(VT100),
所以能长出 xterm.js 这样人人可用的库。

我们这边渲染是白拿的 —— 浏览器天生会解图片。**但协议是自造的,
没有第三方实现可用。**

> **ttyd 省下了协议,我们省下了渲染。** 两边的客户端都不大,
> 但省下的是不同的那一半。

我们自带一个观看页,和 ttyd 自带一个前端是同一个道理。**它不是"界面"** ——
画面 + 一条 tab 条 + 一个地址栏,没有会话列表、没有登录页、没有设置面板。
它存在的唯一理由是**跑起来之后打开那个地址,链路通没通一眼就看出来**。
上层要自己画就自己画,用的是同一组接口,没有私货。

## 7. 这条链路为什么是这个形状:载荷是像素,不是语义

前面每一跳的形状,追到底都是同一个原因。

`\x1b[10;5H` 这七个字节的意思是"把光标挪到第 10 行第 5 列"——
它不是画面,是**让客户端去画**的指令。终端的输出流从头到尾都是这样的东西,
而且是几十年没变的标准。

浏览器的画面是像素。**没有一条流能同时表达"这个按钮是蓝色的"和"这里可以点"**——
前者在像素里,后者在 DOM 里。

| | 终端 | 浏览器 |
| --- | --- | --- |
| **谁在渲染** | 客户端 | **远端**,客户端只贴图 |
| **一帧多大** | 几十字节 | 几十 KB |
| 静止时的流量 | 0 | 0(画面不变就不产帧) |
| **光标** | 在流里 | 既不在像素里也不在协议里,得单独同步 |
| **语义在哪** | **就是流本身** | 在 DOM 里,要另开一条路去取 |

最后一行是这个项目一半工作量的来源:**终端不需要"观测"这个概念**,
因为它的流本身就是语义;要让程序知道浏览器页面上有什么,必须另外去 DOM 里取。

## 8. 往下写什么

```
载荷是像素,不是语义
   ├─ 画面必须由我们产,而且产出来就是最终形态
   ├─ 客户端不渲染,只贴图
   ├─ 输入必须由我们翻译回去,而这带来了一个安全收口
   ├─ 语义要另开一条路去 DOM 里取
   └─ 终端白给的那些东西要一件件重建
```
