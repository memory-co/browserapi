# a · 架构基础定位

**一句话**:webmuxd 是浏览器的 tmux + ttyd。tmux 那一半照搬,ttyd 那一半重写 ——
因为**终端传的是语义,浏览器传的是像素**。本篇按链路顺序说明每一跳的职责与形状,具体取舍见后续各篇。

## 1. 定位

| tmux 的概念 | webmuxd | |
| --- | --- | --- |
| session 活得比连接久 | 一个浏览器 + 一个 sessiond | 照搬 |
| window / pane | tab | 照搬 |
| `new -A -s` 幂等 | `session(id=…)` 幂等 | 照搬 |
| attach / detach | 打开或关掉那个网页 | 照搬 |
| scrollback | 一个 `log.jsonl` | 照搬 |
| **ttyd:把终端搬进浏览器** | **把浏览器搬进浏览器** | **重写** |

前五行可以直接沿用:**「门面短命、屋子长命」这个模型在浏览器上原样成立**。
设计问题集中在最后一行,下面这条链路即是它的展开。

## 2. 整条链路

```
   ┌─ 服务端 ──────────────────────────────┐        ┌─ 观看端 ──┐

     Chromium ◀──── CDP ────▶ sessiond ◀─── WS /channel/… ───▶ 客户端 ──▶ 屏幕
        ▲            RPC         │            一条或多条          <img>
        │                        │
     真实浏览器             唯一持有状态的进程                   程序 ──▶ HTTP /api

     ── 帧:Chromium → sessiond → 客户端
     ── 输入:客户端 → sessiond → **翻译成 CDP Input.\*** → Chromium
        观看者永远接触不到左边那条 CDP 连接
     生命周期长于连接       帧由此输出、输入由此进入
```

与 ttyd 逐跳对照:

| | 终端 | 浏览器 |
| --- | --- | --- |
| 被驱动的东西 | `bash` | Chromium |
| 服务怎么接它 | **pty,一条字节流** | **CDP,一个 RPC 接口** |
| 服务 ↔ 客户端 | 一条 WS | 一条 WS |
| 客户端是什么 | xterm.js(几万行) | 一个 `<img>` + 一层薄协议 |

以下按此顺序展开。

## 3. Chromium ↔ sessiond:CDP 是 RPC,不是流

**这一跳的性质最容易被误判。**

ttyd 那侧,`bash` 启动后 pty 即是一条现成的字节流:输出持续流出,输入直接写入。
**连上即可用。**

CDP 不是。它是一个 JSON-RPC 接口(也跑在 WebSocket 上,但那是巧合):

```
sessiond ──▶ {"method":"Page.startScreencast","params":{…}}
Chromium ──▶ {"method":"Page.screencastFrame","params":{"data":"<base64>",…}}
sessiond ──▶ {"method":"Page.screencastFrameAck","params":{…}}
```

**画面和输入都是我们主动要来的,不是流过来的。** 三条推论:

- **必须显式请求才有画面。** 不发 `startScreencast` 则一帧都不会产生;
  反过来,**无人观看时可以不请求**。
- **必须回执,流才继续。** 不回 ack,Chromium 停止产帧 —— 流控在协议内。
- **输入是逐条命令。** 一次点击对应一次 `Input.dispatchMouseEvent`,
  而非向字节流写入。**因此输入必然经过 sessiond** —— 这一性质后续反复被用到。

## 4. sessiond:唯一有状态的那个

链路两端都可能随时消失:观看页关闭后浏览器照常运行,浏览器崩溃后可以重启。
**中间这个进程是唯一必须持有状态的位置**:

- 谁在看(以及是只读还是可写)
- 现在截的是哪个 tab
- 该发多大、多清晰的帧
- 那本 scrollback

它同时是两侧的**翻译层**:把 CDP 的帧转成线上格式,把客户端的输入转成 CDP 命令。
后续的设计问题基本都落在这个进程内。

## 5. sessiond ↔ 客户端:一条 WebSocket,两种帧

**与 ttyd 同样只有一条连接。** 这一点常被误解为「浏览器方案更复杂,需要多条连接」。

ttyd 在载荷的**第一个字节**里自造了一个 opcode 来区分控制和数据:

```
'0' + 终端输出        '1' + 标题        上行:'0' 键盘、'1' 改尺寸
```

我们用的是 **WebSocket 本来就有的那一位** —— 协议自己就分 text(0x1)和
binary(0x2):

```
binary   28 字节定长头 + 图片裸字节        ← 载荷
text     {"type":"cast",…} / {"type":"cursor",…}   ← 控制
上行 text {"type":"mouse",…} / {"type":"ack","frameId":N}
```

两者开销相当,但后者更可取:**分层由传输层保证,而非由约定保证。**

> **实际的连接可以不止一条。** 观看端采用通道模型:每条通道对应一个上游系统
> (`/channel/cdp` 对应 Chromium,`/channel/xpra` 对应 xpra),各自提供自己能提供的数据,
> 可开可关,并可并列加入第三条 —— 见 [e §6](e-client.md#6-通道模型)。
> 骨架不受影响:**输入永远只走 `/channel/cdp`**,这是一条结构约束而非默认值。
>
> 另有 `/api/events` 是给程序听的事件流,与画面无关。

## 6. 客户端:位置换了

链路最右端与直觉相反。

| | ttyd | webmuxd |
| --- | --- | --- |
| 客户端在做什么 | **全是渲染** —— 解 VT 状态机、维护屏幕缓冲、画字形 | **全是协议** —— 拆头、丢残帧、回 ack、心跳、输入归一化、IME |
| 有多大 | 几万行 | 几百行 |
| 渲染谁做 | 客户端自己 | **浏览器自带**(`<img>` 解 JPEG) |
| 有没有现成的 | **`npm i xterm`** | **没有** |

终端侧的难点是渲染,而渲染有一个沿用数十年的标准(VT100),
因此能够形成 xterm.js 这样的通用库。

这一侧渲染由浏览器提供,无需实现;**但线上格式是自定义的,没有第三方实现可用。**

> **ttyd 省去了协议,这一侧省去了渲染。** 两边客户端体量都不大,省去的是不同的一半。

内置观看页与 ttyd 自带前端同理。**它不是产品界面** —— 画面、一条 tab 条、
一个地址栏,没有会话列表、登录页或设置面板。它存在的唯一理由是**验证链路**:
启动后打开该地址即可确认整条链路是否连通。上层可自行实现界面,
所用接口与内置页完全一致。

## 7. 这条链路为什么是这个形状:载荷是像素,不是语义

前面每一跳的形状,追到底都是同一个原因。

`\x1b[10;5H` 这七个字节表示「将光标移至第 10 行第 5 列」——
它不是画面,而是**指示客户端绘制**的指令。终端输出流通篇如此,
且遵循一个数十年未变的标准。

浏览器的画面是像素。**没有一条流能同时表达"这个按钮是蓝色的"和"这里可以点"**——
前者在像素里,后者在 DOM 里。

| | 终端 | 浏览器 |
| --- | --- | --- |
| **谁在渲染** | 客户端 | **远端**,客户端只贴图 |
| **一帧多大** | 几十字节 | 几十 KB |
| 静止时的流量 | 0 | 0(画面不变就不产帧) |
| **光标** | 在流里 | 既不在像素里也不在协议里,得单独同步 |
| **语义在哪** | **就是流本身** | 在 DOM 里,要另开一条路去取 |

最后一行是本项目约一半工作量的来源:**终端不需要「观测」这一概念**,
因为其数据流本身即是语义;而要让程序获知浏览器页面的内容,必须另行从 DOM 提取。

## 8. 往下写什么

```
载荷是像素,不是语义
   ├─ 画面必须由我们产,而且产出来就是最终形态
   ├─ 客户端不渲染,只贴图
   ├─ 输入必须由我们翻译回去,而这带来了一个安全收口
   ├─ 语义要另开一条路去 DOM 里取
   └─ 终端自带的那些能力需逐项重建
```
