# c · 画面从哪来

**一句话**:画面有**三条来源**,使用者看到的名字是 **JPG / VNC / DOM**
(对应 CDP 截屏、xpra、rrweb —— 后面这三个词只出现在代码和这篇里,不出现在界面上)。
它们只回答同一个问题:**画面从哪来**。
接缝之上(输入、光标、tab、原生 UI、日志、权限)只有一套实现,
所以三条之间**可以像切画质一样切**(§9)—— 切的只是这一条路径,别的一个字不动。

前两条传的是像素,第三条传的是语义(DOM 变更,由观看端重排)。
**这不影响它们并列** —— 接缝的定义是"画面从哪来",不是"传的是不是像素"。

## 1. 第一条:让 Chromium 自己截

画面由我们生成之后,第一个问题是来源。CDP 中现成的答案是
`Page.startScreencast`:请求 Chromium **在页面变化时推送一张图**。

选择它的理由:

- **零依赖。** 浏览器自带能力,headless 即可运行,不需要 X,也不需要第三方进程
- **只包含页面内容。** 截取的是渲染结果而非桌面 —— 没有窗口边框和 tab 条,
  因而不存在「裁掉浏览器 UI」一类问题
- **静止不产帧。** 页面无变化时不发送任何帧

这条路可用,效果也好于预期。**但它的形状决定了它的上限。**

`screencastFrame` 提供的是**整屏图像**。Chromium 不提供「哪一块发生了变化」,
只提供当前的完整结果。由此:

| | 结果 |
| --- | --- |
| 滚动一行 | **整屏重发** |
| 编码 | 只能**预先选定一种**,全程不变 —— 文字与图片使用同一质量 |
| 静止之后 | 就停在最后那张有损的图上,**不会变清晰** |
| 局部动画 | 一个角落在动,发的还是整屏 |

这不是参数问题,而是**该接口只提供整屏**。要突破这一上限,必须引入
damage 追踪:识别变化区域、只发送该区域,并按其内容选择编码。

## 2. 缺的那半,自己造还是拿现成的

把上面那张表倒过来,就是一张待办清单:

```
知道哪一块变了            ← damage 追踪
把变化切成合适的块        ← 区域合并、边界处理
按各块内容选择编码        ← 文字用无损,图片用有损,视频用帧间
滚动时只发位移            ← 位移编码
静止后补一张无损的        ← 质量分级刷新
链路慢了自动降质          ← 码率自适应
```

**这是一个发展了二十余年的领域** —— X11 远程显示、VNC、RDP、SPICE 各有成熟实现。
自行重做一遍,等于把本项目变成一个远程显示项目,而它的定位是「浏览器的 tmux」。

因此问题转化为:**能否引入一个已完成上述清单的实现,仅将其用作画面来源?**

一个硬性条件:**它只能负责画面。** 这类协议通常自带完整的输入、剪贴板、
音频与文件传输;一旦启用,[b](b-input.md) 中的安全收口即不复存在(见 §10.1)。
因此候选实现必须可以拆分:**取其下行,不取其上行。**

## 3. 第二条:xpra

xpra 的定位是「X11 的 tmux」:使远端 X 程序的生命周期长于连接,允许断开后重新接入。
它为此实现的能力,恰好覆盖 §2 的清单:

```
观测一个 X 显示 ──▶ 识别变化区域 ──▶ 切分 ──▶ 逐块选择编码 ──▶ 按其协议发送
```

它自带的编码器包括 `webp` / `jpeg` / `png` / `rgb`,以及一个 **`scroll`**
(只发位移向量,不发像素),视频那档还有 `h264` / `vp8` / `vp9`。
质量自适应和「静止后补一张无损的」也是现成的。

它有一个前提:**其观测对象是一个真实的 X 显示**,因此浏览器必须是有头的;
而服务器上没有物理显示器 —— 相关的一整套(Xvfb 是什么、为何不用 Xorg)见 §8。
**这个前提也决定了它能不能被切到**(§9.3)。

而其上行可以不使用:协议要求的上行仅有六个握手与回执包,**输入是可选的**(§10.1)。
这一性质决定了它可以作为一条画面来源接入,而不是一个并行的整体方案。

## 4. 前两条产出的是同一种东西

CDP 那条:

```
Page.screencastFrame
   data      base64 的一整屏 JPEG
   metadata  尺寸、滚动位置、时间戳
   sessionId 哪个 tab
```

xpra 那条:

```
draw
   wid            哪个窗口
   x, y, w, h     屏幕上的哪一块
   coding         这块用什么压的:webp / jpeg / png / rgb32 / scroll
   data           压完的字节
   packet_sequence 用来回执
```

**抛开命名,两者结构一致:一块像素、它的位置、所用编码,以及一个回执号。**

| | CDP screencast | xpra |
| --- | --- | --- |
| 一次给多大 | **整屏** | **一块 damage 区域** |
| 编码谁挑 | 我们挑一次,全程不变 | **每块各挑** |
| 有哪些编码 | jpeg / png / webp | webp / jpeg / png / rgb / **scroll** / h264… |
| 回执 | `screencastFrameAck` | `damage-sequence` |
| 静止时 | 不产帧 | 不产帧 |

差异集中在**粒度**与**编码由谁选择**,而不在数据的性质上。

> 这是两者能够共用同一抽象、而 VNC 不能的原因 ——
> VNC 替换的不只是画面,还包括输入、权限与 runtime 契约。
> **仅替换画面、其余不动**,才构成可并列的来源。

### 4.1 它强在哪,以及它的劣势区

xpra 的长处**恰好对应 screencast 在结构上的缺失**:

| | screencast | xpra |
| --- | --- | --- |
| 更新粒度 | 整屏一帧 | **按 damage 区域** |
| 选编码 | 固定一种 | **每块区域各选**:文字走无损 webp/rgb |
| 滚动 | 整屏重发 | **`scroll` 包只发位移向量** |
| 静止之后 | 就那样了 | **`auto-refresh`:先发有损的,静止后补一张无损的** |

最后一条是其文字更清晰的根本原因:**运动时降质、静止后转为无损**。
screencast 无论是否运动都维持同一质量。

实测(同机同页,2026-08-18):

| 场景 | 结果 |
| --- | --- |
| 滚一页 Wikipedia,22 秒 | 3.71 Mbps。其中 **`scroll` 包用零字节完成了 57% 的重绘面积** |
| 全屏动画 1024×768,24 秒 | 2.86–9.34 Mbps ≈ 20 fps |

第二行是**它的劣势区间**,须一并说明:整屏持续变化时,分区域重传退化为整屏重传,
并额外承担分区开销。因此 screencast 并非被取代的旧实现,
而是**该场景下更合适的那一条**。

## 5. 第三条:rrweb —— 它不传像素

rrweb 注入页面后监听 DOM:先发一张全量快照,其后只发增量变更,
由观看端的 replayer 重排出画面。

它是三条里唯一一条**传语义而非像素**的。这不影响它并列 —— 它回答的仍然是
「画面从哪来」,只是答案是「不从远端来,由观看端渲染」。

### 5.1 它凭什么算一条

按接缝的定义逐条对:**只提供画面、不承载输入、不碰 tab、不碰权限。** 全中。
[e §6.6](e-client.md#66-这个模型是用来想清楚的不是插件框架) 那三个问题也答得上:
上游是页面里的记录器、只提供帧、在帧这一能力上排序见 §9。

### 5.2 它强在哪

**① 文字是真的文字。** 前两条到观看端是像素,rrweb 到观看端是 DOM ——
可以选中、可以搜索、缩放不糊。**在以文字为主的页面上,它的画质上限高于另外两条**,
因为它根本没有"压缩"这一步。

**② 带宽低一到两个数量级。** 实测靶页:rrweb 事件流 114 KB/s,
而未限流的 CDP 截屏 2686 KB/s。链路差的场景(移动网络、跨洲)这条是唯一舒服的。

**③ 它顺带就是回放。** 同一条流写下来就能按时间重放 ——
[i §5](i-agent-surface.md#5-现在的三个缺口) 缺的那一项它自带。

### 5.3 它的边界:能补的和补不了的

缺口在「有没有帧」这一侧,而**大部分可以补,补法本身说明了这条腿的性质**
(全部实测,见 §15):

| | 怎么补 | 结果 |
| --- | --- | --- |
| `<canvas>` 的绘制 | 打开 `recordCanvas` | **有了**,代价是它一直在把 canvas 转成图 |
| 图片 / 字体 / 样式 / 普通 mp4 | **资源代理**:从 `Network.getResponseBody` 收字节,把快照里的地址改写到我们身上 | **有了**,而且比 rrweb 自带的 `inlineImages` 更强 —— 后者要把图画进 canvas 才取得出字节,跨域没 CORS 头就污染画布、内联失败 |
| **MSE / `blob:` / `srcObject` 的视频** | —— | **没有,也补不了** |

最后一行是硬边界:那类视频**根本没有可代理的地址**,画面在浏览器内存里由
MediaSource 拼出来,rrweb 记的是元素和播放位置、不是帧。
实测 B 站视频页:播放器的控件、"试看30秒"那层提示都在(它们是 DOM),
唯独中间那块是黑的。

> **代理能补的是「地址够不够得着」,补不了「有没有帧」。**
> 于是这条腿的边界很清楚:
>
> ```
> canvas   → recordCanvas    已经是在传图
> 图片/mp4 → 资源代理        在传原始字节
> MSE 视频 → 只能自己抓帧    —— 那就是又写了一条截屏通道
> ```
>
> **每补一样,就往「传像素」退一步。** 补到 MSE 那一步,这条来源就变成了
> 另外那条,只是绕了一圈、还更贵 —— 所以停在这里,那种页面切到 xpra 或截屏(§9)。

### 5.4 保真度的误差就是坐标的误差

这条曾经被当成 rrweb 的死穴,现在要写准:**它不是一条独立的缺陷,
而是 §5.3 的直接后果。**

输入送出的是页面坐标([b §1](b-input.md#1-收口在哪))。前两条来源上这件事不用管:
观看端看到的正是远端渲染出的那张图。rrweb 上观看端看到的是**它自己重排出来的 DOM** ——
只要重排的结果和真页面一致,坐标就一致;**不一致的地方,恰恰就是没重排出来的地方**。

量过两次,差别正说明了这一点:

| | 最大偏移 |
| --- | --- |
| canvas 画不出来(盒子塌了,下面全体上移) | **124 px** |
| 打开 `recordCanvas` + 资源代理之后 | 实用上对得齐 —— B 站上点链接、往搜索框里打中文都正常 |

**所以这条的处理方式不是"修坐标",是"把画面补齐"。** 补不齐的那类页面
(§5.3 最后一行),同时也是坐标会偏的页面 —— 它们是同一批,而对那批页面
本来就该切走。

### 5.5 背压不能沿用「丢旧保新」

前两条来源上,缓冲满了保留最新、丢弃最早
([e §5](e-client.md#5-背压客户端的义务是必须回执))—— 每一帧自足,
丢掉旧的只损失一个中间状态。

rrweb 的事件是一条**增量链**。丢掉其中一条,重放出的 DOM 自此与真实页面不一致
且不自恢复 —— **界面看上去正常、内容却是错的**,比画面卡住更难发现。

因此这条通道要么不丢(以延迟换顺序),要么丢弃之后**重发一张全量快照**。
现在的实现是不丢 + 断线重连时从最近一张全量快照重放。
**这是三条里唯一在接缝之上留下痕迹的一处** —— 背压和回执本来就随通道走
([e §6.7](e-client.md#67-通道内部画面这条的共性)),但要记下来。

### 5.6 它改页面,而且改得比现在多

[b §5](b-input.md#5-光标同步) 那个光标探针已经在改变页面环境了,这件事一直是承认的。
rrweb 是同类代价的放大:一个持续运行的 MutationObserver、一个**五百多 KB 的脚本**,
并且**它的开销落在被自动化的那个页面上**(前两条的开销都在页面之外)。
对注入敏感的场景,这是一条比探针显著得多的痕迹。

## 6. 三条并排

| | **JPG**(CDP 截屏) | **VNC**(xpra) | **DOM**(rrweb) |
| --- | --- | --- | --- |
| 传的是 | 整屏图片 | 区域图片 | **DOM 变更** |
| 谁渲染 | 远端 Chromium | 远端 Chromium | **观看端** |
| 依赖 | **无** | X server + xpra | 页面里注入记录器 |
| 文字 | 有损压缩过的图 | 静止后补无损 | **真的文字**,可选中可搜索 |
| canvas | 有 | 有 | 要 `recordCanvas` |
| MSE 视频 | 有 | 有 | **没有** |
| 带宽(靶页) | 2686 KB/s(未限流) | 见 §4.1 | **114 KB/s** + 资源 |
| 中间过程 | 有 | 有 | 有(它是变更流) |
| 最适合 | 通用兜底、什么都能显示 | 连续动画、视频、滚动 | **文字为主的页面、链路差的时候** |

**没有一条是"最好的那条"** —— 这正是要能切的原因。

## 7. 接缝切在哪

> **三条来源之间唯一的差别,是画面从哪来。**
> 输入、光标、tab、原生 UI、日志、token、只读 —— **一模一样**。

这一条已经被验过:观看端的画面整个换成 rrweb 重排的 DOM 之后,
输入那一侧一个字没改(§15)。

在观看端,这一条被推广成了**通道模型**:每条通道对应一个上游系统,
声明自己能提供哪些能力,由一张固定的优先级表仲裁
([e §6](e-client.md#6-通道模型))。本篇之后的内容是「帧」这一种能力上的展开。

| | 谁负责 |
| --- | --- |
| 画面 | ← **只有这一行会变** |
| 输入翻译成 `Input.*` | 我们([b](b-input.md)) |
| 光标同步 | 我们 |
| tab 表 / `active` | 我们(`Target.activateTarget`) |
| 浏览器自己的那些 UI | 我们(CDP 拦截 + 自己画卡片) |
| 日志、事件、token、只读 | 我们 |

### 7.1 xpra 还提供了什么,以及为什么不取

xpra 是一个完整的远程显示协议,除画面外还提供输入、剪贴板、音频、文件传输,
以及**光标**。其中光标最值得讨论,因为我们确实需要它,并且为此付出了成本
([b §5](b-input.md#5-光标同步):向页面注入探针 + 命中测试 + 白名单)。

**它确实可用。** 实测:悬停在链接与空白之间切换时,xpra 按变化推送 cursor 包:

```
cursor  png 24×24  热点(4,4)  serial=3  720 B    ← 箭头
cursor  png 24×24  热点(8,5)  serial=4  722 B    ← 手型
```

即使输入来自 CDP 的合成事件(X 指针并未移动),Chrome 仍会更新窗口的 X 光标,
因此该通道随悬停正常变化。

**结论:不取。** 理由按重要性排列:

**① 它只存在于一条来源上。** 采用它意味着同一个用户可见行为存在两套实现,
而这正是 §7 那条接缝要避免的情况;并且 CDP 探针无论如何都必须保留 ——
另外两条来源没有别的选择。**这是新增复杂度,不是替换。**
**能切换之后这条理由更强了**:切一次画面来源就换一次光标实现,是不可接受的。

**② 它会使各条来源的信任模型不一致。** 白名单存在的原因是:光标取值会写入
观看端的 `style.cursor`,而远端页面不可信。改用图像后,远端可以完全控制
观看端光标的像素 —— 而这一变化只发生在一条来源上。

**③ 名称字段为空,无法低成本转换。** 若 xpra 能给出 X 光标名
(`left_ptr` / `hand2` / `xterm`),即可映射为 CSS 关键字并保持白名单模型;
实测该字段为空,只能得到图像。

## 8. 那一套 X 是什么

```
  ┌─ 浏览器 ────────────┐  画页面。它不知道自己在被录,
  │  chrome --kiosk      │  只知道"我有一个 X 显示可以画"
  └───────┬──────────────┘
          │ X 协议
  ┌───────▼──────────────┐  **虚拟显示**:一个没有显示器的 X server,
  │  Xvfb :80            │  把像素画进内存。没有键鼠,没有 GPU
  └───────┬──────────────┘
          │ X 的 Damage / Composite 扩展(哪块变了?)
  ┌───────▼──────────────┐  **xpra**:盯着那个 X 显示,把变化的区域
  │  xpra start-desktop  │  切分、逐块编码,按其协议发送
  └───────┬──────────────┘
          │ ws,只绑回环
  ┌───────▼──────────────┐  **我们**:一个口、token、上行白名单
  │  sessiond            │
  └──────────────────────┘
```

三个常被混起来的名字:

| | 是什么 | 不是什么 |
| --- | --- | --- |
| **X / Xorg** | 一套显示协议,以及它的参考实现 | 不是"图形界面"本身 |
| **Xvfb** | **一个 X server**,把像素画进内存而不是显卡 | 不是 xpra 的一部分 |
| **xpra** | 盯着一个 X 显示做 damage 追踪 + 编码 + 传输 | **它不自己造显示** —— 得有人给它一个 |

**X 这一层的必要性**:xpra 采集的是**一个真实窗口**,而真实窗口需要 X server;
服务器上没有物理显示器,该 X server 只能是虚拟的。
另外两条都不需要 X —— 一条截的是渲染结果,一条根本不在远端渲染。

### 8.1 虚拟显示钉死 Xvfb

xpra 的配置(`xvfb =` 那行)列了四种,**选哪个是发行版打包方定的**:

| | 要什么 | |
| --- | --- | --- |
| **`Xvfb`** ← 用这个 | `xvfb` 包,几 MB | 没有 GLX/DRI,分辨率靠 RandR 改 |
| `Xorg` + dummy 驱动 | **整个 Xorg** + 一份 xorg.conf | 云主机上通常没装 |
| `Xephyr` | 一个**已经在跑**的 X 显示 | 服务器上用不了 |
| `weston` + `Xwayland` | weston | 依赖更重 |

**显式传入 `--xvfb=Xvfb …`,不读取该配置。** Debian 系默认 `Xvfb`,
RHEL 系默认 Xorg+dummy,而云主机通常不安装 Xorg —— 同一条命令在两台机器上结果不同。

更关键的是它**绕过了探测**:`which("Xvfb")` 探测成功,而 xpra 实际使用 Xdummy。

> **探测对象必须与实际使用的对象一致。** 中间隔着第三方配置时,探测不构成保证。

分辨率:Xvfb 以较大尺寸(`8192x4096`)启动,再由 xpra 通过 RandR 调整到目标尺寸,
变更尺寸无需重启 X。

### 8.2 有头 + Xvfb 和 headless 差在哪

| | headless | 有头 + Xvfb |
| --- | --- | --- |
| **WebGL** | 有(自动退到 SwiftShader) | **默认没有** —— 要显式 `--use-gl=angle --use-angle=swiftshader`;`--disable-gpu` **救不回来**,有头下它关得更彻底 |
| GPU | 没有 | 没有 —— 两条都是软件渲染 |
| 原生对话框 | 不渲染 | **渲染,但点不动**(§12) |
| 浏览器自己的 bar | 没有 | 有 —— 所以要 `--kiosk`(§11) |
| 进程数 | 一个 | 三个:Xvfb + xpra + chrome |
| **能用哪几条来源** | JPG、DOM | **三条都能**(§9.3) |

### 8.3 要探哪些东西

| 探什么 | 少了会怎样 | |
| --- | --- | --- |
| `xpra` 可执行文件 | 什么都起不来 | ✓ |
| `Xvfb` 可执行文件 | vfb 起不来,xpra 自己退出 | ✓ |
| **跑 xpra 的那个 python 里有没有 PIL** | `start-desktop` 起不到一半就死。注意是**它的解释器**(读 shebang),不是我们的 —— webmuxd 常在 venv 里 | ✓ |
| 空闲的 X 显示号 | 撞号,起不来 | ✓ |
| **服务端有哪些图像编码器** | 我们只报 jpeg/png/webp/rgb/scroll。这个 xpra 编译时要是没带 webp 和 jpeg,就只剩 rgb —— **画面能出但带宽爆炸,而且不报错** | ✗ 还没探 |
| **xpra 的协议版本** | 我们写死 rencodeplus,更老的版本握手就失败,报错不指向版本 | ✗ 还没探 |

第五条属于「可运行但表现很差」一类,**比启动失败更难定位** —— 启动失败至少有报错。

## 9. 切换:像切画质一样

### 9.1 使用者看到的是三个词

**JPG / VNC / DOM。** 技术名字(screencast / xpra / rrweb)不出现在界面上 ——
它们说的是我们怎么实现的,而使用者要判断的是"这三个有什么不一样"。

| 界面上 | 一句话体感 | 什么时候选它 |
| --- | --- | --- |
| **JPG** | 一张一张的图,**什么都显示得出来** | 拿不准就用它;有视频、有 canvas 的页面 |
| **VNC** | 像远程桌面,**连续、跟手** | 动画、视频、大量滚动 |
| **DOM** | 传的是网页本身,**字最清楚、最省流量** | 文字为主的页面;网络差的时候 |

这三个词都是使用者已经有直觉的:JPG 就是一张图,VNC 就是远程桌面,
DOM 就是网页。**不解释原理,直接给体感** —— 选错了随时能切回来,代价只是几百毫秒。

三样东西要跟着这三个词走完全程(**一件事一个词**):切换器上的标签、
`--transport` 的取值、报错里的措辞。现在 CLI 收的还是 `screencast` / `xpra`,
**改成 `jpg` / `vnc` / `dom`(旧值留作别名)这件事还没做**(§17)。

一处得实话实说:**DOM 上看不了视频。** 这不能只写在文档里 ——
切到 DOM 而页面上有个播放器的时候,界面上要能看出来"这块是空的不是坏的",
并且给一条"切到 JPG/VNC"的出路。**沉默地少一块画面,比明说更糟。**

### 9.2 切的只有一样东西

三条在接缝之上完全一致(§7),所以「切」这个动作的定义很窄:
**停掉当前这条的下行,起另一条的下行。**

它之所以能这么窄,是因为**没有需要迁移的状态**:哪些 tab、当前 URL、
页面里已经填了什么,全都在 Chromium 里,不在任何一条来源里。
来源是只读的观测者 —— **观测者换人,被观测的东西不知道。**

> 一处得说实话:**「无缝」不等于「零间隙」。** 新那条要先产出第一张完整画面
> (截屏的第一帧、xpra 的全屏刷新、rrweb 的全量快照)才有得看,
> 中间有个几百毫秒的空档。切换应当保留上一张画面直到新的第一张到达,
> 而不是先黑一下。

### 9.3 能切到哪几条,起 session 的时候就定了

xpra 观测的是一个真实的 X 显示,所以浏览器必须是有头的 ——
**这不是运行时能改的,无头浏览器根本没有那个显示。**

| 起的时候 | 之后能切的 |
| --- | --- |
| **有头 + Xvfb** | **JPG / VNC / DOM 三条都能** —— JPG 在有头浏览器上照样工作 |
| 无头 | JPG、DOM |
| `remote`(只有一个 CDP 端点) | JPG、DOM |

> **所以起 session 时那个选择不是「用哪条」,是「以后能选哪几条」。**
> 有头那一档要装 X([d](d-install.md)),换来的是三条都在手上。
> 这一点必须在文档和报错里说清楚 —— 使用者会以为切换是纯运行时的。

### 9.4 切到 DOM 要先把记录器注进去

另外两条是从外面看,rrweb 要在页面里跑,这是它唯一一处不对称的地方。

`Page.addScriptToEvaluateOnNewDocument` 只对**之后的文档**生效 ——
中途切过去时,当前这一页是没有记录器的。两条路:等下一次导航,或者当场注一次。
**实测:五百多 KB 的 `Runtime.evaluate` 会挂住**(三十秒不回包),
所以当场注入得先把记录器拆成一个小的 record-only 包。**这一项还没做** ——
现在切过去只会在日志里告警"当前页没有记录器,要等下一次导航"(§17)。

反过来从 DOM 切走是干脆的:停止发事件即可,注入的东西留在页面里也无害
—— 但**它留下的痕迹不会因为切走而消失**(§5.6)。

### 9.5 切了必须说出来

和「启动失败不静默回退」是同一条规矩:**画质变了而人不知道为什么,
比画质差本身更糟。** 切换要在观看端留一条可见的记录:现在是哪条、为什么变的
(是人选的,还是某条起不来)。

**自动切换目前不做。** 判据是那句老话:**tmux 会做这个吗?**
—— 它不会替你决定用哪种终端。

## 10. 线切在哪

```
浏览器  ├── WS /channel/xpra     xpra 协议,只下行画面
        ├── WS /channel/rrweb    rrweb 事件流,只下行
        └── WS /channel/cdp      输入、光标、tab、ack —— 三条腿共用这一条
```

### 10.1 输入不走 xpra

xpra 自带完整的输入协议(`pointer-position` / `button-action` / `key-action`),
直接使用最为省事。**但这会拆掉 [b](b-input.md) 中的安全收口** ——
边界将由「仅能表达 `Input` 域的四种意图」退化为「在代理层过滤 packet」,
而**过滤属于黑名单模型,遗漏一类即出现一个缺口**。

因此**客户端不向该连接发送任何输入**。协议本身要求上行六个包
(`hello` / `map-window` / `focus` / `damage-sequence` / `ping_echo` / `disconnect`),
缺少任一个将导致收不到帧或被断开。这一约束反而带来一个更强的性质:

> **上行是一个闭集,因此可以使用白名单。** 代理仅放行这六个,其余全部丢弃。
> 白名单与黑名单的区别在于:**新增的 packet 类型默认被拒绝**。

收口由此成为**两层**:客户端不实现发送逻辑,代理也不放行。

同样的道理适用于 rrweb:**它是纯下行的**,重放出来的 DOM
在观看端 `pointer-events: none`,没有任何一条路把事件送进去。
**这不是靠自觉,是结构上做死的**(§15)。

### 10.2 那条连接经过我们

**经反向代理,不直接暴露 xpra 的端口。** 对外只呈现一个地址;
且 token 需在此校验一次 —— xpra 自身的鉴权是进程级的,
不识别我们的只读/可写 token。

rrweb 那条同理,并且多一件事:**页面里的资源也经过我们**
(§5.3 的资源代理),否则观看端要回原站拉,而原站往往认 `Referer`。

## 11. 画面里没有 bar

xpra 截的是真实的浏览器窗口,所以画面里本来会有 tab 条和地址栏。
量一下 `outerHeight - innerHeight`:

| 启动方式 | bar 高度 |
| --- | --- |
| 普通启动(带 `--no-sandbox` 警告条) | 143 |
| `--test-type --disable-infobars` | 88 |
| 再加 **`--kiosk`** | **0** |

**采用 `--kiosk`,不做裁剪。** 结果与裁剪一致(画面中不含浏览器 bar,tab 由我们绘制),
但省去一整套易错机制:无需发送高度变更通知、无需在客户端计算裁剪、
**无需为鼠标 `y` 补回偏移**(这一处最易出错且不易发现);
同时那 88 行像素不再被编码传输后丢弃(768 中的 88,约 **11.5% 带宽**)。

> `crop_top` 一旦存在,就必须处理其变化(视频全屏时归零、书签栏展开时增大);
> kiosk 下它恒为 0,**不存在变化这一情形**。
>
> **能切换之后这条更要紧了**:三条来源的画面必须是同一个矩形,
> 否则切一次坐标就偏一次。kiosk 让它们天然对齐。

一处细节:kiosk 配合 `--window-size=1024,768`,在 1024×768 的显示上实际得到
**1023×767**,右侧与底部各有一列黑边。处理方式是**多请求两个像素**,
超出显示的部分被裁掉,画面铺满;代价是页面视口变为 1026×770,
右下各 2 像素落在可见区域之外 —— 优于一条持续可见的黑边。

## 12. 接缝之上的东西一律不动

更换画面来源不影响接缝之上的任何一层。最容易被误以为可以省掉的是
**浏览器自己的那些 UI**(对话框、下载、文件选择、权限、认证)——
有头之后画面里能看见它们了,直觉上似乎可以让人自己点。

**不能。** 实测:有头 Chrome 会把 JS 对话框绘制出来,但**那个按钮无法被点击** ——
它属于浏览器进程绘制的 UI,而 `Input.*` 作用于渲染进程;
加之 §10.1 规定输入不走 xpra,**我们允许的任何输入路径都无法关闭它**。

而在另外两条来源上,后果更重:**不接管的话整个会话会冻住。**
开了 `Page.enable` 之后 Chrome 把对话框交给客户端**并一直等**,
没人应答则渲染进程卡死,之后每一个 `Input.dispatchMouseEvent` 都超时。
实测:`alert` 弹出之前 CDP 往返 3 ms,弹出之后连着三次十二秒不回;
真实场景里最容易触发的是 `beforeunload`。

> **症状是「鼠标点了没反应」,不是报错。** 这类失败最难查 ——
> 所以拦截不是优化项,是必需项。展开见
> [g §5](g-native-ui.md#5-有头之后能看见但点不动)。

## 13. 默认走哪条

```bash
webmuxd install                                          # 有 root 就把 xpra 那套装上
webmuxd new --id work --port 7900                        # 默认 xpra
webmuxd new --id work --port 7900 --transport screencast # 零系统依赖那条
```

**默认选择效果更好的一条,而非更易安装的一条。** 安装成本由 `webmuxd install` 承担 ——
它本就是运行前必须执行的步骤(需要下载浏览器),一并处理 xpra / Xvfb / PIL。

**启动失败即报错,不静默回退。** 静默回退会使使用者误以为当前画质来自 xpra。
退路是显式指定另一条。

**`remote` 上少一个选项**:该路径下只有一个 CDP 端点,无法访问对端的 X 显示,
所以只有 JPG 和 DOM —— **这不是降级,是那条路上的全集**(§9.3)。

## 14. 客户端

三条来源,客户端要有三种解码路径:

| | 客户端做什么 | 解码器 |
| --- | --- | --- |
| CDP 截屏 | 拆 28 字节头、换 `<img>.src` | 浏览器提供 |
| xpra | 拆包、按区域调度绘制 | 浏览器提供(`createImageBitmap`) |
| rrweb | 喂给 `Replayer`,live 模式 | **第三方库**,几万行 |

前两条**客户端不含渲染器**;rrweb 那条客户端重新成为一个渲染器,
而且那个渲染器既非我们实现、也非浏览器内置。
**这是三条里客户端体量差得最远的一处** —— 也是切换的实际成本所在:
要能切,客户端就得同时带着这三份。

xpra 的协议部分是自己解的:
[`static/xpra.js`](../../../webmuxd/view/static/xpra.js) +
[`rencode.js`](../../../webmuxd/view/static/rencode.js),去掉注释三百来行。
只需三百行的原因是 **`xpra-html5` 中不存在解码器** ——
其余五千行为窗口管理、剪贴板、音频、虚拟键盘与 jQuery,**均不在需求范围内**。

一条重要的设计杠杆:**服务端只发送客户端在握手中声明过的编码**。
**未声明的编码永远不会被发送。** 因此客户端的复杂度由我们决定 ——
当前不声明视频编码,也就不需要 WebCodecs。

## 16. Playwright trace:不是来源,是产物

查过、也做过,结论单独记一句免得再问一遍:**它的像素那一半就是第一条腿**
(字面意义上同一套 `Page.startScreencast` 调用),**DOM 那一半在我们的架构里
一张也产不出来** —— 它的快照只在 Playwright 自己的 API 调用前后拉,
而我们的输入是裸 CDP,不构成它的调用。

但它回答的本来就是另一个问题:**这次会话事后怎么复盘。**
作为那个用途它很强,而且我们能自己写:动作边界本来就是我们定义的
—— 实测导出的 trace 用官方 viewer 打得开。归 [i §6](i-agent-surface.md#6-还没定的) 定。
