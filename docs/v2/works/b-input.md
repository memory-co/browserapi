# b · 输入翻译,以及它换来的东西

**一句话**:观看者的鼠标键盘被归一化成 JSON 发上来,服务端翻译成 CDP 的
`Input.*` 打回远端。**这层翻译不是一道工序,是整个安全模型的收口** ——
观看者能对远端做的事,全部被限制在 `Input` 域那四个命令里。

> 本篇展开 [a](a-architecture.md) 中「输入必须由我们翻译回去」这一条,
> 并说明它带来的能力:**这一层多出来的工作量,换来的是 VNC 那条路做不到的事。**

## 1. 收口在哪

先把一次鼠标移动的完整路径摆出来 —— 后面所有的性质都从这条路径读出来:

```
①  观看者的浏览器      mousemove 落在画面元素(<img> 或 <canvas>)上

②  客户端归一化        用该元素的实际尺寸,把客户端坐标换算成画面坐标

③  WS /channel/cdp · text  {"type":"mouse","event":"move","x":412,"y":233,
                            "buttons":0,"modifiers":0}
    (当前实现中该路径是 /api/view,见 [e §6.1](e-client.md#61-通道--一个上游系统的连接))

④  sessiond · 白名单   消息类型不在允许集合内 → 丢弃

⑤  sessiond · 权限     只读连接 → 丢弃,且不逐事件回错(见下)

⑥  sessiond · 翻译     Input.dispatchMouseEvent
                        {type:"mouseMoved", x, y, button, buttons, modifiers}

⑦  CDP(另一条 WS)   带 sessionId 发给 Chromium

⑧  Chromium 渲染进程   页面收到真实的 mousemove
```

四条性质:

**① 无论像素从哪条来源来,这条路径完全一样。** xpra 那条连接不参与输入 ——
客户端不向它发送任何输入,代理也不放行([c §7.1](c-pixels.md#71-输入不走-xpra))。
换来源只改变第 ①、② 步作用在哪个元素上。

**② ③ 与 ⑦ 是两条不同的 WebSocket。** 前者是我们对外提供的,
后者是 sessiond 作为 Chromium 客户端持有的。**观看者永远接触不到后者** ——
这正是这一层被称为收口的原因。

**③ ⑦ 的 `sessionId` 决定输入落在哪个 tab。** 它取的是**当前正在被观看的那个**,
因此一次输入到不了其他 tab。

**④ 移动与滚轮不触发让路窗口**,只有按下与按键触发。否则鼠标一移动,
程序侧的动作就会被"人正在操作"挡住。

抽象成能力,观看者可表达的意图只有四种:

```
观看者的 DOM 事件 ──归一化──> sessiond ──> Input.dispatchMouseEvent
                                            Input.dispatchKeyEvent
                                            Input.insertText
                                            Input.dispatchWheelEvent
                                      └──> 仅此四个
```

观看者**无法取得 DOM、无法执行脚本、无法发送任意 CDP 命令**。可表达的意图仅限于
「在某坐标点击」「按下某键」—— 与坐在真实浏览器前的人完全等价,不多不少。

这条边界的位置与 VNC 相同(RFB 同样只能传输鼠标键盘)。**区别在于它由我们实现,
因此可以附加条件。**

最直接的推论:**权限在服务端强制,而非前端禁用。**
只读观看者照常收帧,其输入在这一层被丢弃 —— 即使自行实现客户端直接发送也无效。
VNC 无法做到这一点:口令只有「给或不给」,给出即为全权;而我们不在 RFB 链路上,
**没有任何位置能拦截一次鼠标点击**。

(token 的种类、签发方式与有效期属于接口设计,不在本篇范围。)

## 2. 键盘:带 `text` 的 `keyDown`,不是 `insertText`

| | 字符能进输入框 | 页面收到真实 `keydown` |
| --- | --- | --- |
| `Input.insertText` | ✅ | ❌ |
| `Input.dispatchKeyEvent(type=keyDown, text=…)` | ✅ | ✅ |

**必须使用后者。** 监听按键的页面 —— 快捷键、搜索联想、编辑器、游戏 ——
只有收到真实 `keydown` 才能正常工作。

一次按键需发送完整三元组 `keyDown` → (`char`) → `keyUp`,并带齐
`key` / `code` / `windowsVirtualKeyCode` / `modifiers`。缺少任一项,
依赖 `e.key` 判断或 `preventDefault` 的页面即出现异常行为。

`insertText` 另有用途 —— 它是 **IME 提交**与**粘贴**的正确手段(§3、§4),
这两种场景本就不应逐字符伪造按键。

## 3. IME:这条路反而比 VNC 短

VNC 传输中文一直是难点:要么在服务端安装完整输入法(候选词框须作为像素回传,
**延迟直接叠加在输入过程上**),要么客户端组字、服务端按键,两侧状态错位。

该问题在这一路线上**从根本上不存在**:

```
用户在自己的浏览器里打字 → 本地 IME 组字(候选词框是本地 UI,零延迟)
                          → compositionend 拿到最终文本 "提交订单"
                          → Input.insertText("提交订单")   一次,不是四次按键
```

组字过程**完全不离开本地**。客户端监听 `compositionstart` / `compositionend`,
**组字期间不发送任何按键事件**(否则远端将收到一串无意义的字母),
`compositionend` 时以一条 `insertText` 提交最终文本。

代价:组字期间远端页面无法看到输入中间态,对搜索联想一类页面有轻微影响。

> **这是少数几处优于 VNC 而非持平的地方**,且不需要额外成本 ——
> 观看端本身就是一个完整的浏览器,自带输入法。

## 4. 剪贴板

| 方向 | 做法 |
| --- | --- |
| 本地 → 远端 | 客户端 `paste` 事件拿 `clipboardData` → `Input.insertText` |
| 远端 → 本地 | 客户端按 Ctrl+C 时,服务端读 `document.getSelection()`,回给客户端写进本地剪贴板 |

反向传输必须在客户端的 `copy` 事件中完成 —— 浏览器要求用户手势才允许写入剪贴板。

**只读观看者两个方向均禁止。** 粘贴属于写操作;复制属于**将远端内容带出隔离边界**,
后者是否禁止取决于场景,此处的选择是**跟随写权限** —— 只读即只能查看,不能带走。
如需放开,应由另一种授权承担,而不是默认行为。

## 5. 光标同步

远端页面的光标形状需同步到本地。缺少这一步,画面上一切均为箭头,
**使用者无法分辨哪里可点击**。

终端中光标包含在字节流内,无需额外处理;这里**既不在像素中,也不在协议中**:
合成器不将光标绘入帧,CDP 也没有「光标形状变化」这类事件。因此只能在页面内放置探针,
读取命中元素的计算样式,**仅在取值变化时上报**,再经控制通道下发。

两条约束:

**命中测试不可省略。** `cursor: auto` 的语义是「文字上为 I 型、其余为箭头」,
仅读取计算样式时两种情况均为 `auto`。而 `caretRangeFromPoint` 会
**吸附到最近的文字节点**,因此还需用 `getClientRects()` 确认指针确实落在字形矩形内 ——
缺少这层校验,空白处也会被判为 I 型。

> xpra 那条来源自带 cursor 通道,可以不注入探针就拿到光标 ——
> **实测可用但不采用**,理由见 [c §5.1](c-pixels.md#51-xpra-还提供了什么以及为什么不取)。

**取值必须经过白名单。** 该值会被直接写入观看端的 `style.cursor`,
而**远端页面不可信**。CSS 的 `cursor` 接受 `url(...)`,原样透传相当于允许
被隔离的页面**驱使观看端浏览器请求任意 URL**,隔离在此处即被突破。
因此只放行 CSS 规范中的关键字,其余降级为 `default`。

## 6. 一条已知代价:探针页面看得见

光标探针(以及后续各篇涉及的其他探针)注入于页面内,**页面可以观察到它** ——
这是 CDP binding 的固有性质,不宣称能够隐藏。

它影响的是承诺的边界:「用 DevTools 直接连上去,看到的与 webmuxd 看到的一致」
仍然成立,但页面环境中**确实多了一个由我们注入的对象**。
对反自动化检测敏感的场景需要考虑这一点 —— **这是该路线的已知特征,不作为缺陷**。

由此确立一条约束:**探针只保留一个,新功能复用它,不为每个功能新增。**
