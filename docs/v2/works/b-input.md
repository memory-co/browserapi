# b · 输入翻译,以及它换来的东西

**一句话**:观看者的鼠标键盘被归一化成 JSON 发上来,服务端翻译成 CDP 的
`Input.*` 打回远端。**这层翻译不是一道工序,是整个安全模型的收口** ——
观看者能对远端做的事,全部被限制在 `Input` 域那四个命令里。

> 这一篇是 [a](a-architecture.md) 里"输入必须由我们翻译回去"那一条的展开。
> 它同时解释了一件不直观的事:**这条路上多出来的工作量,换来了 v1 做不到的能力。**

## 1. 收口在哪

```
观看者的 DOM 事件 ──归一化──> sessiond ──> Input.dispatchMouseEvent
                                            Input.dispatchKeyEvent
                                            Input.insertText
                                            Input.dispatchWheelEvent
                                      └──> 就这四个,没有别的
```

观看者**拿不到 DOM、执行不了脚本、发不出任意 CDP 命令**。他能表达的全部意图是
"在某个坐标点一下""按某个键" —— 和坐在真实浏览器前的人完全等价,不多不少。

这条边界的位置和 VNC 那条一样(RFB 也只能送鼠标键盘)。**区别在于它是我们实现的,
所以它可以带条件。**

最直接的一条推论:**权限可以在服务端强制,而不是前端 disable。**
一个只读的观看者照样收帧,他的输入在这一层被丢弃 —— 他自己写个客户端直接发也没用。
VNC 那条做不到:口令只有"给不给",给了就是全权,而我们不在 RFB 链路上,
**没有任何位置能拦下一次鼠标点击**。

(具体有几种 token、怎么签、多久过期,是接口的事,不在这一篇。)

## 2. 键盘:带 `text` 的 `keyDown`,不是 `insertText`

| | 字符能进输入框 | 页面收到真实 `keydown` |
| --- | --- | --- |
| `Input.insertText` | ✅ | ❌ |
| `Input.dispatchKeyEvent(type=keyDown, text=…)` | ✅ | ✅ |

**必须用后者。** 监听按键的页面 —— 快捷键、搜索联想、编辑器、游戏 ——
只有收到真实 `keydown` 才工作。

一次按键发的是完整三元组 `keyDown` → (`char`) → `keyUp`,带齐
`key` / `code` / `windowsVirtualKeyCode` / `modifiers`。少一样,
靠 `e.key` 判断或 `preventDefault` 的页面就会行为异常。

`insertText` 不是没用 —— 它是 **IME 提交**和**粘贴**的正确工具(§3、§4),
那两种场景本来就不该逐字符伪造按键。

## 3. IME:这条路反而比 VNC 短

VNC 传中文是老大难:要么在服务端装一整套输入法(候选词框还得作为像素传回来,
**延迟直接叠加在打字上**),要么客户端组字、服务端按键,两边错位。

这个问题在这儿**从根上不存在**:

```
用户在自己的浏览器里打字 → 本地 IME 组字(候选词框是本地 UI,零延迟)
                          → compositionend 拿到最终文本 "提交订单"
                          → Input.insertText("提交订单")   一次,不是四次按键
```

组字过程**完全不出本地**。客户端监听 `compositionstart` / `compositionend`,
**组字期间一个按键事件都不发**(否则远端会收到一串乱码般的字母),
`compositionend` 时一条 `insertText` 送最终文本。

代价:组字期间远端页面看不到"正在输入"的中间态,对搜索联想那类页面有轻微影响。

> **这是少数几处"我们比 VNC 更好"而不是"打平"的地方**,而它是免费的 ——
> 因为观看者用的是一个真的浏览器,它自带输入法。

## 4. 剪贴板

| 方向 | 做法 |
| --- | --- |
| 本地 → 远端 | 客户端 `paste` 事件拿 `clipboardData` → `Input.insertText` |
| 远端 → 本地 | 客户端按 Ctrl+C 时,服务端读 `document.getSelection()`,回给客户端写进本地剪贴板 |

反向那条必须挂在客户端的 `copy` 事件里做 —— 浏览器要求用户手势才允许写剪贴板。

**只读观看者两个方向都禁。** 粘贴属于写;复制属于**把远端内容带出隔离边界**,
后者是不是该禁取决于场景,这里的选择是**跟随写权限** ——
只读就是只能看,不能带走。要放开,那是另一个 token 的事,不是默认。

## 5. 光标同步

远端页面里光标是什么形状,本地就跟着变。没有它,画面上一切都是箭头,
**人分不清哪里能点**。

这件事在终端里是白给的(光标在字节流里),在这儿**既不在像素里也不在协议里**:
合成器不把光标画进帧,CDP 也没有"光标形状变了"这类事件。所以只能往页面放一个探针,
读命中元素的计算样式,**值变了才上报**,再由控制通道下发。

两条约束:

**命中测试不能省。** `cursor: auto` 的语义是"文字上 I 型、别处箭头",
光读计算样式两种情况都是 `auto`。而用 `caretRangeFromPoint` 找文字时它会
**吸附到最近的文字**,所以还要用 `getClientRects()` 确认指针确实落在字的矩形里 ——
不加这层校验,空白处也会报 I 型。

**值必须过白名单。** 这个值会被直接写进观看者的 `style.cursor`,
而**远端页面不可信**。CSS 的 `cursor` 接受 `url(...)` ——
原样透传等于让被隔离的页面**指使观看者的浏览器去拉任意 URL**,隔离在这一处就破了。
只放行 CSS 规范里的关键字,其余降级成 `default`。

## 6. 一条已知代价:探针页面看得见

光标探针(以及后面几篇会用到的其他探针)是注入进页面的,
**页面能看见它** —— 这是 CDP binding 的固有性质,不假装能隐藏。

这条影响的是承诺的边界:"你自己拿 DevTools 连上去,看到的和我们看到的一样"
仍然成立,但那个页面环境里**确实多了一个我们放的东西**。
反爬敏感的场景对此敏感,**这是这条路线的已知特征,不是缺陷**。

由此定下一条规矩:**探针只有一个,新功能复用它,不为每个功能再开一个。**
