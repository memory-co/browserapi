# e · 观看端的客户端

**一句话**:这个位置在 ttyd 侧由 xterm.js 承担,在这里**没有现成实现**。
它要做的不是渲染 —— 渲染由浏览器提供 —— 而是**协议**:拆解帧头、丢弃过期帧、
回执、心跳、输入归一化、IME、光标。它分为三层,**只有最底层无法由外部实现**。

## 1. 它要做什么

| | ttyd 的客户端 | 我们的 |
| --- | --- | --- |
| 解 VT 状态机、维护屏幕缓冲、画字形 | ✔ 全部工作量 | — |
| 拆定长头、按 `targetId` 丢残帧 | — | ✔ |
| 回执 + 心跳(丢一帧就永久卡死) | — | ✔ |
| 输入归一化、批量、IME、粘贴 | 部分 | ✔ |
| 光标形状同步 | — | ✔ |
| 把图贴上去 | — | 一行 |
| **规模** | **几万行** | **几百行** |

**难点的位置发生了转移**:终端侧的难点是渲染,这一侧的难点是协议。

## 2. 为什么没有现成的

xterm.js 得以存在,是因为它实现的是一个**数十年未变的公开标准**(VT100),
因此值得投入形成一个通用库。

这里的线上格式是自定义的 —— 28 字节定长头、`frameId` 与 `targetId` 的语义、
回执的时机规则 —— **不存在第二个实现,也不会自发出现**。
原因不是缺少调研,而是该格式尚无外部使用者。

**推论:该组件必须自行实现,且实现后应可供外部直接使用。**
否则每一个自建界面的使用者都需重写协议层,而这一层的约束
(回执时机、过期帧识别)均不体现在接口表面。

## 3. 分三层

```
┌─ UI 层 ────────────────────────────────────┐
│  tab 条、地址栏、原生 UI 卡片、状态栏       │  纯 REST 消费者
│  数据来自 /api/tabs、/api/pending           │  **可由外部重写,本就应当重写**
├─ 画面层 ───────────────────────────────────┤
│  <img> 或 <canvas>,把解出来的图贴上去      │  解码是浏览器自带的
├─ 协议层 ───────────────────────────────────┤
│  拆头 / 丢残帧 / ack / 心跳 /               │  **只有这一层别人写不了**
│  输入归一化 / IME / 光标 / 尺寸             │
└─────────────────────────────────────────────┘
```

**该分层即为打包边界**(§9):仅协议层对外发布,上面两层归上层产品负责。

## 4. 协议层:四条规则

### 4.1 收到帧立刻回执,带帧号,不搭车

```jsonc
{"type": "ack", "frameId": 41}
```

**回执同时充当 RTT 探针,而 RTT 是自适应降质的唯一输入。**
若将其附加在输入消息上,发出时刻即被输入的批量节奏约束 ——
所测得的 RTT 中混入了客户端自身的排队时间,不再是网络往返时延。

`frameId` 必须携带。服务端**按编号查表**计算 RTT,编号不匹配时跳过,不计入窗口:
客户端漏发一个(例如该帧解码失败)仅损失一个样本;
而「取出最早的时间戳」将导致**永久错位**,此后每个 RTT 均对应上一帧,且无法自行恢复。

### 4.2 三秒补一个回执

在推送模型下**回执中断即导致永久停滞**:客户端收不到帧 → 不发回执 → 服务端额度耗尽 → 更无帧可发。

```
每收到一帧 → 重置 3 秒定时器
3 秒没帧   → 无条件补一个(带手上最新的 frameId)
```

它与「静止页面不产帧」不冲突 —— 静止时服务端本就无帧可发,补发回执只是归还额度。
**成本为每 3 秒数十字节,换取的是自恢复能力。**

### 4.3 输入批量,回执不批量

| | 节奏 |
| --- | --- |
| `mousemove` / `wheel` | 攒 25ms 一批,**同批里只留最后一个 mousemove** |
| `mousedown` / `mouseup` / `key` / `text` | **立即发**,不进批 |
| 回执 | **立即发**,永远不进批(4.1) |

按下与抬起不可延迟:25ms 在点击上可被感知,且 `mousedown` 与 `mouseup` 之间
插入 25ms 会使部分页面判定为长按。

### 4.4 上行不做 RPC

输入为单向投递,不需要响应。**所有需要响应的操作**(打开 tab、导航、观测、回填对话框)
**经 REST** —— 该通道本身即具备请求-响应、状态码与错误结构。

> 在 WS 上另建一套请求-响应,等同于重新实现 `/api/` 的全部能力。
> 边界为:**WS 仅承载高频、单向、无需响应的数据** —— 帧、输入、回执、光标。

## 5. 背压:客户端的义务是「必须回执」

服务端一侧采用额度制:每条连接**各自持有额度与缓冲**,额度耗尽时新帧进入缓冲,
**缓冲满时保留最新、丢弃最早**(实时画面中过期帧没有价值,保留旧帧只会累积延迟)。

因此较慢的连接**仅影响自身丢帧**,不影响其他连接。

客户端在此只有一项义务:**收到即回执**(两条来源各自的回执机制见 §6.5)。不回执的客户端会自行停滞 ——
这是设计结果,不是故障;而 §4.2 的心跳保证该停滞始终是暂时的。

## 6. 两条像素来源在客户端的完整形态

### 6.1 screencast:一条连接

```
WS /api/view ──┬── binary  28 字节头 + 整屏图片 ──▶ Blob ──▶ <img>.src
               ├── text    尺寸 / 光标 / 权限
               └── text ▲  输入 / 回执 / resize
```

一条连接同时承载画面与控制,回执走同一条(§4)。

### 6.2 xpra:两条连接,同一个元素

```
WS /xpra     ──── binary  8 字节头 + rencodeplus ──▶ 区域解码 ──▶ <canvas>
                                                                    ▲
WS /api/view ──┬── text    尺寸 / 光标 / 权限 ────────────────────────┘
               └── text ▲  输入 / tab / resize
```

差别只有一处:**画面从第二条连接来,而控制仍在原来那条。**

具体到实现:切换来源时把 `<img>` 换成 `<canvas>`,并把"当前画面元素"这一引用
指向新元素。此后光标、尺寸、输入坐标全部作用于该引用 ——
**上层代码不需要知道当前是哪一条来源。**

在这一模式下,`/api/view` **不再承载任何帧**,其回执环处于空转;
背压完全由 xpra 的 `damage-sequence` 承担(§6.5)。

### 6.3 光标如何与另一条流合并

这是两条连接必须共存时最值得说明的一处,而结论是:**合并发生在 DOM 层,
不在像素层。**

- **远端不绘制光标。** 无论哪条来源,帧里都不含光标 —— 合成器不绘制,
  xpra 也不把它编码进区域。
- **本地光标由观看者自己的浏览器绘制**,位置就是真实鼠标位置,
  层级天然在画面元素之上。
- **服务端下发的只是形状**(`pointer` / `text` / `grab` …,已过白名单),
  客户端写入当前画面元素的 `style.cursor`。

```
远端页面   命中测试 → 计算样式里的 cursor,变化才上报
   │        (走 CDP)
sessiond   过白名单
   │        WS /api/view · text {"type":"cursor","cursor":"pointer"}
客户端     画面元素.style.cursor = 那个值
```

由此得到两条性质:

**① 两条流不需要时间对齐。** 光标形状晚一帧到达,视觉上无损 ——
它与像素不共享同一个平面,不会出现"光标画在旧画面上"这类撕裂。
若把光标当作像素传输(VNC 的做法之一),就必须处理这种对齐。

**② 换来源不影响这条路径。** 光标始终走控制通道、始终落在当前画面元素上,
`<img>` 与 `<canvas>` 在这一点上没有区别。

### 6.4 坐标为什么天然对齐

输入坐标由画面元素的实际尺寸换算得到,两条来源共用同一段代码。
成立的前提是**两条来源的画面原点相同**:

| | 画面内容 | 原点 |
| --- | --- | --- |
| screencast | 页面视口 | 视口左上角 |
| xpra | 整个浏览器窗口,而 `--kiosk` 下窗口内没有 bar | 同为视口左上角 |

**`--kiosk` 在这里的作用不止是"画面更干净"**:它使窗口坐标与视口坐标重合,
从而消除了坐标换算中的偏移项。存在 bar 时必须在客户端补回该偏移
([c §8](c-pixels.md#8-画面里没有-bar)),而这类偏移错误不会报错,
只表现为"点击位置整体偏移"。

### 6.5 背压:各自的回执

| | 回执 | 语义 |
| --- | --- | --- |
| screencast | `/api/view` 上的 `{"type":"ack","frameId":N}` | 额度制,由 §4.1 / §4.2 约束 |
| xpra | `/xpra` 上的 `damage-sequence` | xpra 自身的流控,按包序号 |

两者互不相干,且**在任一时刻只有一个在工作**。心跳同理:
screencast 由客户端每 3 秒补一次回执,xpra 由服务端 `ping` / 客户端 `ping_echo` 承担。

### 6.6 一条连接断开时的行为

两条连接的生命周期独立,但**可用性判定以控制通道为准**:

| 断开的是 | 结果 | 判定 |
| --- | --- | --- |
| `/api/view` | 无法输入、无法切 tab、光标不再更新;像素仍在到达 | **判为不可用**,画面置灰并重连 |
| `/xpra` | 画面停止更新;输入仍会送达远端 | 画面置灰并重连 |

控制通道之所以是权威,原因是:**只有像素而不能操作,不构成一个可用的会话** ——
此时画面还在更新反而具有误导性。

### 6.7 两条来源在解码上的共性

| | screencast | xpra |
| --- | --- | --- |
| 收到什么 | 28 字节头 + 整屏图片 | 8 字节头 + rencodeplus 包 |
| 如何解码 | `Blob` → `<img>` | `createImageBitmap` / 画布内位移 |
| 绘制目标 | `<img>` | `<canvas>` |
| **解码器** | **浏览器提供** | **浏览器提供** |
| 客户端实现的部分 | 拆头、替换 `src` | 拆包、按区域调度绘制 |

**共性比差异更重要:两条来源均未自行实现编解码器。** 客户端负责的是**调度** ——
绘制顺序、区域映射,以及回执时机。

一处具体约束:**解码为异步,因此绘制必须串行**。并发绘制会使后到的帧覆盖先到的帧,
在滚动时表现为画面撕裂。

## 7. IME:客户端存在的另一个理由

§6 说明了画面与光标为何需要一个客户端;IME 是另一条,而且它是这条路线相对
VNC 的净收益。

组字全部在本地完成:候选词框为本地 UI、无延迟,`compositionend` 之后才提交
最终文本。**组字期间不发送任何按键** —— 否则远端将收到一串无意义的字母。

该处理只能在客户端完成,因为**组字本就发生在用户自身的浏览器中**。
把它挪到服务端,就回到了 VNC 的处境:要么在远端安装完整输入法并把候选词框
作为像素回传,要么两侧状态错位。

## 8. UI 层:内置那个页面不是"界面"

内置观看页与 ttyd 自带前端同理。**它不是产品界面**:
画面、一条 tab 条、一个地址栏,以及若干原生 UI 卡片,
**没有会话列表、登录页或设置面板**。

它存在的唯一理由是**验证链路**:打开该地址即可确认整条链路是否连通。

它使用的接口与外部可用接口**完全一致**:`/api/tabs` 获取 tab 表、
`/api/pending` 获取阻塞页面的项。**不使用未公开接口** —— 这是一项自检:
一旦内置页依赖了未公开能力,「上层可自行实现界面」这一承诺即失效。

## 9. 该发出去的是哪一层

```
@webmuxd/client   ← 只包协议层
```

三条自律:

**① 内置页必须是它的第一个使用者。** 而非附带使用 ——
若内置页采用另一套实现,该库将逐渐失效,且失效过程不会被察觉。

**② 零依赖、单文件 ESM。** 需支持 `<script type=module>` 直接引入,
同时可发布至 npm;在严格 CSP 环境下亦须可用。

**③ 版本跟随格式,而非跟随 webmuxd。** 仅当帧头或上行消息集合变更时升版本;
新增 REST 端点与其无关。

**当前完成一半**:xpra 来源的协议客户端已是独立模块
(`static/xpra.js` + `rencode.js`,去除注释约三百行),
而 screencast 来源**仍位于内置页内** —— 外部无法获取,只能自行重写。
