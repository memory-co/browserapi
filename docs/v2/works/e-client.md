# e · 观看端的客户端

**一句话**:这个位置在 ttyd 那边是 xterm.js,在我们这儿**没有现成的**。
但它要做的不是渲染 —— 渲染浏览器自带 —— 而是**协议**:拆头、丢残帧、回执、
心跳、输入归一化、IME、光标。它分三层,**只有最底下那层别人写不了**。

## 1. 它要做什么

| | ttyd 的客户端 | 我们的 |
| --- | --- | --- |
| 解 VT 状态机、维护屏幕缓冲、画字形 | ✔ 全部工作量 | — |
| 拆定长头、按 `targetId` 丢残帧 | — | ✔ |
| 回执 + 心跳(丢一帧就永久卡死) | — | ✔ |
| 输入归一化、批量、IME、粘贴 | 部分 | ✔ |
| 光标形状同步 | — | ✔ |
| 把图贴上去 | — | 一行 |
| **规模** | **几万行** | **几百行** |

**位置换了**:那边的难点是渲染,我们的难点是协议。

## 2. 为什么没有现成的

xterm.js 能存在,是因为它实现的是一个**几十年没变的公开标准**(VT100 那套),
所以值得有人做一个人人可用的库。

我们的线上格式是自造的 —— 28 字节的定长头、`frameId`/`targetId` 的语义、
ack 的时机规则 —— **没有第二个实现,也不会自然长出来**。
这不是"我们懒得找",是这个格式还太年轻。

**推论:这个位置的东西必须我们自己写,而且写完要能被别人拿去用。**
否则每个想自己做界面的人都要把协议层重写一遍,而那一层的坑
(ack 什么时候发、残帧怎么认)全都是隐性的。

## 3. 分三层

```
┌─ UI 层 ────────────────────────────────────┐
│  tab 条、地址栏、原生 UI 卡片、状态栏       │  纯 REST 消费者
│  数据来自 /api/tabs、/api/pending           │  **谁都能重写,也本来就该重写**
├─ 画面层 ───────────────────────────────────┤
│  <img> 或 <canvas>,把解出来的图贴上去      │  解码是浏览器自带的
├─ 协议层 ───────────────────────────────────┤
│  拆头 / 丢残帧 / ack / 心跳 /               │  **只有这一层别人写不了**
│  输入归一化 / IME / 光标 / 尺寸             │
└─────────────────────────────────────────────┘
```

**这个分层就是打包边界**(§8):只有协议层该被发出去,上面两层是上层产品的事。

## 4. 协议层:四条规则

### 4.1 收到帧立刻回执,带帧号,不搭车

```jsonc
{"type": "ack", "frameId": 41}
```

**回执同时是 RTT 探针,而 RTT 是自适应降质的唯一输入。**
一旦把它搭在输入消息上,发出时刻就被输入的批量节奏绑住了 ——
测出来的"RTT"里混着客户端自己的排队时间,不是网络往返。

`frameId` 必须带。服务端**按号查表**算 RTT,对不上就跳过、不污染窗口:
客户端漏回一个(比如那帧解码失败)只是少一个样本;
而"弹最旧的那个时间戳"会**永久错位**,之后每个 RTT 都算成上一帧的,且不会自愈。

### 4.2 三秒补一个回执

推模型下**回执断了就是永久卡死**:客户端等不到帧 → 不回执 → 服务端额度耗尽 → 更没有帧。

```
每收到一帧 → 重置 3 秒定时器
3 秒没帧   → 无条件补一个(带手上最新的 frameId)
```

它和"静止页面不产帧"不冲突 —— 静止时服务端本来就没帧要发,补一个只是把额度还回去。
**代价是每 3 秒几十字节,买的是自愈。**

### 4.3 输入批量,回执不批量

| | 节奏 |
| --- | --- |
| `mousemove` / `wheel` | 攒 25ms 一批,**同批里只留最后一个 mousemove** |
| `mousedown` / `mouseup` / `key` / `text` | **立即发**,不进批 |
| 回执 | **立即发**,永远不进批(4.1) |

按下抬起不能等:25ms 在点击上感觉得到,而且 `mousedown` 和 `mouseup` 之间
插进 25ms 会让某些页面判成长按。

### 4.4 上行不做 RPC

输入是 fire-and-forget。**所有要响应的事情**(开 tab、导航、观测、回填对话框)
**走 REST** —— 那儿本来就有请求-响应、状态码、错误信封。

> 在 WS 上再造一套请求-响应,等于把 `/api/` 那一整套重新发明一遍。
> 线画在:**WS 只走"高频、单向、不要回执"的东西** —— 帧、输入、回执、光标。

## 5. 背压:客户端的义务是"必须回执"

服务端那一侧是额度制:每条连接**各自一份额度和缓冲**,没额度时新帧进缓冲,
**缓冲满了留最新丢最旧**(直播画面里过期帧没有价值,留旧的只会让延迟越积越大)。

所以慢的那个只是**自己掉帧**,不拖累别人。

客户端在这件事上只有一条义务:**收到就回执**。不回执的客户端会自己卡住 ——
这是设计好的,不是故障。而 4.2 那个心跳保证"卡住"永远是暂时的。

## 6. 画面层:两种像素来源,一个接口

两条腿([c](c-pixels.md))在客户端这一侧的形状:

| | screencast | xpra |
| --- | --- | --- |
| 收到什么 | 28 字节头 + 整屏图片 | 8 字节头 + rencodeplus 包 |
| 怎么解 | `Blob` → `<img>` | `createImageBitmap` / 自搬 |
| 画在哪 | `<img>` | `<canvas>` |
| **解码器** | **浏览器自带** | **浏览器自带** |
| 客户端写的是 | 拆头 + 换 `src` | 拆包 + 按区域调度 |

**共同点比差别重要:两边都没有自己写编解码器。** 图片交给
`createImageBitmap`,视频(如果哪天要)交给 WebCodecs。客户端做的是**调度** ——
按什么顺序画、哪块画到哪、什么时候回执。

一个具体的坑:**解码是异步的,所以画必须串起来**。并发画会让后来的帧压在
前面的上,滚动时表现为画面撕成两半。

于是接口收敛成三件事:

```js
view.attach(element)         // <img> 或 <canvas>,由哪条腿决定
view.on("size", (w, h) => …) // 画面尺寸变了
view.on("cursor", (s) => …)  // 光标形状(服务端已过白名单)
```

**换一条腿,上面的 UI 层一行不用改。**

## 7. IME 和光标为什么必须在客户端

这两件事解释了"为什么一定要有一个客户端",而不是"随便贴个 `<img>` 就行"。

**IME 是这条路相对 VNC 的净胜。** 组字全在本地:候选词框是本地 UI、零延迟,
`compositionend` 之后才把最终文本发出去。**组字期间一个按键都不发** ——
发了远端会收到一串乱码般的字母。这件事只能在客户端做,因为组字本来就发生在
用户自己的浏览器里。

**光标必须由客户端落地。** 服务端把形状下发过来(已经过白名单),
客户端写进 `style.cursor`。没有这一步,画面上一切都是箭头,人分不清哪里能点。

## 8. UI 层:内置那个页面不是"界面"

我们自带一个观看页,和 ttyd 自带一个前端是同一个道理。**它不是界面**:
画面 + 一条 tab 条 + 一个地址栏 + 几张原生 UI 卡片,
**没有会话列表、没有登录页、没有设置面板**。

它存在的唯一理由是**打开那个地址,链路通没通一眼看出来**。

它用的接口和外面的人能用的**完全一样**:`/api/tabs` 拿 tab 表、
`/api/pending` 拿挡着页面的东西。**没有私货** —— 这一条是自检:
一旦内置页面用上了没公开的东西,那个"上层要自己画就自己画"的承诺就空了。

## 9. 该发出去的是哪一层

```
@webmuxd/client   ← 只包协议层
```

三条自律:

**① 内置页面必须是它的第一个用户。** 不是"顺便也用一下" ——
如果内置页面走的是另一条实现,这个库会腐烂,而且腐烂的时候没人发现。

**② 零依赖、单文件 ESM。** 要能被 `<script type=module>` 直接引,
也要能进 npm;严格 CSP 的环境里也得能跑。

**③ 版本跟着格式走,不跟着 webmuxd 走。** 帧头或上行消息集合变了才升版本;
加一个 REST 端点和它无关。

**现状是一半**:xpra 那条腿的协议客户端已经是独立模块了
(`static/xpra.js` + `rencode.js`,去掉注释三百来行),
而 screencast 那条**还埋在内置页面里** —— 外面的人拿不到,只能自己重写。
