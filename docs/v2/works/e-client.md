# e · 观看端的客户端

**一句话**:这个位置在 ttyd 侧由 xterm.js 承担,在这里**没有现成实现**。
它要做的不是渲染 —— 渲染由浏览器提供 —— 而是**协议**:拆解帧头、丢弃过期帧、
回执、心跳、输入归一化、IME、光标。它分为三层,**只有最底层无法由外部实现**。

## 1. 它要做什么

| | ttyd 的客户端 | 我们的 |
| --- | --- | --- |
| 解 VT 状态机、维护屏幕缓冲、画字形 | ✔ 全部工作量 | — |
| 拆定长头、按 `targetId` 丢残帧 | — | ✔ |
| 回执 + 心跳(丢一帧就永久卡死) | — | ✔ |
| 输入归一化、批量、IME、粘贴 | 部分 | ✔ |
| 光标形状同步 | — | ✔ |
| 把图贴上去 | — | 一行 |
| **规模** | **几万行** | **几百行** |

**难点的位置发生了转移**:终端侧的难点是渲染,这一侧的难点是协议。

## 2. 为什么没有现成的

xterm.js 得以存在,是因为它实现的是一个**数十年未变的公开标准**(VT100),
因此值得投入形成一个通用库。

这里的线上格式是自定义的 —— 28 字节定长头、`frameId` 与 `targetId` 的语义、
回执的时机规则 —— **不存在第二个实现,也不会自发出现**。
原因不是缺少调研,而是该格式尚无外部使用者。

**推论:该组件必须自行实现,且实现后应可供外部直接使用。**
否则每一个自建界面的使用者都需重写协议层,而这一层的约束
(回执时机、过期帧识别)均不体现在接口表面。

## 3. 分三层

```
┌─ UI 层 ────────────────────────────────────┐
│  tab 条、地址栏、原生 UI 卡片、状态栏       │  纯 REST 消费者
│  数据来自 /api/tabs、/api/pending           │  **可由外部重写,本就应当重写**
├─ 画面层 ───────────────────────────────────┤
│  <img> 或 <canvas>,把解出来的图贴上去      │  解码是浏览器自带的
├─ 协议层 ───────────────────────────────────┤
│  拆头 / 丢残帧 / ack / 心跳 /               │  **只有这一层别人写不了**
│  输入归一化 / IME / 光标 / 尺寸             │
└─────────────────────────────────────────────┘
```

**该分层即为打包边界**(§9):仅协议层对外发布,上面两层归上层产品负责。

## 4. 协议层:四条规则

### 4.1 收到帧立刻回执,带帧号,不搭车

```jsonc
{"type": "ack", "frameId": 41}
```

**回执同时充当 RTT 探针,而 RTT 是自适应降质的唯一输入。**
若将其附加在输入消息上,发出时刻即被输入的批量节奏约束 ——
所测得的 RTT 中混入了客户端自身的排队时间,不再是网络往返时延。

`frameId` 必须携带。服务端**按编号查表**计算 RTT,编号不匹配时跳过,不计入窗口:
客户端漏发一个(例如该帧解码失败)仅损失一个样本;
而「取出最早的时间戳」将导致**永久错位**,此后每个 RTT 均对应上一帧,且无法自行恢复。

### 4.2 三秒补一个回执

在推送模型下**回执中断即导致永久停滞**:客户端收不到帧 → 不发回执 → 服务端额度耗尽 → 更无帧可发。

```
每收到一帧 → 重置 3 秒定时器
3 秒没帧   → 无条件补一个(带手上最新的 frameId)
```

它与「静止页面不产帧」不冲突 —— 静止时服务端本就无帧可发,补发回执只是归还额度。
**成本为每 3 秒数十字节,换取的是自恢复能力。**

### 4.3 输入批量,回执不批量

| | 节奏 |
| --- | --- |
| `mousemove` / `wheel` | 攒 25ms 一批,**同批里只留最后一个 mousemove** |
| `mousedown` / `mouseup` / `key` / `text` | **立即发**,不进批 |
| 回执 | **立即发**,永远不进批(4.1) |

按下与抬起不可延迟:25ms 在点击上可被感知,且 `mousedown` 与 `mouseup` 之间
插入 25ms 会使部分页面判定为长按。

### 4.4 上行不做 RPC

输入为单向投递,不需要响应。**所有需要响应的操作**(打开 tab、导航、观测、回填对话框)
**经 REST** —— 该通道本身即具备请求-响应、状态码与错误结构。

> 在 WS 上另建一套请求-响应,等同于重新实现 `/api/` 的全部能力。
> 边界为:**WS 仅承载高频、单向、无需响应的数据** —— 帧、输入、回执、光标。

## 5. 背压:客户端的义务是「必须回执」

服务端一侧采用额度制:每条连接**各自持有额度与缓冲**,额度耗尽时新帧进入缓冲,
**缓冲满时保留最新、丢弃最早**(实时画面中过期帧没有价值,保留旧帧只会累积延迟)。

因此较慢的连接**仅影响自身丢帧**,不影响其他连接。

客户端在此只有一项义务:**收到即回执**(两条来源各自的回执机制见 §6.5)。不回执的客户端会自行停滞 ——
这是设计结果,不是故障;而 §4.2 的心跳保证该停滞始终是暂时的。

## 6. 通道模型

客户端不是"一条连接加一个可选的第二条",而是**若干条并列的通道**。
这一节定义通道是什么、谁提供什么、以及冲突时如何仲裁。

### 6.1 通道 = 一个上游系统的连接

```
客户端
  ├── WS /channel/cdp     ← sessiond ↔ Chromium 那一侧派生的数据
  ├── WS /channel/xpra    ← sessiond ↔ xpra 那一侧派生的数据
  └── (以后并列的第三条)
```

> **`/channel/…` 是设计名。** 当前实现中这两条分别是 `/api/view` 和 `/xpra` ——
> 前者的名字来自「只有一条画面连接」的时期,后者没有体现它是并列的一条。
> **路径前缀本身就是这个模型的一部分**:看到 `/channel/x` 就知道它是一条通道,
> 遵守 §6.2 的能力表和 §6.6 的三个问题。改名列在 §10。

**划分依据是上游是谁,不是数据是什么。** 这一点决定了后面所有的性质:
一条通道断开时,失去的是"某个上游能提供的全部东西",
而不是"某一类数据的一部分" —— 故障边界与系统边界重合。

### 6.2 每条通道能提供什么

| | 帧 | 光标 | 输入 | 尺寸 / 权限 / tab |
| --- | --- | --- | --- | --- |
| **`/channel/cdp`** | ✔ `Page.startScreencast` | ✔ 页面探针 | **✔ 且仅此一条** | ✔ |
| **`/channel/xpra`** | ✔ damage 区域 | ✔ X 光标(实测可用) | ✗ | ✗ |

两条通道**同时具备帧与光标的提供能力**,这正是需要仲裁规则的原因(§6.3)。

**`输入` 那一列不是能力,是收口。** 它只能走 `/channel/cdp`,且不可配置:

> 输入的边界价值来自"观看者能表达的意图被限制在 `Input` 域那四个命令里"
> ([b §1](b-input.md#1-收口在哪))。一旦某条通道也能承载输入,
> 该边界就退化为"在各通道上分别过滤",而**过滤是黑名单模型**。
>
> 因此这是一条结构约束,不是默认值:**新增通道一律不得承载输入。**

同理,尺寸、权限、tab 与原生 UI 只走 `/channel/cdp` —— 它们本就是 sessiond 的状态,
不是任何上游的产物。

### 6.3 仲裁:每种能力在任一时刻只有一个提供者

两条通道都能给帧,但**客户端不消费两份**。规则是一张固定的优先级表,
不是运行时协商:

| 能力 | 优先级 | 理由 |
| --- | --- | --- |
| 帧 | `/channel/xpra` > `/channel/cdp` | 按区域编码优于整屏重发([c §4.1](c-pixels.md#41-它强在哪以及它的劣势区)) |
| 光标 | `/channel/cdp` > `/channel/xpra` | 关键字可过白名单;图像不能。且两条来源行为需一致([c §5.1](c-pixels.md#51-xpra-还提供了什么以及为什么不取)) |

两条值得记住:

**① 优先级按能力定,不按通道定。** 帧走 xpra、光标走 cdp —— 这不是矛盾,
而是每种数据各自选最合适的来源。把它简化成"启用 xpra 就全用 xpra"会丢掉白名单。

**② 未被选中的提供者不消费。** `/channel/xpra` 启用时,`/channel/cdp` 上不请求帧
(不发 `Page.startScreencast`);`/channel/xpra` 的 cursor 包被丢弃。
**同一份数据不解码两遍,也不产生两份状态。**

### 6.4 开关的粒度是通道,不是能力

```
--transport xpra          启用 /xpra;帧由它提供
--transport screencast    不启用 /xpra;帧由 /cdp 提供
```

**开关只作用于"这条通道开不开"**,不提供"帧用 A、光标用 B"这类逐能力配置。
理由是组合数:三条通道、三种能力,逐项可配就有 27 种状态,
而其中绝大多数从未被验证过。**优先级表是设计的一部分,不是用户的选项。**

`/channel/cdp` 不可关闭 —— 输入与控制在它上面。

### 6.5 一条通道断开时

故障边界与系统边界重合,因此后果可以直接读出来:

| 断开的是 | 失去什么 | 判定 |
| --- | --- | --- |
| `/channel/cdp` | 输入、光标、尺寸、tab —— **会话不可操作** | **判为不可用**,画面置灰并重连 |
| `/channel/xpra` | 帧 | 画面停止更新并重连;输入仍可送达 |

`/channel/cdp` 之所以是权威,原因是:**只有像素而不能操作,不构成一个可用的会话** ——
此时画面还在更新反而具有误导性。

> 一个可选的降级路径:`/channel/xpra` 断开时回退到 `/channel/cdp` 提供帧。
> **当前不做** —— 静默改变画面来源会使人误判当前画质
> ([c §10](c-pixels.md#10-默认走哪条))。若将来要做,必须显式告知。

### 6.6 这个模型是用来想清楚的,不是插件框架

**加第三条通道要写代码,不是注册一个插件。** §6.2 和 §6.3 那两张表是硬编码的,
将来大概也还是硬编码 —— 这里不打算做能力协商或运行时注册,
那是为一个还不存在的需求付成本。

这个模型买到的是**写客户端时的清晰度**:面对一条新通道,只需要回答三个问题,
而不必重新考虑整个客户端。

1. **它是哪个上游的连接?** —— 决定它的故障边界(§6.1)
2. **它能提供哪些能力?** —— 在 §6.2 那张表里加一行
3. **在每种能力上它排第几?** —— 在 §6.3 那张优先级表里加一行

以及一条不可协商的约束:**它不承载输入。**

回答完这三个问题之后,客户端的分层(§3)、协议层的四条规则(§4)、
UI 层的接口(§8)全部不用动 —— **这才是这个模型的价值所在。**

### 6.7 通道内部:画面这条的共性

无论帧由哪条通道提供,客户端做的都是同一件事:

| | `/channel/cdp` | `/channel/xpra` |
| --- | --- | --- |
| 收到什么 | 28 字节头 + 整屏图片 | 8 字节头 + rencodeplus 包 |
| 如何解码 | `Blob` → `<img>` | `createImageBitmap` / 画布内位移 |
| 绘制目标 | `<img>` | `<canvas>` |
| **解码器** | **浏览器提供** | **浏览器提供** |
| 客户端实现的部分 | 拆头、替换 `src` | 拆包、按区域调度绘制 |

**两条来源均未自行实现编解码器。** 客户端负责的是**调度** ——
绘制顺序、区域映射,以及回执时机。

一处具体约束:**解码为异步,因此绘制必须串行**。并发绘制会使后到的帧覆盖先到的帧,
在滚动时表现为画面撕裂。

回执也随通道走:`/channel/cdp` 上是 `{"type":"ack","frameId":N}`(§4.1),
`/channel/xpra` 上是 `damage-sequence`。**任一时刻只有被选中的那条在回执。**

## 7. IME:客户端存在的另一个理由

§6 说明了画面与光标为何需要一个客户端;IME 是另一条,而且它是这条路线相对
VNC 的净收益。

组字全部在本地完成:候选词框为本地 UI、无延迟,`compositionend` 之后才提交
最终文本。**组字期间不发送任何按键** —— 否则远端将收到一串无意义的字母。

该处理只能在客户端完成,因为**组字本就发生在用户自身的浏览器中**。
把它挪到服务端,就回到了 VNC 的处境:要么在远端安装完整输入法并把候选词框
作为像素回传,要么两侧状态错位。

## 8. UI 层:内置那个页面不是"界面"

内置观看页与 ttyd 自带前端同理。**它不是产品界面**:
画面、一条 tab 条、一个地址栏,以及若干原生 UI 卡片,
**没有会话列表、登录页或设置面板**。

它存在的唯一理由是**验证链路**:打开该地址即可确认整条链路是否连通。

它使用的接口与外部可用接口**完全一致**:`/api/tabs` 获取 tab 表、
`/api/pending` 获取阻塞页面的项。**不使用未公开接口** —— 这是一项自检:
一旦内置页依赖了未公开能力,「上层可自行实现界面」这一承诺即失效。

## 9. 该发出去的是哪一层

```
@webmuxd/client   ← 只包协议层
```

三条自律:

**① 内置页必须是它的第一个使用者。** 而非附带使用 ——
若内置页采用另一套实现,该库将逐渐失效,且失效过程不会被察觉。

**② 零依赖、单文件 ESM。** 需支持 `<script type=module>` 直接引入,
同时可发布至 npm;在严格 CSP 环境下亦须可用。

**③ 版本跟随格式,而非跟随 webmuxd。** 仅当帧头或上行消息集合变更时升版本;
新增 REST 端点与其无关。

**当前完成一半**:xpra 来源的协议客户端已是独立模块
(`static/xpra.js` + `rencode.js`,去除注释约三百行),
而 screencast 来源**仍位于内置页内** —— 外部无法获取,只能自行重写。
