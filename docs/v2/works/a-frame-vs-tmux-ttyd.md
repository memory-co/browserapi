# a · 对标 tmux + ttyd

**一句话**:webmuxd 想成为浏览器的 tmux + ttyd。tmux 那一半几乎是照搬的,
**ttyd 那一半搬不过来** —— 因为终端的画面就是它的语义,而浏览器的不是。
这一篇讲的就是这个差别,以及它逼出来的几条 WebSocket。

> 这是新一轮设计稿的第一篇。它**不解决任何具体问题**,只负责把技术框架讲清楚:
> 有哪几条链路、各走什么协议、为什么不能合成一条。
> 具体的取舍在后面各篇,这里只给指路。

## 1. 两半,一半照搬一半重写

| tmux 的概念 | webmuxd | 搬得动吗 |
| --- | --- | --- |
| session:活得比连接久 | 一个浏览器 + 一个 sessiond | **照搬** |
| window / pane | tab | **照搬**(tab 表就是浏览器那张表) |
| `new -A -s` 幂等 | `session(id=…)` 幂等 | **照搬** |
| attach / detach | 打开或关掉那个网页 | **照搬** |
| scrollback | 一个 `log.jsonl` | **照搬** |
| **ttyd:把终端搬到浏览器里** | **把浏览器搬到浏览器里** | **搬不动,见 §2** |

前五行是这个项目最省心的部分 —— **"门面短命,屋子长命"这个模型在浏览器上原样成立**。
麻烦全在最后一行。

## 2. ttyd 只需要一条 WebSocket,我们需要三条

ttyd 的线上格式极简:**一个字节的 opcode + 载荷**。

```
'0' + data     服务端 → 客户端:终端输出
'0' + data     客户端 → 服务端:键盘输入
'1' + json     改窗口大小
```

一个字节就够,是因为**终端的输出流里已经什么都有了**。
`\x1b[2J` 是清屏,`\x1b[10;5H` 是把光标挪到第 10 行第 5 列 ——
画面、光标、标题、响铃**全都编码在同一条字节流里**,而且是标准化的
(VT100 那套几十年没变)。所以客户端只要有一个 xterm.js 把这些语义
重新渲染成像素就行。

**浏览器没有这样一条流。** 它的画面是像素(几百 KB 一帧),它的语义在 DOM 里
(一棵树),两者是完全不同的东西,不可能塞进同一个字节流。于是那一条流
必须拆开:

```
      ┌── WS /api/view   画面下行 + 输入上行  ← 人在看和操作
人 ───┼── WS /api/events 事件下行            ← 人和程序都在听
      └── (HTTP /api/…)  动作、tab、日志、观测

  webmuxd ──── WS(CDP)──── Chromium          ← 这条是我们**消费**的
```

**这三条(加一条我们消费的)就是整个技术框架。** 剩下的都是细节。

## 3. 每条走什么协议

| | 方向 | 协议 | 为什么是这个形状 |
| --- | --- | --- | --- |
| **`WS /api/view`** | 下行像素 | **28 字节定长头 + 图片裸字节** | 头里有 castSessionId / frameId / targetId。定长是为了**零解析**,`targetId` 是为了让客户端丢掉切 tab 前的残帧 |
| | 上行输入 | **JSON** | 一秒几十条鼠标移动,但每条都小;可读性比几个字节的节省值钱 |
| | 上行 ack | **JSON,独立发、立即发、带帧号** | 它同时是背压和 RTT 探针 —— 搭车就测不准了 |
| **`WS /api/events`** | 只下行 | **JSON,一行一个事件** | tab 变了、对话框弹了、下载完了。**给程序听的**,和画面无关 |
| **`WS`(CDP)** | 双向 | **JSON-RPC** | 不是我们定的,是 Chromium 定的。我们是它的客户端 |

三条我们提供的 WS 里,**只有第一条是二进制的**,而且只有它的下行是二进制 ——
因为只有像素这一种数据大到值得为它定一个定长头。

> 还有一条 `WS /xpra`,只在换了像素来源的时候存在,走的是 xpra 自己的协议
> (8 字节头 + rencodeplus)。**它只是第一条那个"下行像素"的另一种实现** ——
> 输入、事件、动作一条都不走它。详见后面专门那篇。

### 3.1 为什么不合并成一条

最容易想到的简化是"都塞进 `/api/view`"。不做,理由是**这三条的读者不一样**:

| | 谁在听 | 断了会怎样 |
| --- | --- | --- |
| `/api/view` | 一个正在看的人 | 画面停住。**程序不受影响** |
| `/api/events` | 程序(可能同时好几个) | 程序瞎了。**人还在正常操作** |
| CDP | 我们自己 | 整个 session 完了 |

合并之后,一个观看者关掉网页就会牵动程序那一侧 —— 而这正是
"门面短命,屋子长命"要避免的事。

## 4. 光标:终端白给的,浏览器得自己造

这一节讲一个具体例子,因为它最能说明 §2 那个差别有多具体。

**终端里光标是数据。** `\x1b[?25l` 藏光标,`\x1b[10;5H` 挪光标 ——
它在流里,xterm.js 照着画就行,ttyd 一行代码都不用写。

**浏览器里光标不是数据,而且它连像素都不是**:

- **CDP 里没有"光标变了"这个事件** —— 光标形状是纯渲染层的东西
- **截出来的帧里不含光标** —— 合成器不画系统光标

于是画面上一切都是箭头,**人分不清哪里能点**。链接不变小手、输入框不变 I 型、
拖拽把手看不出来 —— 这个损失比听起来严重得多。

我们的做法是往页面注入一个探针:

```
页面里:elementFromPoint(x, y) → getComputedStyle().cursor
        值变了才上报,没变不发     ← 基本不占带宽
   ↓    (走 CDP 的 binding 回来)
服务端:过一遍白名单
   ↓    (走 /api/view 的 JSON 上行通道下发)
客户端:screen.style.cursor = 那个值
```

三处值得记住的:

**① 命中测试是必须的。** `cursor: auto` 的语义是"文字上 I 型、别处箭头",
光读计算样式区分不出来 —— 两种情况读出来都是 `auto`。

**② 白名单不是洁癖。** CSS 的 `cursor` 支持 `url(...)` 自定义光标。
远端页面是不可信的,原样透传等于**让被隔离的页面指使观看者的浏览器去拉任意 URL**
—— 隔离当场破掉。所以只放行 CSS 规范里那些关键字,其余降级成 `default`。

**③ 探针改变了页面环境,这件事要承认。** 我们往页面里注入了东西,
页面能看见它。所以复用同一个 binding,**不为光标再开第二个** ——
既然已经承认了,就更没理由多加一个。

> **这一节是整篇的缩影。** 终端把画面、光标、标题、响铃打包在一条标准流里;
> 浏览器把它们散在像素、DOM、CDP 事件和什么都没有的地方。
> webmuxd 的工作量,大半来自把这些一件件捡回来。
> [六类原生 UI](06-no-desktop.md) 是同一件事的更大号版本。

## 5. 所以 webmuxd 到底是什么

```
tmux 那一半    session / tab / 幂等 / scrollback        ← 照搬,几乎没有新问题
ttyd 那一半    画面怎么来、输入怎么回、光标怎么办、
               原生 UI 怎么办、只读怎么保证             ← 全是新问题
CDP            这两半共同的地基                          ← 别人定的协议,我们是客户端
```

**"ttyd 那一半是自己写的"** —— 这句话展开就是后面所有篇。
