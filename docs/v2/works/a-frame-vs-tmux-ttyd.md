# a · 对标 tmux + ttyd

**一句话**:webmuxd = 浏览器的 tmux + ttyd。tmux 那一半照搬,ttyd 那一半重写。
两边的线上形状**几乎一样**:一条 WebSocket,一半发控制、一半发载荷。
**唯一的差别是载荷里装的是什么** —— 终端装语义,浏览器装像素。
这一个差别决定了后面所有的设计。

## 1. 两半

| tmux 的概念 | webmuxd | |
| --- | --- | --- |
| session 活得比连接久 | 一个浏览器 + 一个 sessiond | 照搬 |
| window / pane | tab | 照搬 |
| `new -A -s` 幂等 | `session(id=…)` 幂等 | 照搬 |
| attach / detach | 打开或关掉那个网页 | 照搬 |
| scrollback | 一个 `log.jsonl` | 照搬 |
| **ttyd:把终端搬进浏览器** | **把浏览器搬进浏览器** | **重写** |

前五行是这个项目最省心的部分:**"门面短命,屋子长命"这个模型在浏览器上原样成立**。
所有的设计问题都在最后一行。

## 2. 一条 WebSocket,两种帧

**两边都是一条连接。** 这一点常被误解成"浏览器方案更复杂所以要多开几条" ——
不是的,形状是一样的。

### 2.1 ttyd 的一帧

```
┌────┬──────────────────────────────┐
│'0' │ \x1b[2J\x1b[H$ ls -la\r\n… │   服务端 → 客户端
└────┴──────────────────────────────┘
  ↑        ↑
opcode   终端输出的字节流

'0' OUTPUT  '1' SET_WINDOW_TITLE  '2' SET_PREFERENCES
```

上行同理:`'0'` 是键盘输入,`'1'` 是改窗口大小,`'{'` 开头的是 JSON。
**ttyd 在载荷的第一个字节里自己造了一个 opcode**,用它区分"这是控制"还是"这是数据"。

### 2.2 webmuxd 的一帧

```
binary 帧  ┌──────────────28 字节──────────────┬──────────────┐
           │ castId │ frameId │ targetId(16B) │ JPEG 裸字节  │
           └────────────────────────────────────┴──────────────┘

text 帧    {"type":"cast","w":1024,"h":768,"quality":80}
           {"type":"cursor","cursor":"pointer"}
```

上行同理:text 帧发输入和 ack(`{"type":"mouse",…}` / `{"type":"ack","frameId":N}`)。

**我们没有自造 opcode —— 用的是 WebSocket 本来就有的那一位。**
WS 协议自己就区分 text(0x1)和 binary(0x2),ttyd 那个字节是在重复造它。
差别不大,但方向是对的:**控制走 text、载荷走 binary,分层由传输层保证,不由约定保证。**

### 2.3 相似的和不同的

| | ttyd | webmuxd |
| --- | --- | --- |
| 几条连接 | 一条 | 一条 |
| 控制和载荷怎么分 | 载荷里的第一个字节 | **WS 自己的 text / binary** |
| 方向 | 下行推、上行输入 | 一样 |
| 有没有"改尺寸" | `'1' + json` | `{"type":"resize"}` |
| **载荷是什么** | **终端输出的字节流** | **一张完整的图片** |

前四行几乎逐条对应。**全部的设计差异来自最后一行。**

> 另有两条 WS 不在这个对照里:`/api/events` 是给程序听的事件流(和画面无关),
> 以及换像素来源时才存在的那条(后面专门一篇)。它们都不改变上面这个骨架。

## 3. 载荷是语义,还是像素

这是**唯一**的差别,但它是一个会级联的差别。

`\x1b[10;5H` 这七个字节的意思是"把光标挪到第 10 行第 5 列"。
它不是画面 —— 它是**让客户端去画**的指令。终端的输出流从头到尾都是这样的东西:
清屏、变色、移动光标、响铃、改标题,全都在同一条流里,而且是 VT100 那套
几十年没变的标准。

浏览器的画面是像素。**没有一条流能同时表达"这个按钮是蓝色的"和"这里可以点"** ——
前者在像素里,后者在 DOM 里。

于是:

| | 终端 | 浏览器 |
| --- | --- | --- |
| **谁在渲染** | 客户端(xterm.js 解 VT 序列画字形) | **远端**。客户端只是把图贴上去 |
| **客户端要多重** | 几万行的终端模拟器 | **一个 `<img>`** |
| 有没有现成的 | `npm i xterm` | 没有 —— 格式是自造的 |
| **一帧多大** | 几十字节(一行输出) | 几十 KB(整屏 JPEG) |
| 静止时的流量 | 0 | **0**(不变就不产帧) |
| 能不能重放 | 存下字节流重放就行 | 要存图 |
| **光标在哪** | **在流里** | **哪儿都不在** —— §4 |
| **语义在哪** | **就是流本身** | 在 DOM 里,要另外去取 |

两条值得单独说:

**① 客户端从"几万行"塌成了 `<img>`。** 这是像素方案白拿的好处 ——
浏览器天生会解 JPEG。代价是每帧几十 KB 而不是几十字节。

**② "语义在 DOM 里"是这个项目一半工作量的来源。** 终端的流本身就是语义,
所以 ttyd 不需要"观测"这个概念;而浏览器要让程序知道页面上有什么,
必须另开一条路去 DOM 里取 —— 那就是 `observe` 和 `act` 存在的理由。

## 4. 光标:那个差别最短的证明

终端里光标是流的一部分,`\x1b[?25l` 藏它、`\x1b[10;5H` 挪它,ttyd 一行代码不用写。

浏览器里光标**既不在像素里,也不在协议里**:

- 合成器不把系统光标画进帧
- CDP 没有"光标形状变了"这类事件

结果是画面上一切都是箭头:链接不变小手、输入框不变 I 型、拖拽把手看不出来。
**人分不清哪里能点。**

所以它必须走控制通道,和画面并行:

```
远端页面     命中测试 → 计算样式里的 cursor,变了才报
   ↓
服务端       过白名单
   ↓         text 帧 {"type":"cursor","cursor":"pointer"}
客户端       style.cursor = 那个值
```

两条设计约束:

**命中测试不能省。** `cursor: auto` 的语义是"文字上 I 型、别处箭头",
光读计算样式两种情况都是 `auto` —— 不做命中测试就区分不出来。

**值必须过白名单。** CSS 的 `cursor` 接受 `url(...)`。远端页面不可信,
原样透传等于**让被隔离的页面指使观看者的浏览器去拉任意 URL** ——
隔离在这一处就破了。只放行 CSS 规范里的关键字,其余降级成 `default`。

> 光标只是最小的一个例子。同一个形状会以更大的规模再出现:
> 对话框、文件选择、下载、权限 —— 终端里不存在的东西,浏览器里全都要
> 一件件捡回来([06](06-no-desktop.md))。

## 5. 这条差别往下决定了什么

```
载荷是像素,不是语义
   ├─ 画面必须由我们产,而且产出来就是最终形态   → 01 · 02 · 09
   ├─ 客户端不渲染,只贴图                       → 一个 <img> 就够
   ├─ 输入必须由我们翻译回去                     → 03(而这带来了安全收口)
   ├─ 语义要另开一条路去 DOM 里取                → observe / act
   └─ 终端白给的那些东西要一件件重建             → 04 · 05 · 06
```

**这五条就是 v2 的全部工作量。** 后面每一篇都是其中一条的展开。
