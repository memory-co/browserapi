# g · 浏览器自己的那些 UI,得一件件接管

**一句话**:对话框、下载、文件选择、权限、认证 —— 这些由浏览器自己绘制的 UI,
在画面里**要么不存在,要么存在但点不动**。必须逐类用 CDP 拦下来、抛事件、
由观看端绘制、再回填。**这是这条路线上唯一无法回避的工作量。**

## 1. 为什么必须接管

浏览器的 UI 分两层:**页面内容**由渲染进程绘制,**浏览器自身的 UI**
(tab 条、地址栏、对话框、下载气泡)由浏览器进程绘制。
两条像素来源对第二层的处理不同,但结果都要求我们接管:

| | 浏览器自身的 UI 在画面里 | 后果 |
| --- | --- | --- |
| `/channel/cdp` | **不存在** —— 截的是渲染结果 | 页面停住,而使用者看不出原因 |
| `/channel/xpra` | **存在,但点不动** —— 见 §5 | 看得见一个无法操作的对话框 |

第一列容易理解:一个 `confirm()` 弹出后,页面的 JavaScript **同步阻塞**,
而画面上什么都没变。不拦截,现象就是"页面卡住了",没有任何线索。

第二列是这条路线上更强的约束,§5 展开。

> 这一层与「有没有桌面」无关。即使把整个桌面搬过来,
> 文件选择框仍然没用 —— 那个虚拟显示里**没有文件管理器**。

## 2. 五类,逐条

| 原生 UI | 怎么拦 | 怎么回填 |
| --- | --- | --- |
| **JS 对话框**<br>`alert` / `confirm` / `prompt` / `beforeunload` | `Page.javascriptDialogOpening` | `Page.handleJavaScriptDialog {accept, promptText}` |
| **文件选择框** | `Page.setInterceptFileChooserDialog` → `Page.fileChooserOpened` | `DOM.setFileInputFiles` |
| **下载** | `Browser.setDownloadBehavior` + `downloadWillBegin` / `downloadProgress` | 文件落到 session 目录,经 API 取回 |
| **权限请求**<br>定位 / 通知 / 摄像头 / 剪贴板 | 不弹框,**默认拒绝** | `Browser.grantPermissions` / `resetPermissions` 显式授予 |
| **HTTP Basic 认证** | `Fetch.enable {handleAuthRequests}` → `Fetch.authRequired` | `Fetch.continueWithAuth`。**默认不开**,见 §2.1 |

每一类都是**一个事件 + 一个端点**,不改变架构。

(PDF 与浏览器内置查看器不单列:无头浏览器没有内置查看器,按下载处理;
要取内容用 `Page.printToPDF`。)

### 2.1 认证那条默认不开

其余四类都是常开拦截,认证不是。原因是拦截手段的代价不同:

拦截认证的唯一途径是 `Fetch.enable`,而一旦启用,**该 target 的每一个请求
都要经过我们再放行** —— 一个页面几十上百个请求,全部多绕一趟。

关键在于**不拦的后果也不同**:

| | 不拦会怎样 |
| --- | --- |
| 对话框 / 文件选择 | **页面静止**,使用者看不出原因 —— 彻底卡死 |
| Basic 认证 | 401 照常渲染成服务器返回的页面 —— **看得见的失败** |

所以它改为**设置凭证时才开启**(`POST /api/auth`),清除时关闭把开销退回。
真实流程本就是这个顺序:先撞上 401,再设凭证,再重进。

### 2.2 三条共同约束

**① 不替使用者决定。** `alert` 不自动确认、文件选择不自动填入、
权限不自动授予,一律抛出事件等待回填 —— 这些**本就是人的决定**。
代为决定会在「以为点了确定」与「实际没点」之间产生看不见的分歧。

**② 超时是显式的,且一律偏向「取消」。** 拦下来无人回填,页面会永远等待。
每类都有默认超时与默认动作:对话框 dismiss(`confirm` 视为未确认、
`beforeunload` 留在原页)、文件选择填入空列表。**超时写入日志,不静默。**

**③ 观看端必须能绘制它们。** 内置观看页不含产品决策
([e §8](e-client.md#8-ui-层内置那个页面不是界面)),但这五类是**协议的一部分**,
不是产品功能 —— 不绘制,使用者就会遇到「点了没反应」。

## 3. 日志里必须看得见

这几类事件是**页面停住的唯一解释**,因此必须进入操作日志:

```jsonc
{"kind":"dialog","subtype":"confirm","text":"确定要删除吗?","state":"pending"}
{"kind":"dialog","subtype":"confirm","action":"accept","by":"user:alice"}
{"kind":"download","file":"报表.xlsx","bytes":48213,"state":"done"}
{"kind":"permission","name":"geolocation","action":"deny","by":"default"}
```

没有它们,「程序跑着跑着停住了」的现象只剩下"观测返回的页面一直没变",
无法区分是网络慢还是有一个 `confirm` 挡着。

## 4. 另一类:原本由桌面承担的行为

不是对话框,但同样是「桌面负责的事」:

| | 在这里怎么处理 |
| --- | --- |
| **新窗口 / popup** | 就是一个 tab([f §5](f-tabs.md#5-popup-不是特殊情况)) |
| **全屏**(视频) | 页面内的事,画面尺寸不变,不需要处理 |
| **打印** | `Page.printToPDF`,按下载处理 |
| **拖放文件进页面** | `Input.dispatchDragEvent` + 文件经上传端点 |
| **右键菜单** | 浏览器默认菜单不存在,**由观看端自己绘制** |

右键菜单需要说明:`contextmenu` 事件仍会传给远端页面,
因此自定义右键菜单的网站正常工作;消失的是**浏览器默认**的那个菜单 ——
它本就属于浏览器 UI,不是页面内容。

## 5. 有头之后:能看见,但点不动

`/channel/xpra` 那条上浏览器是有头的。直觉上会想:这几类原生 UI 是不是就能看见、
能不能让人自己点?

**实测:能看见,但点不动。**

```
Page.enable → 页面执行 alert() → Page.javascriptDialogOpening 抛出
                              → 同时 Chrome 将对话框绘制出来,页面变灰
Input.dispatchMouseEvent(点击 OK) → 没有 javascriptDialogClosed
```

原因是该按钮属于**浏览器进程绘制的 UI**,而 `Input.*` 作用于渲染进程;
加之输入不走 xpra([e §6.2](e-client.md#62-每条通道能提供什么))——
**我们允许的任何输入路径都无法关闭它**,只有 `Page.handleJavaScriptDialog` 可以。

三条推论:

**① 我们绘制的卡片不是可选项,是必需品。** 它的按钮是画面上唯一有效的按钮。
这一整篇的结论未变,但理由从「不画就看不见」变成了**「不画就点不动」** ——
后者更强。

**② 卡片必须是覆盖整个视口的不透明遮罩。** 否则画面上会同时出现两个对话框,
而其中一个无法操作。screencast 那条上无所谓,这条上是硬要求 ——
因此[两条来源采用同一套行为](c-view.md#7-接缝切在哪),遮罩统一为不透明。

**③ 文件选择更明显。** 那个虚拟显示里根本没有文件管理器,
原生选择框即使弹出也无法使用,仍须 `DOM.setFileInputFiles`。

## 6. 优先级

按「不做会不会卡住人」排序:

| | 做什么 | 不做的后果 |
| --- | --- | --- |
| **必须** | JS 对话框 | 任何 `confirm` 都会让页面永久卡住,且看不出原因 |
| **必须** | 下载 | 点击下载后没有任何反应,文件在远端无人知晓 |
| **必须** | 文件选择 | 上传类流程完全无法完成 |
| 应该 | 权限 | 默认拒绝是安全的默认,不做也不会卡住 |
| 应该 | Basic 认证 | 遇到即白屏,但已较少见。**已做,默认不开**(§2.1) |
| 可以晚 | 右键菜单 / 拖放 / 打印 | 存在替代路径 |

前三条是「能否宣布可用」的门槛。
