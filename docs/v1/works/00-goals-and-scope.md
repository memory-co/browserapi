# 00 · 目标与范围

## 1. 问题陈述

现有两类方案都不够用:

**A. headless 自动化库(Playwright / Puppeteer / Selenium)**
- 优点:API 成熟、快、易嵌入。
- 缺点:对 Agent 场景是"黑盒"。任务跑失败时,你拿到的是一段 traceback 和几张零散截图,
  很难回答"它当时看到了什么、为什么点了那个按钮、点完页面变成了什么样"。
- 缺点:没有人机共存通道。遇到验证码 / 二次验证 / 风控弹窗,只能整条任务失败。

**B. kasm/chrome 这类流式桌面容器**
- 优点:天然有 GUI、有真实浏览器指纹、人可以用浏览器直接看和操作。
- 缺点:它是给**人**用的。没有程序化控制面,没有语义化的页面表示,没有动作/事件留痕,
  Agent 只能退化成"截图 + 猜坐标点击",既慢又脆。

**browserapi 要做的是 A ∩ B**:把 B 的可视性与人机共存,接上 A 的程序化控制,
再补上两者都缺的一环——**智能体操作路径的一等公民化**。

## 2. 目标(v1)

| # | 目标 | 验收标准 |
| --- | --- | --- |
| G1 | 基于 `kasm/chrome` 提供可程序化控制的浏览器会话 | 一条命令起容器,SDK 可 `goto/click/type`,同时浏览器画面可在网页里实时看到 |
| G2 | 双模式:Python lib + API service | 同一段业务逻辑,改一行连接方式即可在本地进程内跑或指向远端服务跑,行为一致 |
| G3 | 面向 Agent 的观测层 | 一次 `observe()` 返回「标注截图 + 可交互元素表」,可直接喂给多模态模型,无需调用方自己做 DOM 解析 |
| G4 | **操作路径全程可见** | 任一 run 可 (a) 实时直播 (b) 事后逐步回放并高亮点击位置 (c) 导出结构化轨迹用于审计/评测/训练 |
| G5 | 人机接管 | 人可在 Agent 跑到一半时接管同一个会话完成操作,接管区间在轨迹里明确标注 |
| G6 | 安全隔离 | 会话级容器隔离、出网白名单、凭证不落轨迹、截图可脱敏 |

## 3. 非目标(v1 明确不做)

- **不做 Agent 大脑。** 不内置 LLM 调用、不内置任务规划。browserapi 是"手和眼",决策留给调用方。
  (提供 `run/step` 语义供调用方把决策过程挂上来,见 [04](04-trajectory-model.md)。)
- **不做反检测 / 指纹对抗产品化。** 使用真实 headful Chrome 是副作用,不作为卖点承诺,也不提供绕过风控的专门能力。
- **不做浏览器插件生态托管。** v1 只支持启动时预置扩展,不支持运行时动态装卸。
- **不做移动端 / 非 Chromium 内核。** Firefox、WebKit 不在 v1。
- **不做可视化编排 IDE。** 回放器是只读的取证工具,不是低代码录制回放平台。

## 4. 目标用户与场景

| 场景 | 谁在用 | 对 browserapi 的核心诉求 |
| --- | --- | --- |
| Web Agent 研发 | 算法/应用工程师 | G3 观测层质量、G4 轨迹用于 debug 与 eval |
| 生产化 Agent 任务(RPA 类) | 平台工程 | G2 service 模式、G6 隔离、失败可归因 |
| 人机协同办理 | 业务运营 | G5 接管、G1 实时画面 |
| 合规与审计 | 风控/审计 | G4 结构化轨迹、G6 脱敏、不可否认的操作证据 |
| 数据集构建 | 研究 | G4 轨迹导出为标准格式 |

## 5. 关键术语

| 术语 | 含义 |
| --- | --- |
| **Operator / 操作体** | 一个具备浏览器 + 控制面 + 取证能力的容器实例 |
| **Session(会话)** | 一个长期存在的浏览器上下文(含 profile、cookie、标签页),生命周期通常绑定一个容器 |
| **Run(任务)** | 会话内一次有始有终的逻辑任务,如"预订一张机票"。轨迹的顶层单位 |
| **Step(步)** | Agent 的一次决策周期:观测 → 思考 → 一到多个动作 → 效果 |
| **Action(动作)** | 原子操作,如 `click` / `type` / `scroll`,见 [03](03-action-protocol.md) |
| **Observation(观测)** | 某一时刻页面对 Agent 的可读表示:标注截图 + 元素表 + 文本摘要 |
| **Effect(效果)** | 动作执行后的可观测变化:导航、DOM diff、网络请求、控制台、下载、弹窗 |
| **Trajectory(轨迹)** | 一个 Run 下所有 Step 的完整有序记录,含全部观测与效果 |
| **agentd** | 跑在容器内的控制进程,是 CDP 之上、协议之下的那一层 |
| **Control Plane** | 负责会话编排、鉴权、轨迹存储的服务(service 模式)或进程内模块(lib 模式) |
| **Takeover(接管)** | 把会话控制权从 Agent 切给人(或反向)的显式操作 |

## 6. 成功的样子

一位工程师在周一早上发现:昨晚的 200 个自动化任务里有 7 个失败了。
他打开轨迹列表,点开其中一个,**看到第 12 步的标注截图上 Agent 把"取消订单"识别成了 `id=8` 的确认按钮**,
右侧时间轴显示这一步之后触发了一次未预期的导航。他把这 7 条轨迹一键导出成评测集,
修完提示词后重跑,并在回放器里对比新旧两条路径的分叉点。

全过程不需要 SSH 进任何容器,不需要看一行原始日志。
