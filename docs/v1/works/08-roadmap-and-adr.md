## 2. 决策记录(ADR)

### ADR-001 · 用 kasm/chrome(headful + VNC)而非 headless
**决定**:用。
**理由**:live view 与人接管是本产品的差异化能力,headless 无法提供;真实 headful 渲染也更接近真实用户环境。
**代价**:资源开销显著高于 headless(每会话一个 X + Chrome),冷启动慢,单机密度低。
**缓解**:预热池、积极回收、`capture_level` 分级。若未来出现纯批处理场景,
可增加 `headless` 后端(同一协议、无 live/takeover 能力),而不是改协议。

### ADR-002 · agentd 内部用 Playwright,协议不暴露
**决定**:`connect_over_cdp()` 驱动,但协议层只暴露 browserapi 自己的动作语义。
**理由**:等待/可点击性/iframe/文件上传这些脏活自研成本高且容易错;同时保持替换底层的自由。
**代价**:多一层映射,某些 Playwright 特性无法直通。
**拒绝的方案**:直接暴露 Playwright API——会把实现细节变成公开契约,以后动不了。

### ADR-003 · Python lib 是 service 的瘦客户端
**决定**:lib 与 service 共用 schema 与执行路径,local 模式内嵌精简控制面。
**理由**:消除"本地能跑线上不行";只维护一套语义。
**代价**:lib 有一点不必要的抽象层,极简用法比直接调 Playwright 重。
**取舍结论**:划算。

### ADR-004 · 视口用 X 分辨率控制,不用 CDP emulation override
**决定**:不用 `setDeviceMetricsOverride`。
**理由**:headful 下 override 会导致截图与人看到的画面不一致,破坏"人和 Agent 看同一个画面"这一核心前提。
**代价**:改视口成本高(要重设 Xvnc 分辨率),不能在一个会话里频繁切换视口。
**开放**:移动端视口模拟需求出现时需重新评估(可能需要独立的 `emulation` 会话类型,并在轨迹中标注)。

### ADR-005 · Step 而非 Action 作为轨迹主单位
**决定**:Step = 观测 + 思考 + 动作组 + 效果。
**理由**:Agent 的失败绝大多数是决策失败;只有把四者绑在一起才能定位"哪一步想错了"。
**代价**:要求调用方按 step 组织循环(不强制,但不这么用会损失大部分可见性价值)。

### ADR-006 · 元素稳定签名作为跨 run 对齐键
**决定**:`sha256(role‖name‖dom骨架‖frame)`,而非元素编号或 CSS 选择器。
**理由**:编号每次观测都变,选择器随构建哈希变;签名对同一控件跨访问稳定,是路径对比与脚本降级的基础。
**风险**:同页多个同名同 role 控件会冲突(靠 `nth` 消歧);站点改版会导致签名失效——
这**恰好是想要的信号**(`page_changed` 归因)。

### ADR-007 · 轨迹写入异步、Step 边界同步 flush
**决定**:如 [04 §8](04-trajectory-model.md)。
**理由**:纯同步会把动作延迟拖高;纯异步会在崩溃时丢掉最有价值的最后几步。
**代价**:每步多 10–30ms。

### ADR-008 · 不做 `shared` 双向同时操作(v1)
**决定**:控制权在 `agent` / `human` 之间互斥切换。
**理由**:并发输入的冲突语义和留痕都很难做对,收益不清晰。
**重新评估触发条件**:出现真实的"人边看边微调、Agent 继续跑"需求。

### ADR-009 · 不内置 LLM
**决定**:browserapi 只做手和眼。
**理由**:模型选择、提示词、规划策略变化极快,内置会迅速过时并绑架使用方。
**补偿**:提供 `as_tools()` 适配器与 `reasoning` 上报位,让接入成本足够低。

## 4. 下一步

按依赖顺序,建议的落地顺序是:
**Q1 实测 → M0 的 agentd + 观测层 → 最小回放器 → 用 Q2 的基准集校准观测质量 → 再往 M1 服务化推。**

先做回放器(哪怕很粗糙)的理由:它是这个项目的"体温计"。
观测层好不好、settle 阈值对不对、动作语义缺不缺,在回放器里看几条真实轨迹就一目了然,
而这些问题在单元测试里几乎发现不了。
