# 一种新的界面 · HTTP 上的一扇窗,加一个能控它的把手

> 这篇讲的不是 webmuxd,是 webmuxd 和 tmuxd **共同属于的那个东西**:
> 它们从哪来、为什么长成同一个形状、为什么是两个项目而不是一个,
> 以及下一个成员要满足什么。

## 1. 从哪来:shellbase 剩下的那两块

[shellbase](https://github.com/) 是一块可自由分割的画布,把终端、浏览器、文件
融进同一屏。它 v1 里有两处"先欠着":

- **终端**是网关后面反代的一个 ttyd,ttyd 挂在 tmux 上。能用,但那是**拼在架构里的**,
  不是一个可以单独拿出来的东西。
- **浏览器面板是纯前端 iframe** —— v1 的原话是"容器内 headless 浏览器
  (CDP screencast / noVNC)留给 v2"。也就是说,**那一块当时根本没做**。

这两块有个共同点:**它们都不该是某个产品的内部零件。**

一个活着的终端、一个能被人和程序同时用的浏览器 —— 这是两种**独立成立的能力**。
把它们留在 shellbase 里,后果是:别人想要一个持久终端,得把整个工作台搬走;
而我们自己想换浏览器实现,得动网关。

所以抽出来,成了 `tmuxd` 和 `webmuxd`。shellbase 从"自己实现"变成"**组织展示**" ——
它仍然是那块画布,但每个块背后是一个独立模块。

## 2. 共同的形状:一扇窗 + 一个把手

抽出来之后,两个项目露出了**同一个形状**:

```
        一扇窗    HTTP 上的一个端口      ← 人打开就能看,而且能直接上手
        一个把手  Python 里的一个对象    ← 程序驱动它
                          ↑
                    同一个东西
```

`tmuxd` 的窗是 ttyd 的端口,把手是 `Session.send()`;
`webmuxd` 的窗是 VNC 的端口,把手是 `Tab.click()`。
**除此之外它们没有共享任何一行代码。**

### 2.1 为什么窗必须在 HTTP 上

不是"顺便支持一下浏览器",是**只做浏览器**:

- **分享就是发一个 URL。** 不用装客户端、不用配 SSH key、不用讲"你先装个 VNC 客户端"。
- **人和程序看的是同一块。** 程序点了什么,人在窗里立刻看见;人伸手改了什么,
  程序下一次读到的就是改完的。**不是两份状态,是一份。**
- **窗活得比连接久。** 关掉网页,里面照常在跑 —— 这是 tmux 教给所有人的那件事,
  浏览器那边同样成立。

### 2.2 为什么把手必须是库,不是服务

**先有库,需要的时候才把它暴露出去。** 大多数调用方(编排程序、Web 后端、脚本)
本来就和它在同一个进程里,让它们绕一圈 HTTP 去调自己进程里就能做的事,是白交的税。

所以 `pip install` 完就能用,不需要先起一个 server:

```python
t = Tmuxd(port=12345);        s = t.session(id="work");  s.send("跑测试", enter=True)
w = Webmuxd();                s = w.session(id="work", port=7900);  s.open(url).click("提交")
```

## 3. HTTP API 存在的唯一理由:让模块能被独立验证

这条要写死,因为它决定了 API 的所有取舍。

**API 不是为了给外部当产品用的。** 它存在,是为了让 tmuxd 和 webmuxd
**能作为独立模块被验证** —— 不依赖任何上层、不需要把 shellbase 拖进来,
就能证明"这个模块自己是对的":

```bash
webmuxd new -s demo -p 7900 && webmuxd click -t demo "提交订单"
curl -s localhost:7900/api/tabs | jq
```

一个模块如果只能在集成环境里被证明是对的,它就还没有真的独立出来。

由此推出三条:

1. **API 不做 lib 没有的事。** 反过来可以 —— `with` 自动清理、`obs[12]` 下标
   这些是纯客户端的东西,导出去没意义。
2. **API 不必优雅。** 它的读者是调试的人和验证脚本,不是产品用户。
   为它做版本兼容、做 SDK 生成、做 OpenAPI 美化,都是错配的投入。
3. **上层不该被迫走 API。** shellbase 用它们的正确方式是 `import`,不是 HTTP。
   API 在那儿,是为了让"不 import 也能验一遍"这件事永远成立。

> 这比早先"为调试和非 Python 集成而加"([README](README.md))收窄了一点:
> 非 Python 集成仍然能用,但那是**顺带**,不是理由。理由只有"可独立验证"这一条。

## 4. 三种包法,同一个规范

同一个形状,底下包的东西完全不同:

| | 包的是 | 例子 |
| --- | --- | --- |
| **一个进程** | 一个现成的服务端 | tmuxd 的 ttyd:`-p <port> -a -W -c user:pw attach.sh` |
| **多个进程** | 自己拼一套 | webmuxd 的 `process` runtime:chromium + Xvnc + sessiond |
| **多个镜像** | 别人做好的整机 | webmuxd 的 `container` runtime:kasmweb / jlesage / linuxserver |

**"包多个镜像"是最有意思的一种。** 它意味着窗那一半整个是别人的产品,
我们只挑一个、把它的端口报出来。挑的依据是体验,而换的时候**我们一行都不改** ——
因为窗不在契约里([works/08](works/08-browser-runtime.md))。

这三种没有优劣,**只是被包的东西成熟度不同**。规范管的是它们对外长什么样,
不是里面怎么实现。

## 5. 规范:一个 `*muxd` 要满足什么

七条。前四条是形状,后三条是脾气。

**① 两个端点,别的都不算。**
一个人能打开的 HTTP 端口,一个程序能驱动的把手。产出这两样就是合法实现 ——
是不是容器、是不是这台机器,都不在契约里。

**② 分清哪一半在契约里。**
用户会直接碰到的那一半是契约(tmuxd 的 tmux、webmuxd 的 CDP),
用户碰不到的那一半是实现细节(tmuxd 的 ttyd、webmuxd 的 VNC)。
**契约那半不能换,实现细节那半随时能换。** 判据不是"谁更重要" —— 两个都缺不得。

**③ id 幂等,端口必须传。**
`session(id="work")` 同一个 id 永远给你同一个,没有 `create()` 和 `get()` 之分
—— 像 `tmux new -A -s`。端口是**部署决定的**,我们不替你猜、不自动分配:
猜一个只会让你的配置和实际对不上。

**④ 活得比连接久。**
关掉网页,里面照常在跑。这是这一族存在的前提,不是特性。

**⑤ 没有配置文件。**
参数从 lib 传。`~/.xxxd.json` 只记**机器的事实**(哪个二进制在哪、docker 通不通),
不记你的选择 —— 键在=探到了,键不在=没探到。

**⑥ 日志就是 scrollback。**
它每一步看到什么、做了什么、结果变成什么样,按 tmux 的 `history-limit` 那种方式
留着、切割。**不是给机器对账的事件流,是给人和模型回看的。**

**⑦ 不代理那扇窗。**
不做 `/s/<id>/` 这类自己发明的路径、不做 302、不 tee 一份流。
只把 URL 报出来 —— 怎么摆、要不要套一层网关,是上层的事。

## 6. 为什么是两个项目,不是一个

**因为共享的只是形状,不是代码。** 底下的技术细节差得太远,合成一个的结果是
一个到处 `if kind == "term"` 的框架,而不是一个更强的东西。

| | tmuxd | webmuxd |
| --- | --- | --- |
| 契约那一半 | `tmux` 命令行 | **CDP**(WebSocket 协议) |
| 状态在哪 | tmux server 自己管,我们只发命令 | 我们**自己维护一份 tab 表**,靠事件流对齐 |
| 驱动方式 | `send-keys` 一句话 | 定位 → 动作 → 等待稳定 → 观测,四段 |
| "看见"是什么 | `capture-pane` 拿文本 | AX 树 + 标注截图,喂多模态模型 |
| 窗那一半 | ttyd,一个静态二进制 | 一整个桌面镜像(4 GB 级) |
| 最难的地方 | 依赖怎么装(ttyd 不在多数发行版仓库里) | **CDP 怎么出容器**(Chromium 只肯听 loopback) |
| 失败长什么样 | 进程没了 | 页面卡住、元素找不到、截图超时 |

**唯一真正共享的是那七条规范** —— 而规范应该长在文档里,不是长成一个基类。

一个反面例子:如果强行统一,`Tab` 和 `Pane` 就得抽象成同一个"块",
而它们唯一的共同点是"有个 id"。为这点共性付出的代价,是两边都得迁就那个抽象。

## 7. 下一个成员会长什么样

这个形状不止能装终端和浏览器。任何**"人要看着、程序要驱动、而且得活着"**的东西
都能套进来 —— 比如一个文件工作区、一个数据库客户端、一个笔记本内核。

新成员进来只需要回答:

1. 窗是什么?(哪个现成的 web 服务端能当它)
2. 把手是什么?(哪个协议/命令行能驱动它)
3. 这两者里,**哪一半是用户会直接碰到的**?(那半就是契约)

答不出第 3 条,就还没想清楚该抽什么。
