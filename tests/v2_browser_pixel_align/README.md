# v2 · 像素对齐

**人的窗口多大,里面那个浏览器就多大。**

ttyd 把终端调成你窗口那么大,tmux 里的 80 列就真是 80 列。这一条我们也得做到 ——
不然人拉大窗口只是把同一张图放大,越拉越糊。

## 判据

三个数**同时**相等:

    人窗口里给画面留的那块地  ==  画面元素占的地  ==  帧本身的像素

少验哪一个都漏掉一整类错:

- 只比前两个:一张 1024 宽的图撑在 1260 的框里也算"对齐"(其实是拉伸)。
- 只比后两个:元素被 CSS 缩过一道,看不出来。

再加一条**页面自己以为的宽度** —— 截图可以是对的而页面按另一个宽度排版,
那时候人看到的图没问题,agent 拿到的元素坐标却是另一套。

## 两条腿,两套机理

| | 怎么变的 |
|---|---|
| **JPG** | 一条 CDP 命令改视口(`Emulation.setDeviceMetricsOverride`),截图跟着出。三个数严丝合缝。 |
| **VNC** | 画面是一个真的 X 桌面。观看端报尺寸 → xpra 调 X 显示 → 服务端把新尺寸回给观看端 → 观看端这才让我们去摁那个 chrome 窗口。 |

VNC 那条链上**每一环都真断过一次**,记在 [works/test.md](../../docs/v2/works/test.md)。

DOM 那条腿这一轮不验:它重放的是 DOM,尺寸的判据是另一回事。

## 两个数字上的讲究

- **尺寸里掺奇数**(1151x641)。全用偶数的话,一个 `//2*2` 的舍入 bug 可以一路蒙混过去。
- **页面故意选不滚动的那个**(example.com)。`cssVisualViewport` 是**不含滚动条**的 ——
  拿会滚的页面来验"页面自己的宽度",量的就不是对齐,是滚动条宽度(15 像素)。

## VNC 那条腿的形状

**画面不是那个 X 桌面,是桌面里那个 chrome 窗口。**

桌面一次开到 4K 就不动了;窗口用三条 CDP 命令摁成人要的大小、钉在左上角
(`normal → bounds → fullscreen`,顺序是死的,理由写在
`webmuxd/screen.py: _fill_screen()`);观看端只把画布建成那么大,
xpra 送来的瓦片超出画布的部分 canvas 自己就丢掉了。

于是**和 JPG 是同一个心智模型**:画面多大由我们定。

一度不是这样:让观看端把尺寸报给 xpra、由 xpra 去改 X 显示。那条链有四个环、
每一环都真断过一次,还逼出了一个 Xorg 依赖和一个一像素的缝
(chrome 不接受一个正好等于屏幕大小的窗口)。窗口永远比屏幕小之后,
那条规则碰都碰不到。
